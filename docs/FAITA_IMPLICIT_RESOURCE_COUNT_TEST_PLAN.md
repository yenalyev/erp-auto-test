# CPMA-832 — кількість додаткового ресурсу у Fight

## Мета і контракт

Для основного Fight-ресурсу Б можна налаштувати один або кілька додаткових ресурсів.
Кожний зв'язок має додатний цілий множник `count`. Якщо Fight передає використання Б у
кількості `N`, очікуване списання додаткового ресурсу А дорівнює `N × count(A)`.

PUT `/api/v1/integrations/faita/resources/{externalId}/implicit-resources` зберігає повний
список implicit. Отже, зміна count одного рядка не повинна видалити або змінити інші рядки.

## Автоматизоване покриття

### API

- `TC-FAITA-IMPL-001`: зберегти A×2 і C×3; перевірити PUT, GET і JSON у БД.
- `TC-FAITA-IMPL-003`: full-list PUT видаляє C, але зберігає A×2.
- `TC-FAITA-IMPL-004`: змінити A×2 на A×5 і зберегти C×3 без втрати та дублів.
- RBAC implicit endpoint залишається в загальній матриці `FAITA_IMPLICIT_RESOURCES_PUT`.

### Списання і залишки

- `TC-FAITA-IMPL-002`: для usage Б=4 перевірити write-off Б=4, A=8, C=12 зі спільним
  `sourceId`, потім complete і відповідні stock delta на FLY_POINT.
- Цей зовнішній тест використовує DB seed очікуваного результату SyncTeamProcess, тому перевіряє
  журнал, complete та залишки. Тестові `/faita/log` і `/faita/syncTeams` поки не викликаються,
  оскільки sync обробляє глобальну чергу середовища.
- Створення множених write-off безпосередньо job-ом лишається integration-рівнем backend;
  прямий INSERT не вважається доказом роботи імпорту Fight.

### UI

- `TC-UI-FAITA-001`: список показує `назва × count`.
- `TC-UI-FAITA-004`: count=0 заблоковано без PUT; додати A×3; змінити на A×5; видалити A.
- Page object використовує dialog-scoped combobox/input і останню кнопку рядка для видалення,
  оскільки після CPMA-832 першою кнопкою стала дія редагування.

## Додаткова ручна матриця

### Ручний smoke на dev/staging

1. Увійти як ADMIN і підготувати три вже зіставлені FAITA-вироби: основний Б та
   додаткові А і C. Не використовувати `/faita/syncTeams`: job працює з глобальною
   чергою середовища.
2. Відкрити `/faita-resources/{externalId-Б}` → «Додаткові ресурси», вибрати А,
   ввести `count=3` і зберегти. На картці та у списку очікується `А × 3`.
3. Оновити сторінку. Значення `3` має зберегтися. За наявності DB-доступу перевірити
   `crew.sync_process_config.implicit_resource_usage`: для зв’язку Б→А записано `count: 3`.
4. Додати C×2, після чого змінити лише А×3 → А×5. Після refresh очікується рівно
   А×5 і C×2, без втрати C та без дублів.
5. Спробувати `0`, від’ємне та дробове значення. UI має блокувати збереження й не
   надсилати PUT. Значення `1` має зберігатися як валідне backward-compatible.
6. Видалити А кнопкою «−». Після refresh C×2 лишається, А відсутній.
7. Для перевірки фактичного списання використати лише ізольовану реальну Fight-подію
   або погоджене тестове вікно: usage Б=N має створити один набір write-off, де
   amount(А)=N×count(А). Повторна обробка тієї самої події не повинна дублювати набір.

### Release-регресія

Перед release на інтеграційному середовищі перевірити:

1. Fight usage Б=1 і count=1 — backward-compatible списання А=1.
2. Кілька implicit з різними count створюють окремі write-off без дублів.
3. Ammunition та initiator однаково застосовують множник.
4. Повторний sync тієї самої Fight-події не дублює набір write-off.
5. Зміна count впливає лише на нові Fight-події, не перераховує історичні.
6. На межі stock `N × count` списання успішне; за недостатнього залишку немає часткового debit.
7. Старий запис конфігурації без `count` повертається як `count=1`.

## Відомі межі контракту

- UI дозволяє лише ціле значення `≥ 1`; дробовий count не входить у контракт.
- В автотестах немає перевірки прямого API з `0`, від'ємним або відсутнім count, доки backend
  не має узгодженої серверної валідації. UI-негатив `count=0` покритий.
- `faita-resources.xml` запускає API CRUD, сценарій write-off і UI. `TC-FAITA-IMPL-002`
  потребує `use.database=true`, інакше він контрольовано пропускається.

## Команда запуску

```bash
mvn test -Denv=dev -Dsuite=faita-resources -Duse.database=true
mvn test -Denv=staging -Dsuite=faita-resources -Duse.database=true
```

  застосування `amount × count`.
- Повний набір 11 автоматизованих FAITA-кейсів синхронізується скриптом
  `scripts/sync_tcm_faita_implicit_resource_count.py` у dev та production TCM.
- Власництво `TC-FAITA-IMPL-001/002` лишається у суміжній `REQ-CREW-003 / AC-15`;
  `REQ-FAITA-001 / AC-04` посилається на них як на cross-feature покриття.
- `TC-FAITA-IMPL-002` у TCM має обов’язкову передумову `-Duse.database=true` і явно
  зазначає, що `/faita/log` та `/faita/syncTeams` не викликаються.

Release gate: усі доступні API/UI кейси PASS; для справжньої Fight інтеграції окремо підтверджено,
що один source event створює рівно один набір write-off з `amount(A) = amount(B) × count(A)`.
