# Інвентаризація під час паралельної видачі

TCM: `REQ-WMS-003`, `AC-21` (атомарне відхилення застарілого snapshot),
`AC-22` (узгодження конфліктів та коректні розбіжності).

Регресія: після відкриття форми інвентаризації й зміни одного ресурсу в іншій
вкладці видають інші ресурси. Збереження старого snapshot не має непомітно
повертати видані кількості на склад та додавати їх у запис інвентаризації.

## Контракт фікса

Форма завантажує склад разом з `items[].version`. PUT
`/storages/{id}/inventory` містить `resources[].resourceId/amount/version`,
`knownResourceIds` і коментар. За зміни версій сервер повертає **412** з
`message`, актуальним `snapshot` і точним `modifiedResourceIds`.
Це відхилення всієї операції: незмінені залишки, жодних нових `ADDED_INV` /
`REMOVED_INV`, процес лишається `OPEN`, дані проведення не заповнюються.

Форма показує «було / зараз / ваше» й блокує submit до узгодження.
«Прийняти всі актуальні» та окреме «Взяти актуальне» оновлюють кількість і
версію. Коментар та неконфліктні зміни зберігаються. Явне «Залишити моє»
залишає цільове значення, але підсумкову різницю рахують від актуального
залишку. Наступна видача після узгодження знову потребує перевірки.

API без версій підтримується задля сумісності зі старими клієнтами.
Тому нові регресійні тести явно використовують payload актуальної UI-форми;
звичайний `InventoryDataFactory.mergeWithExisting` не перевіряє цей захист.

## Дані та очікуваний результат

Окремі тестові склади й три власні ресурси: A=10, B=20, C=30.
У формі змінюють A=15, в іншій вкладці видають B=7 і C=30.
Перший submit — 412; залишки A=10/B=13/C=0. Після прийняття актуальних
і повторного submit — A=15/B=13/C=0. Закритий процес та інвентаризаційна
історія містять тільки A:+5. B/C не повертаються на склад і не входять у diff.

Якщо паралельно видано A=4, форма показує A: було 10 / зараз 6 / ваше 15.
Після свідомого «Залишити моє» A=15, різниця +9.

## Автоматизовані сценарії

- `TC-INV-CONCURRENT-API-001`: часткова та повна видача після snapshot;
  точні конфлікти, атомарність 412, незмінена історія й відкритий процес.
- `TC-INV-CONCURRENT-API-002`: прийняття актуальних B/C, збереження A;
  точні залишки, один diff A:+5 та один ADDED_INV з коментарем.
- `TC-INV-CONCURRENT-API-003`: ще одна видача B=2 після узгодження;
  повторний 412, фінальний B=11 і diff тільки A:+5.
- `TC-INV-CONCURRENT-API-004`: видача редагованого A, 412 і свідоме
  збереження A=15 з різницею +9 від поточного 6.
- `TC-INV-CONCURRENT-UI-001`: дві вкладки, справжня змішана видача,
  «Прийняти всі актуальні», залишки та закритий запис після reload.
- `TC-INV-CONCURRENT-UI-002`: окреме узгодження B/C, submit заблокований
  до останнього вибору; коментар і A=15 не губляться.
- `TC-INV-CONCURRENT-UI-003`: видача A у другій вкладці та явне
  «Залишити моє»; закритий запис містить тільки A:+9.

UI-прогін використовує дві вкладки адміністратора в одному browser context.
Вони тримають незалежні snapshots; перевірка відтворює порядок операцій
з дефекту без залежності від планувальника потоків або випадкових затримок.

## Запуск

```powershell
mvn test -Denv=dev -Dsuite=inventory-concurrent-issue -Dtcm.enabled=false -Dgoogle.sheets.enabled=false -Dsuite.artifact.sweep=false
```

API й UI включені також до `inventory`, `inventory-process`, `regression`;
окремо API до `functional`, UI до `ui`. Нові fixtures працюють лише зі своїми
ресурсами й складами. Cleanup завершує створені видачі, очищує залишки та
архівує власні ресурси й локації; незмінювана історія зберігається.

Фактичний результат прогону та посилання на TCM run зберігаються в
`docs/audits/2026-10-17/inventory-concurrent-issue-report.md`.
