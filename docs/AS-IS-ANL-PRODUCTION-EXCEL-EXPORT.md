## Як змінюються дані на екрані

На вкладці «Статистика» є два незалежні перемикачі:

- **Представлення:** «За категоріями» (`category`), «За тегами» (`tag`),
  «За виробами» (`resource`), «Витрати» (`input`), «Продуктивність»
  (`productivity`).
- **Тип виробництва:** «Виготовлення» (`assembly`), «Розбір»
  (`disassembly`), «Несерійне виробництво» (`nonSeriesProduction`).

Для «Виготовлення» і «Розбору» доступні всі п'ять представлень. «За
категоріями» читає `totals-by-category`, «За тегами» — `totals-by-tag`, «За
виробами» — `output`, «Витрати» — `input`, «Продуктивність» — `productivity`
відповідного `assembly` або `disassembly` API. Для «Несерійного виробництва»
`effectiveTab` примусово дорівнює `input`: доступне лише представлення
«Витрати» через `non-serial/input`.

Період, локації, категорії та вироби зберігаються на рівні сторінки. Але на
«Витратах» панель фільтрів показує **окремий** вибір «Категорії матеріалів» і
«Матеріали». Його `categoryIds`/`resourceIds` описують спожиті матеріали; в
інших представленнях ті самі поля фільтра описують виготовлені вироби.
Локальні пошук за назвою і вибір тегів фільтрують рядки `output`/`input` у
браузері.

## Що передає кнопка «Експорт в Excel»

Кнопка викликає `GET /production/analytic/export` та завантажує отриманий blob
як `.xlsx`. `handleExport` передає:

- `parentStorageId` — вибір у дереві локацій;
- `storageIds` — вибрані або доступні актору локації;
- `fromDate`, `toDate` — поточний період;
- `kind`: `assembly`, `disassembly` або `non-serial` за вибраним типом;
- `categoryIds`, `resourceIds`: на «Витратах» — ID з окремого вибору
  матеріалів; в інших представленнях — ID виробів зі стану сторінки;
- `tags` і `resourceName`: локальні фільтри рядків, якщо активні «За виробами»
  або «Витрати»;
- `rawResources=true` лише коли активні «Витрати» та увімкнений чекбокс
  «Лише матеріали».

Цю передачу активного контексту додано у frontend commit `c55f552`. Саме
перемикання типу змінює `kind` у запиті; перемикання на «Витрати» змінює
джерело `categoryIds/resourceIds`. Для «За категоріями», «За тегами» і
«Продуктивність» явний параметр представлення не передається. Backend
контракт нижче ще не підтримує нові `kind`, `tags`, `resourceName`.

## Як backend формує workbook

`ProductionAnalyticController` передає заповнений із query parameters
`ProductionAnalyticExportFilter` до `ProductionAnalyticExportFacade`. Record
містить лише сім полів: `parentStorageId`, `storageIds`, `fromDate`, `toDate`,
`categoryIds`, `resourceIds`, `rawResources`. Полів для `kind`, `tags`,
`resourceName` чи активного представлення немає. Отже, ці нові frontend
параметри не можуть вплинути на файл у поточному backend. Фасад послідовно
створює **всі п'ять аркушів**, навіть якщо відповідна вибірка не має рядків:

1. `Виготовлення - За виробами` — `getOutput` для `PRODUCTION`;
2. `Виготовлення - Витрати` — `getInput` для `PRODUCTION`;
3. `Розбір - За виробами` — `getOutput` для `DISASSEMBLE`;
4. `Розбір - Витрати` — `getInput` для `DISASSEMBLE`;
5. `Несерійне виробництво - Витрати` — non-serial `getInput`.

На двох аркушах результатів заголовки: `Ресурс`, `Категорія`, `Теги`,
`Кількість записів`, `Обсяг`, `Од. вимір`. На трьох аркушах витрат немає
`Кількість записів`; решта заголовків ті самі. `Обсяг` і кількість записів
записуються як числові Excel-комірки. Файл має ім'я
`Аналітика виробництва.xlsx`.

`SerialProductionFilter.from` передає період, локації, категорії й ресурси до
аркушів результатів. `AssemblyInputFilter.from` передає ці самі ID до
аркушів витрат і додає `rawResources`. SQL застосовує `categoryIds` і
`resourceIds` **до готового ресурсу** у `getOutput`, але **до спожитого
матеріалу** у серійному та несерійному `getInput`. Це однакові параметри
запиту з різним предметним значенням на різних аркушах. `rawResources`
використовується лише для витрат: ресурс з активною технологічною картою
виключається, коли параметр істинний.

## Підтвердження на DEV

Підтверджено один валідний XLSX із п'ятьма видимими аркушами в наведеному
вище порядку.

`TC-ANL-UI-015` на DEV 2026-09-28 порівнював файл після «Виготовлення → За категоріями»
та «Розбір → Витрати» з незмінними фільтрами і підтверджує **однакові дані всіх
п'яти аркушів у цих двох станах**. Інші комбінації табів цей тест не перебирає;
цей прогін не доводить поведінку всіх інших станів або те, яка версія frontend
була розгорнута на DEV. Поточний backend залишається загальним багатолистовим
експортом: усі п'ять аркушів формуються з одного набору фільтрів. Він враховує
період, локації, `categoryIds`/`resourceIds` і `rawResources`, але ігнорує
нові `kind`, `tags`, `resourceName` з frontend запиту.

Попередній DEV-прогін 2026-09-28 завершився як **22 passed, 2 failed**. У
`TC-ANL-UI-022` і `023` файл містив вибрані готові вироби,
але не містить пов'язаних із ними ресурсів витрат, яких очікувала попередня
версія acceptance contract. Backend код пояснює результат: `resourceIds` готового
виробу повторно застосовуються до `resourceId` спожитого матеріалу на
аркушах витрат. Це була **невідповідність старому контракту**, а код визначає
її причину; це не доказ залежності від активного таба. Після уточнення
користувача витратні рядки мають відповідати **окремому фільтру матеріалів**;
старі assertions більше не є чинними критеріями дефекту. Два оновлені тести
після вибору окремих UI-фільтрів матеріалів пройшли на DEV у прицільному
прогоні (**2/2**), а повторний повний `ProductionAnalyticsUiTest` завершився
як **24 passed, 0 failed** (2026-09-28 11:10 EEST).

Обидві невдалі assertions виконуються після прямих API-запитів зі значеннями
фільтра виробів; перевірки UI export URL у цих тестах пройшли. Детальний
розбір кроків і запитів є у [звіті прогону](audits/2026-09-28/production-analytics-excel-export-dev-test-report.md).

## Узгоджений контракт і залишкові прогалини

Frontend уже надсилає частину активного контексту, але backend ще не
використовує `kind`, `tags` і `resourceName`. Вибір «Витрати» може змінити файл
через інші `categoryIds/resourceIds`, проте ті самі ID застосовуються до всіх
п'яти аркушів із різною семантикою готового виробу та матеріалу. Поточний
[acceptance contract](REQ-ANL-PRODUCTION-EXCEL-EXPORT.md) визначає результат
окремого фільтра матеріалів для витратних рядків. П'ять аркушів залишаються в
кожному файлі. `TC-ANL-UI-015` перевіряє перемикання між двома табами без
активних фільтрів; `TC-ANL-UI-022`, `023` оновлено для перевірки окремого
вибору матеріалів. Відсутність обробки `kind`, `tags`, `resourceName` у backend
залишається прогалиною: сам по собі вибір типу, тегів або локального пошуку
не змінює рядки XLSX. Деталі повторної перевірки наведено у звіті прогону.
