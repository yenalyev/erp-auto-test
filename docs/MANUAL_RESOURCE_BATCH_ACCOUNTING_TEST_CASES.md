# Тест-кейси: ручний вибір партії ресурсу

Базові передумови: керівник має доступ до локації A; є локація B, ресурси R1 і R2 та дві партії R1 (рання P1 і пізня P2, по 10 одиниць). Якщо в кейсі не зазначено інше, R1 на A має режим `MANUAL`, R2 — FIFO. Для кожної відмови звірити журнал і залишки P1/P2 до й після запиту. Ідентифікатори праворуч відповідають `@TestCaseId` у тематичній suite.

## Налаштування та фільтр

1. **TC-MIB-001, API.** Для R1 на A перевірити початковий FIFO, увімкнути ручний режим як керівник A; GET налаштування та фільтр `batchSelection=true` містять R1. На B R1 залишається FIFO. Анонім та керівник чужої локації не можуть змінити режим. Вимкнення повертає R1 у FIFO.
2. **TC-MIB-002/003, UI.** У списку ресурсів A знайти R1, увімкнути перемикач, перезавантажити сторінку. Він залишається увімкненим. Фільтр «Обліковувати попартійно» показує R1; «Не попартійно (FIFO)» його виключає і показує R2; «Усі способи обліку» повертає обидва. Вимкнення зберігається.

## П'ять операцій витрати

3. **TC-MIB-004 / TC-MIB-UI-004, серійне.** Створити техкарту з R1, увімкнути MANUAL. Без UUID запит відхилений. Обрати P2 і створити виробництво: кількість P2 зменшується на норму, P1 незмінна; UI дає вибрати P2. У перегляді виробленої партії інгредієнт R1 має `selection=MANUAL` та назву P2, а FIFO-інгредієнт — `selection=FIFO`. У FIFO явний UUID відхилений.
4. **TC-MIB-005 / TC-MIB-UI-005, несерійне.** Створити виріб із фактичною витратою R1: без UUID відмова, з P2 успіх. Відповідь зберігає UUID, списання йде тільки з P2; UI має той самий результат.
5. **TC-MIB-006 / TC-MIB-UI-006, проєктне.** Додати етап із планом R1 і нульовою фактичною витратою без партії — успіх без списання. Записати фактичну витрату без UUID — відмова. З P2 — успіх, подальше збільшення кількості коректно дописує різницю. Недійсний UUID не змінює залишку. Після завершення проєкту вибір зберігається.
6. **TC-MIB-007 / TC-MIB-UI-007, передача.** Відправити R1 з A в B з P2: на A P2 зменшується, P1 незмінна; у переміщенні є UUID P2. Після приймання B має відповідну партію. UI дозволяє ввести кількість обраної партії.
7. **TC-MIB-008 / TC-MIB-UI-008, брак на складі.** Створити брак R1 з P2: списується тільки P2, запис містить UUID. Видалити брак: кількість P2 відновлюється, P1 незмінна.

## Відмови, точність і життєвий цикл

8. **TC-MIB-009/010/024.** Без партії, з чужим/неіснуючим UUID, із замалою кількістю партії чи некоректною сумою розбиття передача, брак і виробництво відхиляються. Журнал і всі залишки незмінні.
9. **TC-MIB-011/018.** У виробництві R1 у MANUAL і R2 у FIFO обробляються разом; R2 не приймає явний UUID. Для двох MANUAL ресурсів можна обрати різні партії; відмова одного рядка не списує інший.
10. **TC-MIB-012/013/016.** Повторена назва партії не підміняє UUID; застарілий/вичерпаний вибір відхиляється; дробова витрата списується з потрібною точністю.
11. **TC-MIB-014/019/020.** Перемкнути FIFO → MANUAL → FIFO після попередніх витрат. Історичні списання не змінюються; редагування переміщення або браку після перемикання вимагає коректної вихідної партії.
12. **TC-MIB-015/025 / TC-MIB-UI-015.** Змінити партію або кількість витрати у несерійному виробництві чи складському браку: старе списання повертається рівно один раз, нове застосовується рівно один раз; невалідне редагування не змінює результат.
13. **TC-MIB-017 / TC-MIB-UI-017.** Для партії невідомого походження, яка реально має залишок, вибір можливий і списує тільки її.
14. **TC-MIB-022/023.** Розбити переміщення або брак між P1 і P2; сума рядків дорівнює загальній кількості. Повернення чи видалення відновлює обидві партії.

## Критерій оцінки

Успіх: усі критичні кейси 1–7 проходять, відмови не змінюють запасу, а звіт TestNG не містить помилок або нез'ясованих пропусків. Кожне падіння слід класифікувати за доказом з відповіді API, UI-скріншота або fixture; тест не пом'якшується під дефект продукту.
