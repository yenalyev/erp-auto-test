# Попартійний облік ресурсів, витрачених на виробництво

## Призначення

Керівник локації визначає для окремого ресурсу, чи система автоматично списує найстарішу доступну партію (FIFO), чи користувач явно вибирає партію при кожній витраті (MANUAL). Налаштування діє для пари **ресурс + локація**. Наприклад, для того самого кабелю на локації A може діяти MANUAL, а на B — FIFO.

## Сценарій користувача

1. Вибрати робочу локацію й відкрити «Довідники ресурсів» → «Ресурси».
2. Знайти ресурс і увімкнути «Обліковувати попартійно». Поточний стан зберігається після перезавантаження. Фільтр «Усі способи обліку / Обліковувати попартійно / Не попартійно (FIFO)» дозволяє знайти ресурси за режимом.
3. У формі операції з фактичною витратою вказати партію, доступну саме в локації списання, та кількість з цієї партії. За потреби розбити кількість між кількома партіями, якщо форма операції це підтримує.
4. Після збереження перевірити партії у записі операції та залишки. Для виробленої партії перегляд інгредієнтів має показувати `MANUAL` для явно обраної партії й `FIFO` для автоматично списаної.

## Правила

- Режим нової пари ресурс + локація — FIFO.
- Режим змінює спосіб **майбутнього списання**. Він не змінює історичні витрати, походження партії чи залишки сам по собі.
- У MANUAL фактичну витрату без партії, з партією іншого ресурсу/локації або понад доступний залишок слід відхилити без часткового списання.
- У FIFO система вибирає партії автоматично; передача явного UUID у виробничому запиті відхиляється.
- Для проєктного виробництва партія потрібна при **фактичній витраті**, а не при внесенні плану з нульовою витратою.
- При редагуванні, скасуванні чи видаленні операції списані кількості мають повернутися в початкові партії; новий вибір застосовується один раз.
- Для передачі режим визначається локацією, з якої знімається запас. Режим локації одержувача від цього не змінюється.

## Операції в межах функції

Серійне виробництво, несерійне виробництво, фактична витрата на етапі проєктного виробництва, передача ресурсу на іншу локацію та брак на складі. API налаштування: `GET /api/v1/storages/{storageId}/batch-selection-resources` повертає ID ресурсів у MANUAL; `PUT /api/v1/storages/{storageId}/batch-selection-resources/{resourceId}` із тілом `{"enabled":true|false}` змінює режим. Список ресурсів підтримує фільтр `storageId` + `batchSelection`.

## Питання до продукту

Формулювання «в партіях вказувати MANUAL» потребує уточнення місця відображення для передачі й складського браку: зараз спосіб вибору зберігається у записах витрати, а перегляд виробленої партії показує його для інгредієнтів. Також варто затвердити, чи дозволено розбиття одного ресурсного рядка на кілька партій у **кожній** з п'яти форм, і чи поширюється вимога на повернення від екіпажа. Тест-план перевіряє всі контури, що вже представлені в автоматизованій suite, та явно фіксує ці межі.

## Стан перевірки на ERP dev — 15.10.2026

Повний прогін `manual-input-batches`: **30 тестів, 24 пройшли, 6 впали** (API 19/22, UI 5/8). Порівняно з 14.10 набір падінь не змінився. Цей результат стосується **ERP dev**; публікація документації в production TCM не означає перевірку ERP production.

Відкриті дефекти розділено за компонентом:

- **Бекенд, передача** (`TC-MIB-009`, `TC-MIB-019`): створення та редагування відправлення ресурсу в MANUAL без явної партії повертають `200` замість відхилення.
- **Бекенд, складський брак** (`TC-MIB-009`, `TC-MIB-020`): створення та редагування складського браку в MANUAL без явної партії повертають `200` замість відхилення.
- **Фронтенд, створення складського браку** (`TC-MIB-UI-008`, `TC-MIB-UI-017`): для невиробленої партії сировини (`isProduced=false`) з додатним залишком форма не показує таблицю «Партії», хоча MANUAL увімкнено й API повертає партію. Контрольний сценарій із `isProduced=true` таблицю показує.
- **Фронтенд, редагування складського браку** (`TC-MIB-UI-015`): після створення браку у FIFO та перемикання ресурсу на MANUAL форма редагування не показує вибір партії.

Приймання фічі потребує явного вибору партії в усіх п'яти операціях витрати та успішного повторного прогону всіх 30 тестів. Детальні відповіді API й скриншоти наведено в [dev-звіті](MANUAL_RESOURCE_BATCH_ACCOUNTING_DEV_REPORT.md).
