# Проведення інвентаризації з двома ролями

Користувач з одночасними ролями «Екіпажі: облік» і «Керівник локації» має проводити відкриту інвентаризацію в межах призначеного доступу без помилки 403. Перевірки охоплюють звичайну локацію, вільний екіпаж і точку вильоту, прямі призначення та успадкування прав.

## Уточнення областей призначення ролей — 22.10.2026

Назви двох ролей не визначають повний доступ користувача. У кожному сценарії потрібно окремо записати для **кожної** ролі: обрану локацію, включення підлокацій і обрані типи — локації, екіпажі та точки вильоту.

Поточний клієнт `tk-ui/src/pages/access/GrantDialog.tsx` надсилає `scopeKind=LOCATION` для «лише ця локація». Для «Включно з підлокаціями» він надсилає `scopeKind=SUBTREE` та `storageKinds`: `LOCATION`, `CREW`, `FLY_POINT` у вибраній комбінації; усі три типи позначаються `null`. Вибір типів доступний лише при включенні підлокацій. Тип `CREW` та тип `FLY_POINT` вибираються окремо; виключення екіпажів не означає виключення точок вильоту. Фільтр типів застосовується також до обраного кореня.

При перевірці варіантів ролі «Керівник локації» область ролі «Екіпажі: облік» має бути явно зафіксована. Відсутність доступу від однієї ролі не означає заборону, якщо його надає друга роль. Очікування API/UI визначається сукупним доступом до конкретної цілі, включно з ефективним `inventory.adjust`.

Сценарії 001/002 нижче — окремі граничні перевірки прямих призначень на CREW/FLY_POINT без доступної звичайної робочої локації. Вони **не є загальною передумовою** для користувачів з двома ролями та не перевіряють фільтр `storageKinds`. Сценарії 003/004 перевіряють SUBTREE без фільтра типів; 005/006 — LOCATION на предку. Нові 008–019 перевіряють окремі області двох ролей та фільтри типів за уточненою схемою призначень на батальйоні й складі. Результати старих прогонів 001–007 не підтверджують виконання нової матриці.

## Правила доступу

- **AC-25:** Обидві ролі дозволяють провести OPEN інвентаризацію безпосередньо на доступній локації без підлокацій: звичайний підрозділ UNIT, вільний CREW або FLY_POINT. Призначення обох ролей зі сферою SUBTREE на предку дозволяє проведення на дочірньому екіпажі чи точці вильоту. API повертає 200, UI відкриває форму і зберігає зміни, процес стає CLOSED; авторство, коментар та розбіжності відповідають проведенню. Контрольний склад залишається без змін. Повторне проведення без нового OPEN відхиляється з 403.
- **AC-26:** Обидві ролі зі сферою LOCATION на предку без інших призначень не дозволяють провести інвентаризацію дочірнього CREW або FLY_POINT. API повертає 403, пряме посилання на редактор не надає редагування; залишки та OPEN процес незмінні.

- **AC-27:** За двох призначень «Екіпажі: облік» на батальйоні та його складі й окремого призначення «Керівник локації» на батальйоні проведення OPEN інвентаризації дочірньої точки чи екіпажу відповідає об'єднанню областей ролей і фільтрам типів. Дозволена ціль доступна в UI і зберігається з API 200; виключена обома ролями ціль повертає 403, не надає редактор і не змінює процес чи залишки. Типи CREW та FLY_POINT перевіряються незалежно.

## Передумови та дані

Для кожного сценарію створюється новий користувач U з рівно двома названими ролями. У 001–007 це два призначення, у 008–019 — три призначення (облік на B/W і керівник на B). Глобальні ролі, індивідуальні дозволи й попередні призначення відсутні. Тест перевіряє збережені grants та ефективне `inventory.adjust` на цілі T до виконання дії.

На T є унікальні ресурси R=10 і S=4; на окремому контрольному складі K є R=7. Користувач змінює лише R на 6, коментар — «Перевірка прав інвентаризації». Очікується R=-4 у розбіжностях, S=4 і K/R=7. Вільний екіпаж не прикріплений до точки вильоту. Ціль у прямому сценарії не має дітей; K є сусідньою локацією.

Адміністратор створює запит і погоджує інвентаризацію до OPEN. Це перевірка проведення користувачем U, а не його права погоджувати запити. Для успішного сценарію API та UI проводять два окремі OPEN процеси на тій самій цілі, з відновленням R=10 перед UI.

## Матриця призначень на батальйоні та складі

Користувач підтвердив два одночасні призначення ролі «Екіпажі: облік» одному користувачу: окремо на батальйон B та на його склад W. Для обох призначень перевіряються LOCATION і SUBTREE без фільтра типів. Це два варіанти області, а не два різні користувачі з одним призначенням.

Ізольована ієрархія: звичайна локація B з `milUnitType=BATALION` → склад W → ціль T (FLY_POINT або вільний CREW); контрольний склад K є окремою дитиною B. Роль «Керівник локації» призначена на B з однією з п'яти конфігурацій: LOCATION; SUBTREE лише LOCATION; SUBTREE LOCATION+CREW; SUBTREE LOCATION+FLY_POINT; SUBTREE усі типи. Користувач має доступ до звичайних B і W, тому обмеження старих сценаріїв 001/002 тут відсутнє.

Збережено рівно три призначення двох ролей: два «Екіпажі: облік» і один «Керівник локації». Тест перевіряє місця призначень, області, точні `storageKinds`, відсутність індивідуальних дозволів і зайвих призначень. Повторне додавання того самого фільтрованого призначення не має створювати дублікат.

Для FLY_POINT при обліку LOCATION на B/W очікується відмова для керівника LOCATION, SUBTREE LOCATION та SUBTREE LOCATION+CREW; дозволено при SUBTREE LOCATION+FLY_POINT та всіх типах. При обліку SUBTREE на B/W точка доступна в усіх п'яти конфігураціях керівника. Для CREW додатково перевірено незалежність фільтрів: керівник LOCATION+CREW дозволяє, LOCATION+FLY_POINT не дозволяє за обліку LOCATION.

Роль «Екіпажі: облік» фіксується в межах кожного сценарію. Очікуване право визначено конфігурацією до запиту ефективних дозволів; відповідь сервера порівнюється з ним і не використовується для вибору очікування.

Окремий набір `crew-inventory-scope-matrix` виконує лише 008–019. Основний `crew-inventory-access`, `ui` та `regression` містять той самий клас і охоплюють також попередні 001–007.

## Кроки позитивних сценаріїв

1. Підготувати дані, перевірити рівно дві ролі, їх сферу та `inventory.adjust=true` на T; створити OPEN процес.
2. Отримати повний snapshot залишків від імені U і виконати PUT інвентаризації з R=6, S=4, актуальними версіями, `knownResourceIds` і коментарем. Очікується 200.
3. Перечитати залишки та процес: T/R=6, T/S=4, K/R=7, CLOSED, `completedBy=U`, точний коментар, єдина розбіжність R=-4.
4. Повторити PUT з актуальним snapshot і R=5 без нового OPEN. Очікується 403; весь завершений процес і залишки незмінні.
5. Відновити R=10, створити окремий OPEN процес, увійти в UI як U та відкрити `/inventory?storageId=T`. Маршрут не має перенаправляти на аналітику чи показувати відмову в доступі.
6. Натиснути проведення, перевірити R=10 у формі, встановити R=6, ввести коментар і зберегти. PUT має стосуватися саме `/api/v1/storages/T/inventory` та повернути 200. Зберегти URL, HTTP-статус і тіло запиту як доказ сабміту. Повторити перевірки збережених даних із кроку 3.
7. Перевідкрити залишки: кнопка проведення недоступна. Повторний API PUT повертає 403, процес і залишки незмінні.

## Кроки негативних сценаріїв

1. Перевірити точну сферу LOCATION на предку та `inventory.adjust=false` на T; зберегти повний OPEN процес і залишки.
2. Виконати PUT з валідним повним snapshot, актуальними версіями, R=6 та коментарем. Очікується саме 403, повний процес і залишки T/K незмінні.
3. Відкрити `/inventory/T` у UI як U. Очікується сторінка заборони або повідомлення про неможливість завантаження з підтвердженим HTTP 403 на читання T. Редаговані рядки R та доступна кнопка збереження відсутні.
4. Повторно перевірити повний незмінний OPEN процес і залишки T/R=10, T/S=4, K/R=7 після відкриття забороненого редактора.

## Контракт клієнта та докази

Тіло PUT відповідає `tk-ui/src/pages/inventory/InventoryEditPage.tsx`: `resources` з `resourceId`, `amount`, `version`; `comment`; `knownResourceIds`. Використано наявні `InventoryFixture`, `InventoryEditPage`, `ApiExecutor` та браузерний вхід. Збереження перевіряється через повторні API GET, а не лише повідомлення UI. Allure містить скріншоти та підтвердження API перед UI.

Попередня діагностика від 19.10.2026 встановила: для прямих ролей на CREW/FLY_POINT API проведення повертав 200, але UI перенаправляв з інвентаризації через відсутність доступної звичайної робочої локації. Це окремий граничний випадок 001/002; він не замінює сценарій звичайної локації 007. Поточний результат визначає новий dev-прогін. Відомий дефект має залишатися FAIL до виправлення продукту.

## Запуск та очищення

Запуск: `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run_crew_inventory_access_dev.ps1`.

Лише нова матриця 008–019: той самий runner з `-Suite crew-inventory-scope-matrix` та окремим `-RunId`.

Набір працює на ERP dev, з Chrome, без JDBC/SSH. Звіти кожного запуску пишуться в окремий каталог `target/crew-inventory-access-*`. Автоматичний імпорт вимкнено у runner, щоб контрольовано опублікувати фактичні результати в обох TCM. Після кожного сценарію закриваються власні процеси, деактивується користувач, обнуляються залишки та архівуються власні локації, деактивуються власні ресурси. Масове очищення чужих або попередніх даних вимкнене.

TCM: production та dev/stage, project 1, feature `REQ-CREW-INVENTORY`, AC-25/26/27. Результати виконання в обох TCM мають environment `dev`; адреса TCM не є середовищем ERP, на якому виконувалися тести.
