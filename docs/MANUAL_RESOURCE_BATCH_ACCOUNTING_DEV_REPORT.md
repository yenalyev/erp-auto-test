# Dev-звіт: ручний вибір партій для витрат ресурсів

Дати прогонів: 14–15.10.2026. Середовище: `dev` (`https://dev.cukerochka.sbs`). Продуктові репозиторії `tk` і `tk-ui` переглянуті лише для читання.

## Актуальний повторний прогін — 15.10.2026

О 17:09 за Києвом завершено повний запуск тієї самої suite `manual-input-batches` командою нижче: **30 тестів, 24 пройшли, 6 впали, 0 помилок виконання, 0 пропущено** (`BUILD FAILURE`). API: **19/22**; UI: **5/8**. Звіт із результатами кожного методу: [TestNG XML](../target/surefire-reports/TEST-TestSuite.xml). Час виконання тестів за TestNG — 451,5 с.

Шість падінь збігаються з попереднім повним прогоном:

- `TC-MIB-009`: `POST /relocations/send` і multipart `POST /defects` без вибраної партії в MANUAL знову повернули `200` замість очікуваного `4xx`. Після тесту створені записи скасовано/видалено; перевірка повернення залишку пройшла.
- `TC-MIB-019`: редагування передачі після FIFO → MANUAL без явної партії повернуло `200` замість `4xx`.
- `TC-MIB-020`: редагування складського браку після FIFO → MANUAL без явної партії повернуло `200` замість `4xx`.
- `TC-MIB-UI-015`: форма редагування FIFO браку після перемикання на MANUAL не показала таблицю «Партії»; очікування виправленого локатора закінчилося таймаутом.
- `TC-MIB-UI-008` і `TC-MIB-UI-017`: форма складського браку не показала таблицю для невиробленої партії сировини, включно з партією невідомого походження. Обидва тести перед відкриттям форми підтвердили через API увімкнений MANUAL і додатний залишок (`isProduced=false`); `UI-008` також підтвердив, що запит самої форми повернув цю партію.

Успішними залишилися, зокрема, явний вибір партії в серійному, несерійному й проєктному виробництві, у передачі, а також створення складського браку з явно переданою партією через API. Порівняно з 14.10 статус suite не змінився. Критерій приймання «усі 30 зелені» **не виконано**.

## Попередній повний прогін — 14.10.2026

Команда:

```powershell
mvn test '-Denv=dev' '-Dsuite=manual-input-batches' '-Dframework.browser.channel=chrome' '-Dtcm.enabled=false' '-Dgoogle.sheets.enabled=false'
```

Попередній прогін, завершений о 16:59 за Києвом: **30 тестів, 24 пройшли, 6 впали, 0 пропущено**. Результат — `BUILD FAILURE`. Його TestNG XML перезаписано повторним прогоном 15.10; скриншоти UI попереднього прогону залишаються в `target/allure-results`. Окремо після виправлення формату запиту три API сценарії складського браку пройшли: `TC-MIB-008`, `TC-MIB-017`, `TC-MIB-023` (**3/3**).

Перед фінальним прогоном прибрано кейс `TC-MIB-UI-017B`: вимога не зобов'язує UI показувати спеціальне пояснення за відсутності невідомої партії. Також прибрано додатковий `TC-MIB-021` про повернення від екіпажа: ця операція не входить до п'яти перелічених у вимозі, а перемикач MANUAL у продукті вимагає локацію з можливістю виробництва, якої точка екіпажа не має.

## Виправлені припущення тестів

- `POST/PUT /api/v1/defects` приймають `multipart/form-data` з JSON-частиною `request`. Загальний JSON-клієнт давав `500` («Something went wrong»). Нові сценарії переведено на `executeDefectCreate` / `executeDefectUpdate`; три позитивні сценарії підтверджено повторним запуском.
- API повертає для невідомої партії назву `Партія невідомого походження`, а не поле `origin`. Пошук і UI тест використовують фактичний `batchNumber`.
- Для ресурсу на новій тестовій локації UI авторизується динамічним керівником саме цієї локації. Статична сесія іншого власника робила перемикач недоступним. Після виправлення `TC-MIB-002/003` пройшли на dev.
- `DefectRequest.isProduced=true` — прапорець явного розкладу партій для складського браку; у рядках сировини `defectBatches[].isProduced=false`. Тест тепер надсилає цю комбінацію, як фронтенд у режимі таблиці партій.
- Прибрано очікування відхилення двох рядків витрати того самого ресурсу: це не випливає з вимоги. Негативні перевірки тепер стосуються лише партій та залишків.

## Підтверджені розбіжності з вимогою

1. **Передача без партії у MANUAL проходить.** `TC-MIB-009`: `POST /relocations/send` повернув `200` без вибраної партії. `TC-MIB-019`: редагування відправлення після FIFO → MANUAL теж повернуло `200` без партії. У локальному `tk` `RelocationValidator.validateSenderBatchStock` перевіряє вказані рядки, але не вимагає їх наявності для MANUAL. Тести залишено негативними.
2. **Складський брак без партії у MANUAL проходить.** Той самий `TC-MIB-009`: multipart `POST /defects` повернув `200`; `TC-MIB-020`: редагування FIFO браку після перемикання на MANUAL повернуло `200` без явного вибору. У локальному `tk` `DefectValidator.validateDefectBatches` пропускає порожній список, а `StorageItemService.take` для `isProduced=false` списує FIFO. Тести залишено як регресійні перевірки вимоги.
3. **UI складського браку не дав вибрати невироблену партію сировини в MANUAL.** `TC-MIB-UI-008` та `TC-MIB-UI-017` чекали таблицю «Партії», яка не з'явилася. У локальному `tk-ui` `DefectFormPage.tsx` у режимі створення вмикає таблицю лише коли серед залишків є `isProduced=true`; налаштування MANUAL для ресурсу не перевіряє.
4. **UI редагування старого FIFO браку приховує партії після перемикання на MANUAL.** `TC-MIB-UI-015` не знайшов таблицю. У `DefectFormPage.tsx` `isProducedHint === false` достроково вимикає `storageBatchMode`.

Ці висновки стосуються поведінки dev у зазначеному прогоні. Перегляд локального коду пояснює результати, але не доводить тотожність його ревізії розгортанню dev.

### Додаткова перевірка UI складського браку після ручної перевірки

О 17:53 за Києвом окремо повторено `TC-MIB-UI-008` на dev з додатковими перевірками перед відкриттям форми. `GET /storages/3552/batch-selection-resources` містив ресурс `4386`, тому MANUAL був увімкнений саме на вибраній локації. `GET /storage-items/batches?storageId=3552&resourceId=4386` повернув партію тесту з `isProduced=false` і додатним залишком. Запит, який зробила сама форма після вибору ресурсу, повернув `200` для тих самих `storageId` і `resourceId` та містив UUID цієї партії. Після цього UI знову показав поле «Кількість» без таблиці «Партії». [Скриншот сировини](../target/allure-results/4b438800-07de-4c36-a38f-299f48afd066-attachment.png).

Контрольний прогін із щойно виробленою партією (`isProduced=true`) показав таблицю «Партії» на цій самій формі. Це також виявило помилку тесту: `CardTitle` у фронтенді — `div`, а старий локатор шукав HTML-заголовок. Локатор сторінки виправлено на `[data-slot='card-title']`. Після цього о 17:59 запущено обидва сценарії: **вироблена партія — пройшов; сировина в MANUAL — знову впав**, бо таблиця не з'явилася. [Скриншот виробленої партії](../target/allure-results/8455f5ab-9343-4cfa-8e30-f8efbe4b790b-attachment.png), [скриншот сировини](../target/allure-results/8a38c8f0-0810-46a5-870c-e14d06c08a65-attachment.png). Контрольний тест був діагностичним і вилучений з постійного набору після прогону.

Отже, причина відсутності таблиці для сировини не в тому, що тест не ввімкнув MANUAL, вибрав іншу локацію чи не мав партії на складі. Якщо ручна перевірка проводилась для виробленої партії, різниця поведінки підтверджена цим контрольним прогоном; параметри ручної перевірки невідомі. Повний результат **30 / 24 / 6** вище стосується попереднього повного прогону; окремі контрольні запуски не змінюють його статистику.

О 18:02 після виправлення локатора окремо повторено `TC-MIB-UI-017`: MANUAL і додатний залишок партії невідомого походження (`isProduced=false`) підтверджені API, але таблиця знову не з'явилася. [Скриншот невідомої партії](../target/allure-results/a7f92f71-0a0f-476b-a6dc-d1a7ecf9108b-attachment.png). Таким чином, обидва регресійні UI кейси залишаються негативними після виправлення помилки локатора.

## Критерій приймання

Повторити актуальний набір командою вище після виправлень у продукті. Критерій приймання — всі 30 тестів зелені, а відхилені запити не змінюють жодного залишку партій.
