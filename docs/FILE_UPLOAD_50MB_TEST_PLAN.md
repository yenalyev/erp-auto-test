# Тест-план: обмеження розміру multipart-завантаження

Основні перевірки оформлено як [TC-UPLOAD-50-01…06](FILE_UPLOAD_50MB_TEST_CASES.md): успішне завантаження, повідомлення про перевищення ліміту в API й UI, фото ресурсу та сумарний запит із 10 файлами по 5 МіБ.

## Підтверджений контракт backend

Джерело істини — поточна реалізація в `tk`:

- `src/main/resources/application.yaml`: `spring.servlet.multipart.max-file-size` і `spring.servlet.multipart.max-request-size` використовують одне значення `${MULTIPART_MAX_SIZE:50MB}`. Отже, **50MB — значення за замовчуванням**; у середовищі воно може бути перевизначене змінною `MULTIPART_MAX_SIZE`. Для Spring `50MB` відповідає 52 428 800 байтам.
- `src/main/java/org/pm/tk/config/ExceptionHandlerConfig.java`: `MaxUploadSizeExceededException` обробляється як **HTTP 400 Bad Request**. Тіло — `Errors` з одним елементом `errors`; у нього `field = null`, а `messages` містить один рядок.
- У локальному checkout `tk/src/main/resources/messages.properties` значення `common.maxUploadSizeExceeded` — «Розмір файлу перевищує допустимий.». **Розгорнутий dev відрізняється від цього checkout**: прогін 26.09.2026 отримав HTTP 400 і `{"errors":[{"field":null,"messages":["Розмір файлу перевищує допустимий 50MB."]}]}`. Автотести для dev перевіряють саме відповідь розгорнутого backend.
- Цей обробник спільний для перевищення ліміту одного файла й загального multipart-запиту; з відповіді неможливо визначити, який саме ліміт спрацював.

Фраза з початкової постановки «Перевищено максимальний розмір <size> на завантажень» **не збігається з фактичною відповіддю dev**. Для тестів dev очікується «Розмір файлу перевищує допустимий 50MB.».

## Обсяг і передумови

Перевіряти реальне значення `MULTIPART_MAX_SIZE` у тестовому середовищі до запуску граничних сценаріїв. Backend-репозиторій тут доступний лише для читання; цей документ не змінює його конфігурацію.

Приклади маршрутів backend з файловими частинами: `POST /api/v1/resources/{id}/image` (`file`), отримання переміщення (`file`), створення обладнання (`file` та зображення позицій), створення проєктного виробництва (`files`) і окреме завантаження файла виробництва. Для граничного тесту достатньо одного маршруту з одним файлом і одного з кількома файлами; решту перевірити короткою регресією.

UI має власні, нижчі за серверний, обмеження: фото ресурсу та обладнання — 5 МБ, вкладення дефекту — 10 МБ, документ обладнання й файл отримання переміщення — 25 МБ. Ці перевірки залишаються чинними; 50MB у backend **не означає**, що кожна форма UI дозволяє вибрати файл такого розміру. Для перевірки серверної межі використовувати прямий API-запит або UI-сценарій без нижчої локальної межі.

## Тестові дані

- `L = 52 428 800` байт для значення `50MB` за замовчуванням; якщо `MULTIPART_MAX_SIZE` перевизначено, обчислити `L` із фактичного значення.
- Валідний для обраного маршруту малий файл і файл поблизу `L`. Для фото потрібне зображення, яке проходить перевірки формату; для довільного файла можна скористатися маршрутом проєктного виробництва.
- Multipart-запити з точно виміряним `Content-Length` по обидва боки від `L`, з урахуванням boundary, заголовків частин, JSON-поля та інших полів.
- Запис із уже збереженим файлом, щоб перевірити стан після відхиленого запиту.

## Сценарії

### P0 — конфігурація та API

1. **Ефективний ліміт.** Перевірити, яке значення `MULTIPART_MAX_SIZE` встановлено у середовищі. За відсутності перевизначення обидва параметри дорівнюють `50MB`. Якщо запит зупиняє proxy або gateway до Spring, зафіксувати його окрему відповідь, не видаючи її за контракт backend.
2. **Позитивний шлях.** Завантажити малий валідний файл; перевірити успіх, можливість одержати файл назад і незмінність його вмісту.
3. **Межа загального запиту.** Підготувати запити з `Content-Length` `L−1`, `L` та `L+1` байт, де кожен файл окремо менший за `L`. Перші два мають пройти за умови валідних даних; `L+1` має бути відхилений з HTTP 400 і зазначеним вище JSON-повідомленням. Сценарій із двома файлами перевіряє сумарний ліміт.
4. **Межа одного файла.** Спробувати файл поблизу `L` і файл `L+1`. Оскільки обидва конфігураційні ліміти однакові, multipart-обгортка робить запит із файлом рівно `L` більшим за `L`: ізольовано підтвердити саме `max-file-size` через цей endpoint не вийде. Документувати цю фактичну межу, а не вимагати успішного завантаження файла рівно 50MB.
5. **Помилка перевищення.** На dev перевірити HTTP 400, `errors[0].field = null` та точне `errors[0].messages[0] = "Розмір файлу перевищує допустимий 50MB."`.
6. **Стан після відхилення.** Відхилений multipart-запит не створює нового файла й не замінює старий; наступне допустиме завантаження працює. Для кількох файлів у **одному** запиті перевірити відсутність часткового збереження після помилки парсингу multipart.

### P1 — UI та регресія

7. **Наявні обмеження форм.** Перевірити повідомлення й блокування вибору файлів понад локальні межі 5, 10 і 25 МБ у відповідних формах. Не очікувати від цих форм пропуску файла до серверного ліміту 50MB.
8. **Відображення серверної помилки.** На UI-сценарії, який досягає backend-ліміту, перевірити, що користувач бачить «Розмір файлу перевищує допустимий 50MB.» без хибного успіху. Проєктне виробництво бере текст із `errors[].messages[]` через `getApiErrorMessage`.
9. **Повторна спроба й інші помилки.** Після помилки розміру допустимий файл завантажується. Помилки формату, прав доступу й мережі не відображаються як перевищення розміру.
10. **Кілька файлів у UI.** У режимі редагування проєктного виробництва файли надсилаються **окремими послідовними запитами**. Якщо пізніший файл відхилено, попередні успішні завантаження можуть лишитися збереженими; це не порушення атомарності одного multipart-запиту. Перевірити відображення фактичного списку файлів після такої помилки.

## Критерії приймання за поточною реалізацією

- Ефективні `max-file-size` і `max-request-size` беруть значення з `MULTIPART_MAX_SIZE`, за замовчуванням `50MB`.
- Допустимий multipart-запит проходить; на dev запит понад серверний ліміт повертає HTTP 400 та `errors[0].messages[0] = "Розмір файлу перевищує допустимий 50MB."`.
- Після відхиленого запиту збережений стан відповідає фактично виконаним запитам; допустиме повторне завантаження працює.
- Окремі UI-ліміти 5/10/25 МБ і їхні повідомлення перевіряються як чинна поведінка форм.
