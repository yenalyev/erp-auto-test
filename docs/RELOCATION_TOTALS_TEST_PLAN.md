# Тест-план: «Всього» у «Логістиці» та «Видати/Отримати»

Дата аналізу: 14.10.2026. Обсяг: `/logistics` і `/relocations` (вкладки «В дорозі», «Історія переміщень» / «Отримано», «Видано», «Втрачено»). Еталон інтерфейсу — підсумки за одиницями виміру на `/inventory` («Залишки»).

## Критерій приймання

Для **всіх** переміщень, що відповідають поточним фільтрам і вкладці, показати «Всього:» з окремою сумою кількості ресурсів для кожної одиниці виміру. Різні одиниці не складати. Підсумок охоплює всі сторінки результату, а не лише видимі рядки. Обладнання рахувати окремо як кількість одиниць. Після зміни фільтра, вкладки або даних підсумок оновлюється синхронно з поточною вибіркою; за відсутності збігів старі числа не лишаються як актуальні.

## Тестові дані

- Дві локації відправлення `A`, `B`, два отримувачі `C`, `D`; щонайменше два ресурси в `шт`, один у `кг` і один об'єкт обладнання. У кожного запису унікальний маркер.
- На вкладці «В дорозі»: `A→C` має `2 шт + 1,25 кг`, `A→D` має `3 шт`, `B→C` має `4 шт + 0,75 кг`; один запис `CANCELLED`. Повна очікувана сума для трьох `CREATED` без скасованого: `9 шт`, `2 кг`; після `A` — `5 шт`, `1,25 кг`; після `A` та `C` — `2 шт`, `1,25 кг`. Скасований запис врахувати окремо за його кількістю, бо вкладка включає `CANCELLED`.
- Історичні записи в `FINISHED`, `AUTO_FINISHED`, `RETURNED` із відомими різними кількостями; `LOST` з частковим списанням і окремим несписаним залишком. Потрібні записи на межах періоду та понад один розмір сторінки.
- Дані створювати через фікстури з унікальними ID/маркерами й очищувати після прогону. На спільному dev для точного арифметичного асерту застосувати ізолюючі фільтри; не покладатися на глобальну кількість записів.

## Сценарії

1. **P0, TOT-01 — Рендеринг і групування.** Відкрити обидві сторінки. Є «Всього:» й окремі чипи `шт`, `кг`; числа дорівнюють сумі ресурсних позицій того самого фільтрованого набору. Рядок із двома позиціями додає обидві; однакові одиниці агрегуються, різні не змішуються. Значення з дробовою частиною форматуються без помилки округлення понад заявлені 2 знаки UI.
2. **P0, TOT-02 — Вкладки і статуси.** У «Логістиці» «В дорозі» використовує `CREATED,CANCELLED`, «Історія переміщень» — `RETURNED,FINISHED,AUTO_FINISHED`. На `/relocations` перевірити «В дорозі», «Отримано», «Видано» та «Втрачено». Підсумок не захоплює статуси сусідньої вкладки. Для `LOST` рахувати лише фактично списану кількість, не початковий обсяг переміщення.
3. **P0, TOT-03 — Усі фільтри.** По черзі та в комбінації застосувати відправника, отримувача, пошук за назвою, ресурс/категорію, модель обладнання, період, статус історії. Порівняти параметри `GET /api/v1/relocations/totals` і запиту таблиці: `states`, `senderIds`, `receiverIds`, `isOr`, `fromIds`, `toIds`, `productIds`, `productName`, `category`, `equipmentModelIds`, `type`, `startDate`, `endDate`. Для пошуку за ресурсом у переміщенні з кількома позиціями сумувати лише відповідні позиції, хоча весь запис може залишатися в таблиці.
4. **P0, TOT-04 — Область доступу.** Адміністратор/логіст бачить глобальний підсумок за своїми фільтрами. Користувач з обмеженою локацією на «Видано» підсумовує лише дозволених відправників, на «Отримано» — дозволених отримувачів; зміна вибраної локації змінює суму. Користувач без права читання не отримує дані `/totals` (`401/403`), зокрема при запиті чужого `senderIds`/`receiverIds`.
5. **P1, TOT-05 — Пагінація та сортування.** При зміні розміру сторінки, переході на іншу сторінку й сортуванні сума не змінюється. Вона охоплює весь фільтрований набір, а не поточну сторінку.
6. **P1, TOT-06 — Порожній результат і помилка.** Фільтр без збігів показує порожню таблицю й не показує попередню суму. При помилці `/totals` старий підсумок прибирається, тоді як таблиця може завантажитися окремо. Повторне застосування фільтра або оновлення сторінки відновлює коректний підсумок.
7. **P1, TOT-07 — Оновлення даних.** Після створення/завершення/скасування/видалення переміщення відповідні вкладки та їхні суми перераховуються без ручного перезавантаження. На швидкі послідовні зміни фільтрів запізніла відповідь попереднього запиту не перезаписує нову суму.
8. **P1, TOT-08 — Обладнання та одиниця відсутня.** Окремий показник «Обладнання» дорівнює кількості об'єктів, не кількості переміщень. Ресурси без одиниці мають окрему групу. Порожні групи/нульове обладнання не створюють хибних чипів.
9. **P2, TOT-09 — Вигляд.** Підсумок видно над таблицею при вузькому екрані; понад чотири одиниці доступні через `+N`. Підпис і числа читаються клавіатурою та допоміжними технологіями; локальне форматування чисел відповідає українській локалі.

## Спосіб перевірки і поточне покриття

- UI-контракт: `LogisticsJournalUiTest` із контрольованими відповідями `/relocations` і `/relocations/totals` перевіряє вкладки, фільтр відправника, параметри запиту і показ окремих одиниць на обох сторінках (`TC-LOG-UI-012/013`). Це перевіряє інтеграцію UI, але не арифметику сервера.
- API-арифметика: `RelocationTotalsApiTest` (`TC-REL-TOTAL-API-001/002/003`) створює ізольовані ресурси з двома одиницями, отримання та видачі; перевіряє точні суми, фільтри ресурсу й назви, пагінацію та право глобального читання. Тест зареєстрований у `relocations.xml` і `regression.xml`. Окреме покриття обладнання та `LOST` лишається пунктом плану. У коді backend `RelocationControllerIT.testGetTotals_sumsMatchingItemsByUnitAndCountsEquipment`, `testGetTotals_lostRelocationCountsOnlyWrittenOffAmount` і `testGetTotals_requiresReadAccessToRequestedStorages` уже описують частину контракту, але сам цей огляд не є їхнім виконанням.
- Наскрізний dev-прогін має окремо підтвердити, що розгорнуті frontend і backend відповідають поточному коду. Зафіксувати URL, середовище, час, ID даних, фактичні суми та Allure-скриншоти.

### Динамічний логіст для API перевірки доступу

`business-roles.yml` визначає бізнес роль `LOGIST` через наявну глобальну системну роль **«Логістика: загальний перегляд»**. `RelocationTotalsApiTest` створює окремого користувача `autotest-logist-<унікальний суфікс>`, задає пароль через штатний Playwright bootstrap і призначає цю системну роль із областю `ALL`. Фікстура перевіряє активний grant і ефективні дозволи ролі. Сесія тимчасово прив'язується до `UserRole.DYNAMIC_GLOBAL_ACTOR`; облікові дані налаштованого `UserRole.LOGIST` у новому API тесті не використовуються. Після класу фікстура відновлює прив'язку слота, відкликає grant і деактивує створеного користувача.

## Виявлені ризики під час аналізу коду

- `RelocationTotals` зберігає попереднє значення до завершення нового запиту. Під час завантаження після зміни фільтра користувач може тимчасово бачити суму старої вибірки. TOT-06/07 має перевірити, чи це прийнятно за UX-вимогою.
- UI форматує підсумок максимум до двох дробових знаків. Якщо одиниця допускає точність понад 2 знаки, потрібно погодити правило відображення й асерту.
- `/inventory` має також показник «Позицій»; поточний компонент для переміщень показує лише суми за одиницями й обладнання. Вимога згадує суму, тому кількість позицій не включено до критерію приймання без окремого уточнення.
