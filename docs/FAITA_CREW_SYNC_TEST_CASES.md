# Тест кейси — синхронізація екіпажів Файти й списання

## Передумови

Окремий dev набір source даних з унікальними `team_id`, `team_code`, flight event і ресурсами; доступ до `imp` / `crew` / stock для перевірки; дозвіл запускати `syncTeams`. Після кожного сценарію прибирати лише власні source рядки й артефакти. Фіксувати ID, статус і залишки до/після, а не визначати успіх лише за HTTP 200.

## Екіпажі й storage

### TC-FAITA-SYNC-001 — новий екіпаж [P0]

Дано активний source team з новим `team_id`. Запустити sync двічі. Очікувати один `crew.team`, один CREW storage, правильний зв'язок, ім'я, підрозділ, `active=true`; ID незмінні після другого запуску.

### TC-FAITA-SYNC-002 — перейменування [P0]

Дано вже синхронізований `team_id`. Змінити `team_name`, запустити sync. Очікувати нове ім'я team/storage за незмінних ID, запасів і доступів.

### TC-FAITA-SYNC-003 — деактивація й повторна активація [P0]

Змінити source статус `ACTIVE → INACTIVE → ACTIVE`, виконуючи sync після кожної зміни. Очікувати `storage.active=true → false → true` без нового storage; team status збігається з source.

### TC-FAITA-SYNC-004 — різні ID з однаковим ім'ям [P0]

Створити два source teams з однаковою назвою й різними `team_id`. Очікувати два окремі team/storage. Це перевіряє пріоритет ID над поточним reconcile за назвою.

## watch_schedule

### TC-FAITA-SYNC-005 — точка за team_code [P0]

Дано активний team і актуальний schedule з його `team_code`. Після sync точка є під правильним підрозділом, а CREW — під точкою. Чужий `team_code` не впливає.

### TC-FAITA-SYNC-006 — запису немає або його видалено [P0]

Перевірити новий екіпаж без schedule, потім екіпаж із точкою після видалення schedule. Очікувати CREW під підрозділом без точки та очищені посилання на стару точку.

### TC-FAITA-SYNC-007 — графік змінено [P1]

Перенести schedule з точки А до Б, запустити sync двічі. Очікувати parent Б, одну міграцію залишків і жодного дублювання. Старі списання зберігають історичну позицію.

## Списання

### TC-FAITA-SYNC-008 — чотири гілки маршруту [P0]

Окремо створити Fight event для: (а) точка + достатній stock точки; (б) точка + stock 0, навіть якщо є stock екіпажа; (в) без точки + stock екіпажа; (г) без точки + stock 0. Очікування: (а) debit лише точки й terminal auto status; (б) `PENDING`, без fallback/debit; (в) debit лише екіпажа й terminal auto status; (г) `PENDING`, без debit.

### TC-FAITA-SYNC-009 — недостатній залишок [P0]

Для amount `N` дати stock `N-1` на цільовому storage. Очікувати `PENDING`, незмінні залишки й відсутність часткового руху.

### TC-FAITA-SYNC-010 — повторний імпорт [P0]

Повторити sync для того самого source event, зокрема на межі watermark. Очікувати один flight log, один набір write-off, одноразовий debit та один `sourceId` у всіх записах події.

## Позиція з ЖБД

### TC-FAITA-SYNC-POS-001 — окремий snapshot [P0]

У `ammo_agg_v2.position_name` задати «Позиція А», а поточну точку екіпажа назвати інакше. Після імпорту перевірити точний текст у БД, `positionName` у GET, колонці «Позиція з ЖБД» у UI та окремий фактичний `flyPointStorage`.

### TC-FAITA-SYNC-POS-002 — точку не знайдено [P0]

Source event має позицію, якої немає серед storage. Очікувати збереження сирого тексту в списанні навіть за `flyPointStorage=null`; route/status визначати за поточною прив'язкою екіпажа.

### TC-FAITA-SYNC-POS-003 — NULL і старі рядки [P0]

Імпортувати event з `position_name=NULL` та відкрити рядок до міграції. Очікувати ключ `positionName` зі значенням `null` у API та `—` у UI; списання не губиться.

### TC-FAITA-SYNC-POS-004 — кілька ресурсів [P0]

Event містить основний ресурс, ініціатор і два implicit. Очікувати однакові `sourceId` та `positionName` в усіх write-off, правильні amount; повторний sync не множить записи.

### TC-FAITA-SYNC-POS-005 — історичність [P1]

Після імпорту змінити schedule й назву точки. Очікувати незмінне `positionName` старого списання в БД/API/UI після refresh.

### TC-FAITA-SYNC-POS-006 — текст і довжина [P1]

Перевірити кирилицю, пробіли і максимальну погоджену довжину; жодного мовчазного обрізання. Експорт, якщо він є, повертає той самий текст.

## Автоматизація та критерій завершення

`TC-FAITA-SYNC-POS-API-001` перевіряє ключ і тип у живих FLIGHT write-off; `TC-FAITA-SYNC-POS-UI-001` перевіряє колонку. Це контрактні проби нового поля. Окремий `TC-FAITA-SYNC-POS-E2E-001` через dev `/log` і `/syncTeams` перевіряє перенесення сирої позиції, `PENDING`, `sourceId` та ідемпотентність. Він вимагає явного opt-in, БД й схвалення загального sync на спільному dev; цей endpoint сіє flight log безпосередньо, тому `imp.ammo_agg_v2 → log` він не покриває. Решта кейсів `001–010` і `POS-001–006` потребують керованого source fixture, stock setup і cleanup. Release gate: усі P0 зелені, stock delta та ідемпотентність доведені на dev, а невизначені статуси й назва поля погоджені.

Прогін `TC-FAITA-SYNC-POS-E2E-001` 2026-10-01 зупинився на HTTP 500 від `syncTeams`; після нього `TC-FAITA-SYNC-CLEANUP-002` видалив один власний `NEW` flight log, а `TC-FAITA-SYNC-CLEANUP-001` підтвердив нуль тестових log/write-off. До діагностики 500 результат E2E не можна трактувати як перевірку поля або маршруту списання.
