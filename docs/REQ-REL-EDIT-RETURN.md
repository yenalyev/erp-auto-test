# Повернення до журналу переміщень зі збереженими фільтрами

Після успішного редагування переміщення зі сторінки «Видано» або «Отримано» користувач повертається на ту саму вкладку з фільтрами, які діяли під час відкриття форми. Збереження примітки чи дати не повинно змушувати користувача повторно налаштовувати вибірку.

TCM: `REQ-WMS-006` → `REQ-REL-EDIT-RETURN`. Перевіряються зовнішні завершені переміщення `AUTO_FINISHED`, для яких доступна кнопка редагування. Передумова: користувач має право редагувати переміщення обраної локації. Автоматизація виконує сценарії як ADMIN на власних тестових локаціях; матриця інших ролей належить наявним RBAC-тестам.

## Критерії приймання

- **AC-01:** Після успішного PUT із форми редагування відкривається вихідна вкладка «Видано» або «Отримано». Зміни переміщення збережені на сервері.
- **AC-02:** Відновлюються значення фільтрів ресурсів: «Від кого», «Кому», «Дата відправки», «Категорія», «Виріб», «Постачальник» та «Статус», включно з множинним вибором виробів. Видимі значення, параметри нового запиту журналу та вибірка узгоджені.
- **AC-03:** Очищені й необрані фільтри залишаються порожніми. Після повторного відкриття форми використовується актуальний знімок фільтрів, а не стан першого редагування.
- **AC-04:** Якщо під час редагування дата переміщення змінена на дату поза активним інтервалом, інтервал зберігається, а запис зникає з вибірки. Саме переміщення існує й містить нову дату.
- **AC-05:** Для обладнання після редагування зберігаються режим «Обладнання», обрана модель і фільтр локації. Параметри ресурсів не повинні з'являтися в запиті обладнання.
- **AC-06:** Після повернення таблиця та справжній Excel використовують відновлені фільтри. Таблиця містить точні очікувані ID, включно з відсутністю записів, що не відповідають вибірці.

Збереження номера сторінки, сортування, сценарії скасування та перезавантаження самої форми не включено до цієї вимоги. Тести працюють через реальний UI та API без підміни відповідей, router state або тіла PUT.

## Автоматизовані тест кейси

Кожен кейс виконується двічі: із «Видано» та із «Отримано». Перед збереженням фіксуються запит Excel, значення видимих полів і точна серверна вибірка. Після збереження перевіряються вкладка, поля, фактичний GET журналу та незалежний GET збереженого переміщення. Повторне завантаження Excel додатково перевіряє параметри активних фільтрів.

### TC-REL-RETURN-UI-001 — Поєднані фільтри ресурсів [AC-02]

Автотест: `RelocationEditReturnFiltersUiTest#combinedResourceFiltersSurviveSave`.

1. Відкрити вихідну вкладку. Обрати власні локації відправника й отримувача та сьогоднішню дату.
2. Обрати категорію A, два вироби з цієї категорії, постачальника «МОУ» та статус «Завершено».
3. Відкрити редагування відповідного зовнішнього переміщення, змінити примітку й зберегти.
4. Перевірити серверне збереження, вихідну вкладку, усі видимі фільтри, точні параметри GET, ID вибірки та повторний Excel.

Очікування: Примітка збережена; обидва вироби, постачальник, категорія, локації, дати й статус залишилися активними; сторонні записи не з'явилися.

### TC-REL-RETURN-UI-002 — Один виріб [AC-01]

Автотест: `RelocationEditReturnFiltersUiTest#singleProductFilterSurvivesSave`.

1. Встановити локації, дату та один виріб; категорію й постачальника залишити необраними.
2. Змінити примітку через форму редагування та зберегти.
3. Перевірити вкладку, значення полів, query, точні ID та повторний Excel.

Очікування: Єдиний виріб і задана область залишаються активними, порожні категорія й постачальник не підставляються.

### TC-REL-RETURN-UI-003 — Очищена категорія [AC-06]

Автотест: `RelocationEditReturnFiltersUiTest#clearedOptionalFiltersStayCleared`.

1. Обрати локації й дату, встановити категорію A, після чого очистити категорію.
2. Відредагувати примітку та зберегти.
3. Перевірити видимі фільтри, відсутність category/productIds/suppliers у query та точну вибірку.

Очікування: Категорія не відновлюється зі старого стану; необрані вироби та постачальник залишаються порожніми.

### TC-REL-RETURN-UI-004 — Актуальний знімок при повторному редагуванні [AC-03]

Автотест: `RelocationEditReturnFiltersUiTest#reopeningEditorUsesLatestSnapshot`.

1. Встановити локації, сьогоднішню дату й категорію A; відредагувати примітку та перевірити повернення.
2. На поверненій сторінці очистити категорію, обрати один виріб та пресет «7 днів», який включає сьогоднішній і старий записи.
3. Відкрити редагування іншого відповідного переміщення, зберегти нову примітку та повторити перевірки.

Очікування: Друге повернення використовує новий інтервал і виріб та очищену категорію; перший знімок не підміняє актуальні фільтри. Таблиця містить обидва відповідні записи.

### TC-REL-RETURN-UI-005 — Запис виходить за межі дати [AC-04]

Автотест: `RelocationEditReturnFiltersUiTest#editedRecordOutsideDateFilterDisappears`.

1. Встановити власні локації та інтервал лише за сьогодні, відкрити відповідне переміщення.
2. У формі змінити дату на вчора й примітку, зберегти.
3. Незалежним GET підтвердити нову дату та примітку. Перевірити вихідну вкладку, сьогоднішній інтервал і відсутність ID у поверненій вибірці.
4. Після перевірки відновити дату власного запису через UI та підтвердити серверне значення.

Очікування: Сьогоднішній фільтр залишається активним; відредаговане переміщення з учорашньою датою відсутнє в таблиці й вибірці Excel.

### TC-REL-RETURN-UI-006 — Обладнання та модель [AC-05]

Автотест: `RelocationEditReturnFiltersUiTest#equipmentModeAndModelSurviveSave`.

1. Перемкнути тип на «Обладнання», обрати власну локацію з боку відповідної вкладки й тестову модель.
2. Відредагувати примітку зовнішньої видачі або отримання обладнання та зберегти.
3. Перевірити режим, модель, локацію, точні ID та query без ресурсних фільтрів; повторно завантажити Excel.

Очікування: Зберігаються вкладка, тип EQUIPMENT, модель та локація; вибірка не розширюється до всіх ресурсів чи іншого обладнання.

## Дані та очищення

`RelocationEditReturnFixture` створює власні внутрішні й зовнішню локації, категорії, ресурси з різними постачальниками, актуальні й старі зовнішні отримання/видачі, дві моделі та два незалежні екземпляри обладнання для отримання й видачі. Контрольні записи включають інші категорії, дати, одержувачів і стани.

Cleanup видаляє власні зовнішні ресурсні видачі перед отриманнями; власні залишки очищаються інвентаризацією з версіями. Обладнання переводиться у RETIRED з незалежною перевіркою статусу: історія відредагованої видачі може бути недоступною для видалення. Ресурси й локації архівуються, категорії видаляються. Залишається внутрішня історія FINISHED/RETURNED та історія обладнання із заархівованими локаціями й неактивними товарами. ID історії додаються в Allure. Помилки cleanup завершують прогін помилкою конфігурації.

## Запуск

```powershell
scripts/run_relocation_edit_return_dev.ps1
```

Або з Java 21:

```powershell
mvn test -Denv=dev -Dsuite=relocation-edit-return-filters -Duse.database=false -Dssh.enabled=false -Dframework.browser.channel=chrome
```

Набір: 6 автоматизованих UI-кейсів, 12 виконань. API використовується для підготовки й незалежної перевірки збереження та складу вибірки. Звіти містять скриншоти, Allure-вкладення з початковими/поверненими query та значеннями фільтрів. Дефекти повернення реєструються як FAIL; успішний PUT сам собою не означає успішний сценарій.
