# Вимога: списання вильоту з точки спотерів

## Правило

У рядку вильоту Файти `spotter_team_id` — впорядкований масив ID команд спотерів. Якщо він непорожній, для кожного ID визначити `crew.team.team_storage_id`, а для CREW під точкою — його батьківський `FLY_POINT`. Повний обсяг використаного ресурсу списати з першої в порядку масиву точки, де достатньо залишку. Якщо залишок є в обох точках, обрати першу. Кількість одного рядка вильоту не розподіляти між кількома точками.

Позиція вильоту (`position_name`/`fly_point_name`) є окремими даними події та не повинна змінювати пріоритет точки спотера. Якщо масив `NULL` або порожній, застосувати існуючий маршрут бойового екіпажу. Для ініціатора та додаткових ресурсів маршрут має застосовуватися окремо до кожного ресурсу за фактичним залишком, з тим самим порядком спотерів.

## Дані й перевірка

Ланцюг: `imp.ammo_agg_v2.spotter_team_id → crew.team_flight_log.spotter_team_id → storage_item_write_off.storage_id/alternative_storage_ids → фактична точка дебету`. Зберегти порядок ID під час SQL aggregation; вибір складу, stock delta, status, history і повторну обробку перевіряти за одним source event. [Тест-план](FAITA_SPOTTER_WRITE_OFF_TEST_PLAN.md) і [кейси](FAITA_SPOTTER_WRITE_OFF_TEST_CASES.md) описують матрицю.

## Питання до продуктового рішення

- Для невідомого `spotter_team_id` або спотера без storage потрібен явний контракт: відхилити/відкласти подію з діагностикою чи пропустити цей ID. Тихий fallback на бойовий екіпаж не відповідає правилу про списання зі спотерів.
- Для нульового або недостатнього залишку всіх точок узгодити, чи створювати запис списання та який статус показувати. Поточний прямий completion ставить `FAILED`; окремий [no-stock контракт](FLIGHT_WRITE_OFF_NO_STOCK_TEST_PLAN.md) описує відсутність запису при нульовому залишку на етапі імпорту.
