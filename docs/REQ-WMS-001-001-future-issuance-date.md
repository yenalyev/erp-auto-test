# REQ-WMS-001-001 — Заборона видачі майбутньою датою

Дочірня вимога `REQ-WMS-001` («Операція Видати»). Стан вимоги — `IN_PROGRESS`.

## Правило

При створенні видачі та при зміні її дати під час редагування дата не може бути пізніше поточної календарної дати за Києвом. Верхня межа однакова для бізнес-власника, комірника й адміністратора. Це стосується видачі ресурсів та обладнання, зокрема форм видачі на локацію, екіпаж і між точками вильоту.

Під час оформлення видачі власник складу обирає дату в календарі форми. Можна вказати сьогоднішню або минулу дату з урахуванням окремих правил для редагування вже створеної видачі. Правила колишньої фічі `REQ-WMS-001-01-01` зібрані тут.

Якщо користувач зазначив майбутню дату, система повідомляє про помилку дати. Невдала спроба не створює видачу і не змінює дату, вміст, стан чи залишки існуючої видачі. Це правило діє і під час роботи у формі, і при збереженні операції.

Це **верхня** межа. Вимога `REQ-EDIT_REL / AC-08` (CPMA-796) задає **нижню** межу для неадміністратора: дата не раніше вчорашньої. Адміністратор звільнений від нижньої межі, але не від верхньої.

Дата прийому під час «Прийняти» — окреме поле: її межі від дати «Надіслано» до сьогодні описані в [тест-плані дати отримання](RECEIVED_DATE_TEST_PLAN.md). Одноденне вікно для редагування видачі не забороняє приймати давнє переміщення.

## Критерії та автотести

| Критерій | Перевірка | Автотести |
|------------|-----------|------------------|
| AC-01 | Створення видачі завтрашньою датою відхилене для неадміністратора й адміністратора; правило окремо перевірене для комірника при `FP1 → FP2`; залишок незмінний | `TC-REL-DATE-010`, `011`, `022` |
| AC-02 | Зміна дати існуючої видачі на завтра відхилена для неадміністратора й адміністратора; правило окремо перевірене для комірника при `FP1 → FP2`; запис та залишок незмінні | `TC-REL-DATE-012`, `013`, `023` |
| AC-03 | Форми видачі дозволяють сьогоднішню дату за Києвом і блокують завтрашню | `TC-UI-REL-DATE-001` |
| AC-04 | Власник складу може оформити видачу минулою календарною датою | Потребує окремої перевірки |
| AC-05 | Дата видачі обирається в календарі форми | Наявний UI-сценарій відкриває поле дати; окремого кейсу для вибору немає |

Усі шість API-сценаріїв знаходяться в `RelocationOneDayLimitTest`. UI-сценарій `RelocationFutureDateUiTest` перевіряє три форми видачі на межі календарних днів.

## Стан реалізації на 15.09.2026

На `dev` серверна перевірка майбутньої дати працює для звичайних переміщень і для `FP1 → FP2`: запуск `RelocationOneDayLimitTest` 15.09.2026 пройшов `39/39`, включно з `TC-REL-DATE-010…013`, `022` і `023`. Відхилені API-запити повернули помилку поля `date`, а тести підтвердили незмінність записів і залишків.

## Виявлений розрив 12.10.2026

У розгорнутому dev UI о 00:30 за Києвом форма звичайної видачі показує верхню межу вчорашнім днем: `TC-UI-REL-DATE-001` отримав `max=2026-10-11` замість `2026-10-12`. Отже, користувач тимчасово не може вибрати поточну київську дату після опівночі. Тест зупинився на першій формі; фактичну поведінку двох інших форм у розгорнутому dev UI цей запуск не підтвердив. Поведінку prod ERP не перевіряли. Дефект передано як розбіжність між бізнес-правилом та поточною поведінкою; код фронтенду й бекенду не змінювався.

Запуск: `mvn test -Denv=dev -Dtest=RelocationOneDayLimitTest`.
