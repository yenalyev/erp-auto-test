# REQ-WMS-009 — Комплекти для видачі

Документація фічі для команди QA / продукту / автотестів.  
TCM feature: **REQ-WMS-009** (модуль WMS, parent `REQ-WMS`).  
SUT: backend `tk`, frontend `tk-ui`. Автотести: `erp-auto-test`.  
SSOT у репозиторії: цей файл.

Ticket: **CPMA-668**.

---

## 1. Огляд

**Комплект** — іменований набір ресурсів (виробів) на рівні **однієї локації**. Потрібен, щоб на формах видачі швидко додати потрібні рядки продукції без ручного вибору кожного ресурсу окремо.

Комплект:

- зберігає лише **перелік ресурсів** (id + назва у відповіді API);
- **не** зберігає кількість і партії;
- **не** є окремим типом переміщення;
- **не** потребує нових permissions і **не** має окремого пункту сайдбару.

Користувач після застосування комплекту сам вводить кількість і (за потреби) обирає партії, після чого підтверджує видачу як звичайне переміщення.

## 2. Область дії та обмеження

| Правило | Суть |
|---------|------|
| Ізоляція локацій | Комплекти локації A не видно і не керуються з локації B |
| Хто може керувати | Користувач з `business-unit-list::read` на цю локацію (окремого Owner-only permission немає) |
| Ліміт ресурсів | Немає обмеження на кількість ресурсів у комплекті |
| «Всі локації» | Вкладка менеджменту комплектів недоступна |
| Де apply працює | Форми **«Видача»** і **«Видача на екіпаж»** |
| Де apply не працює | Редагування видачі, форми отримання / повернення |

---

## 3. Менеджмент комплектів (CRUD)

**Точка входу:** розділ **«Видати/Отримати»** (`/relocations`) → вкладка **«Комплекти для видачі»** (лише при обраній конкретній локації з правом BU read).

| Дія | Поведінка |
|-----|-----------|
| Створити | Кнопка **«Новий Комплект»**: поле назви + вибір ресурсів (autocomplete серед доступних користувачу). Toast: «Комплект створено» |
| Редагувати | Іконка редагування: можна змінити **склад ресурсів**; **назву змінити не можна** (поле disabled). Toast: «Комплект оновлено» |
| Видалити | Підтвердження **«Видалити Комплект?»** → рядок зникає. Toast: «Комплект видалено» |
| Дублікат назви | UI блокує створення з назвою, що вже існує (порівняння **case-insensitive**) |
| Порожній список | Текст **«Комплектів не знайдено»** |
| Upsert (API) | Повторне збереження з тим самим `bundleName` **замінює** перелік ресурсів |

Окремої дії «лише перегляд» немає — перелік ресурсів видно в таблиці вкладки та в hover на формі видачі.

## 4. Застосування комплекту на формі видачі (apply)

**Точки входу:**

- **«Видача»** — `/relocation/create-output`
- **«Видача на екіпаж»** — `/relocation/create-output-crew`

На формі комплекти локації-відправника показуються як **зелені badges** над блоком «Список продукції». Hover по badge показує склад комплекту (назви ресурсів).

```mermaid
flowchart TD
  badges[Badges комплектів на формі] --> click[Клік по комплекту]
  click --> filter["Лише ресурси зі stock > 0 і ще не в рядках"]
  filter -->|є що додати| rows["Нові рядки: ресурс заданий, кількість порожня, партії не обрані"]
  filter -->|усі вже є| toastAlready["Toast: Усі ресурси з цього комплекту вже додано"]
  filter -->|немає на складі| toastStock["Toast: Немає доступних ресурсів з цього комплекту на цьому складі"]
```

### Бізнес-правила apply

1. **Кількість** не заповнюється автоматично (поле порожнє).
2. **Партії** не обираються автоматично.
3. Додаються лише ресурси зі **залишком > 0** на складі-відправнику.
4. Ресурси, **уже присутні** у рядках форми, пропускаються (дозволяються лише відсутні — частковий merge).
5. Якщо додавати нічого (усі вже є або жоден без залишку) — показується відповідний toast; форма не змінюється.
6. Після apply користувач вручну вводить кількість / партії і підтверджує видачу стандартним сценарієм relocation.

Apply виконується **лише на UI** (окремого API «застосувати комплект → створити relocation» немає).

## 5. Користувацькі сценарії

1. **Налаштування.** Користувач з доступом до локації відкриває «Видати/Отримати» → «Комплекти для видачі» → створює / редагує / видаляє комплекти для цієї локації.
2. **Видача за комплектом.** На формі «Видача» або «Видача на екіпаж» бачить badges → за потреби hover (склад) → клік → з’являються рядки з порожньою кількістю → заповнює кількість і партії → «Підтвердити».

## 6. Технічний контракт (API)

| Метод | Path | Permission |
|-------|------|------------|
| GET | `/api/v1/resources/user-bundles?storageId=` | `business-unit-list::read` на `storageId` |
| POST | `/api/v1/resources/user-bundles` | те саме (створення / upsert) |
| DELETE | `/api/v1/resources/user-bundles` | те саме |

- Тіло запиту save/delete: параметри `storageId`, `bundleName`, для save — `resources` (список id).
- Відповідь GET: `{ bundleName, resources: [{ id, name }] }` — без кількості/партій.
- Зберігання: `app_config`, name=`resource_bundles`, ключ локації = `storageId`.
- GET відфільтровує ресурси через видимість користувача на локації (`findGrantedResources`): недоступні id можуть лишатися в збереженому config, але **не** повертаються в `resources[]`.

Endpoints у erp-auto-test: `RESOURCE_USER_BUNDLES_GET` / `POST` / `DELETE`. Fixture: `ResourceBundleFixture`.

## 7. Acceptance Criteria (TCM)

| AC | Суть |
|----|------|
| AC-01 | CRUD API: create / upsert / delete / GET; лише resource ids |
| AC-02 | Ізоляція по `storageId` + 403 без BU read |
| AC-03 | Без нових permissions і без пункту сайдбару |
| AC-04 | UI вкладка «Комплекти для видачі» на `/relocations` (CRUD, empty state, «Всі локації») |
| AC-05 | Apply на формах видачі / видачі на екіпаж (qty/batches/stock/toasts) |
| AC-06 | GET ховає ресурси без grant на локації |

## 10. Нотатки UX

Початковий wireframe описував «шаблони» з попапом «Обрати шаблон» і лінком «Створити шаблон» з форми (Owner-only). У реалізації: термін **«комплект»**, apply через **badges**, CRUD лише з вкладки журналу, доступ через існуючий `business-unit-list::read`, назва на edit незмінна. Бізнес-сутність (набір ресурсів локації → рядки видачі без авто-qty/партій) збережена.
