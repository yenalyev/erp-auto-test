# REQ-REGION — Регіони видимості

Документація фічі для продукту, QA та автотестів.  
TCM feature: **REQ-REGION** «Області видимості» (модуль REGION) — **повна documentation у TCM**.  
Дочірні: **REQ-REGION-001** (локації), **REQ-REGION-002** (ресурси).  
Дзеркало в репо: `docs/REQ-REGION.md`.  
SUT: backend `tk`, frontend `tk-ui`. Автотести: `erp-auto-test` (сьют `storage-regions` / `visibility-isolated`).

Канонічне слово в цьому документі — **регіон**. «Область видимості» в TCM — та сама сутність.

Суміжні фічі (тут лише посилання):

| Feature | Зв’язок |
|---------|---------|
| `REQ-CREW-002`, `REQ-CREW-003` | Регіон типу «Екіпажі» та видача/повернення CREW/FLY — не дублювати тут |
| `REQ-WMS-*` | Журнал видачі / накладні; видимість впливає на селектор «Кому відправляю» |

---

## 1. Навіщо фіча бізнесу

Не кожен підрозділ має бачити всю організацію й усю номенклатуру.

- Підрозділ у режимі **«Всі локації»** працює широко: у селекторах відкрита організаційна структура.
- Підрозділ у режимі **«Регіони»** за замовчуванням бачить **лише себе**. Щоб видавати назовні або бачити чужу номенклатуру, адміністратор відкриває йому **регіони** — іменовані набори дозволених контрагентів і/або ресурсів.

Мета: need-to-know між підрозділами в одній системі, без окремих інстансів.

## 2. Словник

| Канон | Що бачить користувач на екрані | Технічний код |
|-------|--------------------------------|---------------|
| **Підрозділ** | локація типу підрозділ | `UNIT` |
| **Режим підрозділу «Всі локації»** | радіо / бейдж «Всі Локації» | `accessMode=FULL_ACCESS` |
| **Режим підрозділу «Регіони»** | радіо / бейдж «Регіони» | `accessMode=REGIONS` |
| **Регіон** | картка «Новий регіон», список регіонів | `StorageRegion` |
| **Режим доступу регіону** | «Повний доступ», «Регіони», «Ресурси», «Екіпажи» | `FULL_ACCESS` / `REGIONS` / `RESOURCES` / `CREWS` |
| **Локація-одержувач** | поле «Локація-одержувач» | `recipientStorage` — якір регіону |
| **Учасник регіону** | підрозділ, якому регіон відкрито | member |
| **Склад регіону (локації)** | локації всередині регіону | region locations |
| **Склад регіону (ресурси)** | дозволена номенклатура | region resources |
| **Адресний доступ** | видимість однієї локації без регіону | explicit grant |
| **Селектор локацій** | «Кому відправляю», шапка, фільтри журналу | `GET /storages/names` |
| **Селектор ресурсів** | список продукції, autocomplete | `GET /resources/autocomplete?storageId=` |
| **Видача** | «Видати» / send | `POST /relocations/send` |

Не плутати два різні «Регіони»:

1. **Режим підрозділу «Регіони»** — підрозділ обмежений, поки йому не відкриють регіони.
2. **Режим доступу регіону «Регіони»** — у селекторі учасник бачить **назву регіону** (аліас), а не внутрішні склади партнерів.

## 3. Два рівні налаштування

### 3.1. Рівень підрозділу

Адміністратор на картці підрозділу обирає режим видимості:

| Режим | Бізнес-зміст |
|-------|----------------|
| **Всі локації** | Широка видимість структури в селекторах локацій. |
| **Регіони** | За замовчуванням видно лише власний підрозділ. Усе інше — лише через регіони або адресний доступ. |

Це відповідь на питання «наскільки відкритий цей підрозділ», а не список конкретних партнерів.

### 3.2. Рівень регіону

Адміністратор створює іменований регіон (наприклад, «Регіон Захід»), задає **режим доступу**, за потреби **локацію-одержувача**, додає **учасників** і **склад** (локації або ресурси — залежить від режиму).

Учасник у режимі «Регіони» бачить **об’єднання** усіх відкритих йому регіонів **без дублів** однієї локації чи одного ресурсу.

---

## 4. Регіони локацій (`REQ-REGION-001`)

Стосується селекторів контрагентів видачі та споріднених списків локацій.

### 4.1. Підрозділ «Регіони» без відкритих регіонів

- У селекторі локацій — лише власний підрозділ.
- Чужих локацій у списку немає.

### 4.2. Регіон доступу «Регіони»

- У «Кому відправляю» з’являється **назва регіону**, не внутрішні назви складів партнерів.
- Видача на цей аліас фактично йде на **локацію-одержувача** регіону.

### 4.3. Регіон доступу «Повний доступ»

- У селекторі видно **реальні назви** локацій зі складу регіону.
- Якщо на картці локації задано власний аліас — у списку показується аліас локації, не назва регіону.

### 4.4. Адресний доступ

- Окремій локації можна відкрити видимість учаснику **без** регіону.
- У селекторі вона з’являється під **своїм ім’ям**.
- Після відкликання доступу локація знову зникає зі списку.

---

## 5. Регіони ресурсів (`REQ-REGION-002`)

Стосується номенклатури, яку підрозділ бачить і може проводити в операціях.

### 5.1. Підрозділ «Регіони» без регіону ресурсів

- Селектор ресурсів порожній: немає дозволеної номенклатури.

### 5.2. Регіон доступу «Ресурси»

- Учасник бачить **лише** позиції зі складу регіону (і об’єднання кількох таких регіонів).
- Позиція поза регіоном не з’являється в autocomplete / списку продукції.

### 5.3. Системний регіон «усі ресурси»

Існує службовий регіон «Системний регіон - ВСІ РЕСУРСИ» (технічний ресурс «Всі ресурси»).  
Учасник цього регіону бачить усю **реальну** номенклатуру; технічний рядок у словнику користувачу не показується. Без участі або після її відкликання доступу до «всього» немає.

### 5.4. Наслідування CREW / FLY_POINT

Екіпаж і точка вильоту наслідують регіон ресурсів **першого предка**, який не є екіпажем і не є точкою (зазвичай підрозділ). Деталі операцій CREW — у `REQ-CREW-*`.

### 5.5. Auto-grant після отримання

Після внутрішнього отримання на підрозділ «Регіони» ресурсу, якого не було в регіоні, система може **сама додати** його у видимість. Це продуктове правило «отримали — маємо право обліковувати»; не плутати з правом **видавати** ресурс, якого немає в селекторі.

## 6. Видача поза списком — вимога і поточний розрив

**Вимога.** Користувач підрозділу «Регіони» не може видати:

- на локацію (або аліас), якої немає в його селекторі локацій;
- ресурс, якого немає в його селекторі ресурсів;
- на локацію, з якої зняли адресний доступ.

Очікувана реакція системи — **відмова** (користувач бачить, що так зробити не можна; залишок відправника не змінюється).

**Поточний стан (відомий розрив).**

| Канал | Поведінка |
|-------|-----------|
| Інтерфейс (селектори) | Список уже вузький: outsider і «схований» ресурс не пропонуються. |
| Пряма видача через API | `POST /relocations/send` **приймає** отримувача або ресурс поза списком (успіх замість відмови). |

Це **не** прийнята норма «захист лише в UI». Це розрив відносно вимоги: API ще не перевіряє регіон так само, як селектор. Автотести (`TC-REL-VIS-002`, `TC-REL-VIS-008`, `TC-REL-VIS-011`, суміжний `TC-STR-RES-008` на інвентаризацію) залишаються червоними, доки бекенд не відмовить.

Прийом (`resolve`) з чужим `storageId` уже відхиляється — тобто частина write-path захищена, видача — ні.

## 7. Хто що налаштовує

| Роль | Що робить |
|------|-----------|
| Адміністратор | Режим підрозділу; CRUD регіонів; склад і учасники; адресний доступ. Owner регіонами не керує. |
| Користувач підрозділу «Всі локації» | Працює з широкими селекторами. |
| Користувач підрозділу «Регіони» | Бачить лише відкрите йому; видає в межах списку. |
