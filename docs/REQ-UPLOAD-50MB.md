# Завантаження файлів: ліміт 50MB

## Підтверджена поведінка

Backend задає `spring.servlet.multipart.max-file-size` і `max-request-size` через `${MULTIPART_MAX_SIZE:50MB}`. Без перевизначення обидва ліміти дорівнюють 50MB (52 428 800 байт). Ліміт стосується як окремої файлової частини, так і всього multipart-запиту з його службовими даними. Рівно 50MB корисного вмісту файла не гарантує успіху, бо повний запит більший.

На розгорнутому dev 26.09.2026 перевищення повернуло HTTP 400 з `errors[0].field = null` і `errors[0].messages[0] = "Розмір файлу перевищує допустимий 50MB."`. Це фактичний текст для автоматизованих перевірок. Локальний checkout backend `tk` містить старіший текст без `50MB`; початкова фраза «Перевищено максимальний розмір <size> на завантажень» не відповідає перевіреній відповіді dev.

Форма фото ресурсу має власний UI-ліміт 5 МБ і приймає одне фото. Тому серверну помилку 50MB для фото перевіряє прямий API-запит. Десять файлів по 5 МіБ в одному запиті надсилаються через `POST /api/v1/project-production` у масиві `files`: загальний multipart-запит перевищує 50MB. Це не сценарій форми фото ресурсу.

## Основні автоматизовані сценарії

1. `TC-UPLOAD-50-01`: малий PDF завантажується до проєктного виробництва та вивантажується з ідентичним вмістом.
2. `TC-UPLOAD-50-02`: PDF 51 МіБ відхиляється з HTTP 400 і точним текстом помилки; вкладення не змінюються.
3. `TC-UPLOAD-50-03`: UI редагування проєктного виробництва показує текст серверної помилки після завантаження PDF 51 МіБ і не показує хибного успіху.
4. `TC-UPLOAD-50-04`: невелике PNG-фото ресурсу завантажується, `imagePath` заповнюється, фото доступне через GET.
5. `TC-UPLOAD-50-05`: PNG 51 МіБ для фото ресурсу відхиляється з HTTP 400 і точним текстом помилки; фото не зберігається.
6. `TC-UPLOAD-50-06`: один multipart-запит із десятьма PNG по 5 МіБ кожен відхиляється з HTTP 400 і точним текстом помилки через сумарний розмір.

Детальні кроки: `docs/FILE_UPLOAD_50MB_TEST_CASES.md`. Автотести: `src/test/resources/suites/file-upload-50mb.xml`. На dev 26.09.2026 цей набір пройшов 6/6; виконання на production ERP цим не підтверджено.
