# Архівація моделі обладнання

Модель, яку більше не використовують, можна перемістити в архів, зберігши історію обладнання. Архів відокремлений у довіднику та не пропонується під час додавання обладнання.

## Критерії приймання
- **AC-01:** У довіднику моделей обладнання доступна архівація активної моделі без несписаних одиниць. Потрібне підтвердження; скасування не змінює дані. Архівна модель зберігає історію та не має повторної дії архівації.
- **AC-02:** Залишки несписаного обладнання та активне переміщення блокують архівацію. UI пояснює блокування, прямий API перевіряє актуальний стан; відмова не змінює модель, обладнання чи переміщення.
- **AC-03:** Архівовані моделі не відображаються в автокомпліті назви форми додавання обладнання; активні моделі залишаються доступними для пошуку та вибору.
- **AC-04:** Довідник має фільтр статусу: за замовчуванням активні; можна переглядати архівні й усі. Статус поєднується з назвою, категоріями та пагінацією без дублів і сторонніх записів.

## Контракт і тестові дані

Довідник: `/equipment-models`; форма: `/equipment/create`. API: `GET /api/v1/equipment/models` з `status=ACTIVE|ARCHIVED`, `modelName`, `categoryIds`, `page`, `size`; без status повертаються всі статуси. `PUT /api/v1/equipment/models/{id}/archive` повертає 204; при використанні чи повторній архівації — 400. `GET /api/v1/equipment/suggestions?name=...` виключає архів.

У поточному UI статуси підписані «Активна», «Архівна», «Всі статуси»; вимога «Активні» означає типовий вибір ACTIVE. Кількість рахує несписане обладнання, включно з одиницями в дорозі. RETIRED не блокує. Відновлення архівної моделі та нова матриця RBAC не входять у цю вимогу.

Fixture створює дві власні локації, категорію, моделі й одиниці з UUID. Cleanup завершує власні внутрішні видачі, списує обладнання, видаляє незалежні отримання, архівує моделі й деактивує власні локації. Завершені внутрішні переміщення, їхні отримання та категорія зберігаються як незмінна історія; усі моделі мають ARCHIVED та equipmentCount=0. БД не потрібна.

## Автоматизовані сценарії

### TC-EQA-API-001 Архівація списаної моделі зі збереженням історії

Критерій: AC-01. Метод: `archivesRetiredModelAndPreservesHistory`.

1. Створити модель з однією одиницею, списати її. Зберегти модель та історичну одиницю. Виконати PUT архівації.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: HTTP 204, статус ARCHIVED, equipmentCount=0; ID, назва, автор, дата, категорії й історична одиниця не змінені.

### TC-EQA-API-002 Залишки AVAILABLE та IN_REPAIR блокують архівацію

Критерій: AC-02. Метод: `nonRetiredStockBlocksArchive`.

1. Окремо створити модель з одиницею AVAILABLE та IN_REPAIR. Надіслати прямий PUT архівації для кожної.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: Обидва запити: HTTP 400 з поясненням використання моделі. Статус ACTIVE, equipmentCount=1; повні модель та одиниця незмінні.

### TC-EQA-API-003 Активне переміщення блокує архівацію

Критерій: AC-02. Метод: `activeRelocationBlocksArchive`.

1. Видати єдину одиницю на іншу власну локацію без підтвердження отримання. Перевірити IN_TRANSIT і виконати PUT архівації.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: HTTP 400 з поясненням використання; ACTIVE і equipmentCount=1. Модель, одиниця та активна видача збережені.

### TC-EQA-API-004 Зняття останнього блокера та повторна архівація

Критерій: AC-02. Метод: `clearingLastBlockerAllowsArchiveAndRepeatIsRejected`.

1. Спробувати архівувати модель AVAILABLE. Списати останню одиницю, архівувати та повторити PUT.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: До списання HTTP 400, після — 204 і ARCHIVED. Повторний PUT: 400 «Модель вже в архіві», модель незмінна.

### TC-EQA-API-005 Статус із назвою категорією та пагінацією

Критерій: AC-04. Метод: `filtersStatusWithNameCategoryAndPagination`.

1. Підготувати активну й архівну моделі однієї категорії. Запитати ACTIVE, ARCHIVED та без status; поєднати з назвою, категорією і size=1; перевірити page=1 та протилежний статус.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: Фільтри повертають точні ID та status, total=1; друга сторінка порожня. Без статусу обидві моделі; протилежний статус з точною назвою дає порожній результат.

### TC-EQA-API-006 Suggestions виключає архів із результатів пошуку

Критерій: AC-03. Метод: `suggestionsExcludeArchivedModels`.

1. Підготувати активний контроль і списану модель. Знайти обидві через suggestions, архівувати списану та повторити пошук за спільною й точною назвою.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: До архівації обидві моделі; після — лише активний контроль; точний пошук архівної моделі повертає [].

### TC-EQA-UI-001 Типовий фільтр показує активні моделі

Критерій: AC-04. Метод: `defaultsToActiveModels`.

1. Підготувати активну й архівну моделі. Відкрити /equipment-models і знайти їхній спільний фрагмент.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: Обрано активний статус, запити містять status=ACTIVE, рядок лише активної моделі. Поточний текст селектора — «Активна».

### TC-EQA-UI-002 Перемикання статусу та перетин фільтрів

Критерій: AC-04. Метод: `switchesStatusAndCombinesFilters`.

1. Знайти контрольні активну й архівну моделі, обрати категорію. Перемикати Архівна, Всі статуси й Активна; знайти архівну назву з активним статусом і повернутися.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: Кожен статус має точні рядки, архівна модель без кнопки архівації; фільтри назви й категорії зберігаються; несумісна комбінація порожня, повернення відновлює активну модель.

### TC-EQA-UI-003 Скасування архівації не змінює модель

Критерій: AC-01. Метод: `cancelsArchiveWithoutMutation`.

1. Відкрити архівацію списаної моделі. Перевірити назву в діалозі; натиснути «Скасувати».
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: Діалог закрито, PUT не відправлено, модель ACTIVE і лишається у списку.

### TC-EQA-UI-004 Підтвердження архівації та збереження після reload

Критерій: AC-01. Метод: `confirmsArchiveAndPersistsIt`.

1. Натиснути доступну кнопку архівації списаної моделі та підтвердити. Відкрити архівні, перезавантажити сторінку і знову знайти модель.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: Реальний PUT повертає 204, рядок зникає з активних; API ARCHIVED. Після reload модель є в архіві без повторної кнопки.

### TC-EQA-UI-005 Залишки та обладнання в дорозі блокують кнопку

Критерій: AC-02. Метод: `stockAndTransitDisableArchive`.

1. Створити модель із залишком і модель з одиницею в дорозі. Знайти обидві; перевірити кнопку, кількість та підказку.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: Для обох equipmentCount=1, кнопка disabled, підказка пояснює використання несписаним обладнанням; статус ACTIVE.

### TC-EQA-UI-006 Автокомпліт форми показує лише активну модель

Критерій: AC-03. Метод: `autocompleteExcludesArchivedModels`.

1. У формі нового обладнання ввести спільний фрагмент активної й архівної моделі. Обрати активну; потім ввести точну назву архівної.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: Реальний suggestions 200 і список містять лише активний контроль, його вибір заповнює назву. Для архівної назви API [] та кнопки вибору немає.

### TC-EQA-UI-007 Повторна валідація залишку під час підтвердження

Критерій: AC-02. Метод: `revalidatesStockAtConfirmation`.

1. Відкрити підтвердження архівації списаної моделі. Через API відновити одиницю в AVAILABLE. Підтвердити діалог і повторно відкрити довідник.
2. Звірити фактичний результат із даними API; у UI-кейсі перевірити видимі елементи й реальний мережевий запит.

Очікування: PUT 400; UI показує «Модель використовується обладнанням — архівація неможлива.». Модель ACTIVE; після оновлення рядок є, кнопка disabled.
