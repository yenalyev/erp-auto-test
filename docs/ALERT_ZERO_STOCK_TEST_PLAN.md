# Тест план: видимість нульового залишку зі сповіщенням

## Мета й підхід

Перевірити виняток для нульового залишку на сторінці «Залишки» та у hierarchy API, з якого вона отримує дані. Запускати на dev в ізольованій локації з унікальними ресурсами. Створити ресурс зі сповіщенням і залишком `0`, контрольний ресурс без сповіщення з підтвердженим `StorageItem.amount=0` і ресурс із додатним залишком для очікування завантаження таблиці. Після кожного сценарію очистити створену локацію стандартним cleanup fixture.

## Аудит наявних кейсів

- `TC-UI-ALERT-001` перевіряє бейдж «відсутній» для нульового ресурсу зі сповіщенням, але не фіксує стан тогла і не має нульового контролю без сповіщення.
- `TC-UI-ALERT-003` перевіряє сповіщення для п’яти типів локацій, але **вмикає** «Показувати нульові залишки» перед перевіркою.
- `TC-ALERT-002` перевіряє вагу/поріг нульового ресурсу в single-storage API, але не hierarchy `showZeroStock=false`.
- `TC-WMS-007-021` перевіряє, що нульовий ресурс **без** сповіщення прихований при вимкненому тоглі.

Отже, точного кейсу для поєднання `amount=0 + alert + toggle off` не було. Додано `TC-ALERT-006` та `TC-UI-ALERT-005`. Вони використовують чинні fixture/POM; старі кейси залишаються для суміжної регресії.

## Перевірки

1. API: `showZeroStock=false` — нульовий ресурс зі сповіщенням включений, нульовий без сповіщення виключений; `true` — обидва включені. Передумови підтверджені single-storage API (`amount=0`, наявність/відсутність `alertLimit`).
2. UI: вимкнути тогл, знайти унікальну групу ресурсів; перевірити видимість, `0` і статус «відсутній». Увімкнути тогл — перевірити обидва нулі. Вимкнути тогл, видалити сповіщення, оновити сторінку — перевірити зникнення ресурсу.
3. Ручна/подальша регресія: інші типи локацій, сповіщення лише в сусідній локації, фільтрація/пошук і пагінація, перехід `>0 → 0 → >0`, відсутність дубльованого рядка. `TC-UI-ALERT-003` уже охоплює типи локацій за увімкнених нулів.

## Критерій завершення

Обидва нові автотести проходять на dev; screenshot UI і TestNG/Surefire результати збережені. Якщо dev ще не містить зміни, падіння цих перевірок є дефектом продукту, а не підставою послаблювати очікування.
