# Тест-план: єдиний рецепт у межах партії

## 1. Мета

Перевірити, що після будь-якого успішного створення або редагування всі релевантні
записи про виробництво однієї партії використовують:

- одну техкарту;
- одну версію техкарти;
- однаковий вибір ресурсу в кожній групі альтернатив.

Це має гарантувати однозначну декомпозицію будь-якої одиниці ресурсу з партії.

## 2. Тестові дані

| Позначення | Стан партії |
|---|---|
| `EMPTY` | Немає записів про виробництво |
| `SINGLE` | Один запис: ТК-А v1; Зерно = Жито; Олія = Соняшникова |
| `UNIFORM-A` | Два або більше записів з рецептом `SINGLE` |
| `UNIFORM-B` | Один або більше записів: ТК-Б v1; інший набір альтернатив |
| `LEGACY` | Історичні записи з різними рецептами |

## 3. Основні тест-кейси

### TC-01 — Створення запису в непорожній партії

**Передумови:** `UNIFORM-A` уже містить записи про виробництво.

**Кроки:**

1. Відкрити форму створення запису.
2. Вказати номер партії `UNIFORM-A`.

**Очікуваний результат:**

- автоматично підставлено ТК-А v1;
- в усіх групах підставлено вибір альтернатив з еталонного запису партії;
- техкарта, версія й альтернативи недоступні для зміни;
- біля техкарти показано підказку:
  `Техкарту визначено партією UNIFORM-A, якщо треба використати іншу - вкажіть інший номер партії для цього запису`.

### TC-02 — Створення запису в порожній партії

**Передумови:** `EMPTY` не має записів про виробництво.

**Кроки:**

1. Відкрити форму створення запису.
2. Вказати номер партії `EMPTY`.

**Очікуваний результат:**

- техкарта, версія й альтернативи доступні для вибору;
- підказка про рецепт, визначений партією, не показується;
- користувач може зберегти довільний валідний рецепт як еталон партії.

### TC-03 — Зміна непорожньої партії на порожню

**Передумови:** у формі створення вибрана `UNIFORM-A`; рецептурні поля заблоковані.

**Кроки:** змінити номер партії на `EMPTY`.

**Очікуваний результат:**

- рецептурні поля розблоковано;
- підказка для `UNIFORM-A` зникла;
- успадкований рецепт лишається видимою редагованою початковою копією, без
  прихованих readonly-значень.

> Поточний UI знімає `batchLock`, але не очищує техкарту, inputs і вибрані
> альтернативи. Значення попередньої партії залишаються як редагована початкова копія.

### TC-04 — Зміна на іншу непорожню партію

**Передумови:** у формі створення вибрана `UNIFORM-A`.

**Кроки:** змінити номер партії на `UNIFORM-B`.

**Очікуваний результат:**

- рецепт `UNIFORM-A` замінено рецептом `UNIFORM-B`;
- усі рецептурні поля залишаються заблокованими;
- підказка містить номер `UNIFORM-B`;
- у формі не залишилися значення попередньої партії.

### TC-05 — Інша техкарта в другому записі через API

**Передумови:** `UNIFORM-A` використовує ТК-А v1.

**Кроки:** через API створити в `UNIFORM-A` запис із ТК-Б v1.

**Очікуваний результат:**

- збереження заблоковано validation error;
- у БД не створено запис і пов'язані рухи ресурсів;
- повідомлення містить номер партії та текст на кшталт
  `за різними техкартами ТК-А, ТК-Б`.

### TC-06 — Інша альтернатива в одній групі через API

**Передумови:** `UNIFORM-A` використовує ТК-А v1 і `Зерно = Жито`.

**Кроки:** через API створити запис із ТК-А v1 і `Зерно = Пшениця`.

**Очікуваний результат:**

- збереження заблоковано;
- деталь помилки містить
  `ТК-А — Зерно: Жито та Пшениця`;
- решта однакових груп не вказується як конфліктна.

### TC-07 — Розбіжність у двох альтернативних групах

**Передумови:** у `UNIFORM-A` визначено вибір у групах `Зерно` й `Олія`.

**Кроки:** через API створити запис з іншим ресурсом у кожній із цих груп.

**Очікуваний результат:**

- збереження заблоковано;
- обидві групи та відповідні пари ресурсів присутні в повідомленні;
- деталі груп розділені символом `;`;
- групи не дублюються.

### TC-08 — Спроба змінити техкарту єдиного запису партії

**Передумови:** `SINGLE` має рівно один збережений запис за ТК-А v1.

**Кроки:**

1. Перевірити форму редагування: поле техкарти має бути disabled.
2. В обхід UI надіслати update-запит із ТК-Б.

**Очікуваний результат:**

- UI не дозволяє змінити техкарту;
- backend повертає `400 Bad Request`;
- помилка прив'язана до поля `technologicalMapId`;
- текст: `Технологічну карту збереженого запису змінити не можна. Створіть новий запис за потрібною картою`;
- запис і його inputs/альтернативи в БД не змінені;
- наявність лише одного запису в партії не скасовує immutability.

### TC-09 — Редагування одного з кількох записів на іншу техкарту

**Передумови:** `UNIFORM-A` має щонайменше два записи за ТК-А v1.

**Кроки:**

1. Перевірити, що у формі редагування техкарта disabled.
2. Через API спробувати змінити техкарту одного запису на ТК-Б.

**Очікуваний результат:**

- backend повертає `400 Bad Request` з полем `technologicalMapId`;
- показано загальне повідомлення про незмінність техкарти, а не batch recipe mismatch;
- у БД запис не змінився.

### TC-10 — Перенесення запису до партії з іншим рецептом

**Передумови:** існуючий запис використовує рецепт ТК-А; `UNIFORM-B` використовує
інший рецепт.

**Кроки:**

1. Перевірити форму редагування: номер партії має бути disabled.
2. Через API змінити номер партії на `UNIFORM-B`.

**Очікуваний результат:**

- backend повертає `400 Bad Request` з полем `batchNumber`;
- текст: `Номер партії збереженого запису змінити не можна - запис лишається в партії {поточний номер}. Створіть новий запис з потрібним номером партії`;
- перевірка рецепта цільової партії не виконується, тому що номер незмінний;
- запис залишається у вихідній партії;
- немає частково збережених змін.

## 4. Додаткові критичні перевірки

| ID | Перевірка | Очікуваний результат |
|---|---|---|
| TC-11 | Та сама техкарта, але інша версія | `400`; `field = batchNumber`; текст містить `за різними техкартами {назва} (версія {v1}), {назва} (версія {v2})` |
| TC-12 | Редагування кількості, дати та виробничої зміни без зміни рецепта | Збереження успішне; нові кількість, дата й зміна збережені; запис не порівнюється із самим собою |
| TC-13 | Спроба змінити номер партії на порожню партію | `400`, `field = batchNumber`, повідомлення про незмінність номера; запис залишається у вихідній партії. Порожність цільової партії не скасовує immutability |
| TC-14 | Два одночасні перші записи з різними рецептами | **Deferred:** майбутня гарантія через транзакційний lock; поточний race condition зафіксовано як відомий ризик |
| TC-15 | UI відкрив порожню партію, але інший користувач уже додав рецепт | Backend відхиляє несумісний Save; введені дані не втрачаються |
| TC-16 | Збереження через імпорт, bulk API або іншу точку входу | Те саме доменне правило неможливо обійти |
| TC-17 | Відхилене збереження | Не створює часткових змін, складських рухів або події успішного виробництва |
| TC-18 | Декомпозиція одиниць із різних записів однорідної партії | Кожна одиниця розкладається за єдиною ТК, версією та альтернативами партії |

## 5. Зафіксовані рішення та фактична поведінка коду

### 5.1. Текст помилки для різних версій однієї техкарти

Поточний backend формує такий текст:

```text
Одна партія виробів повинна робитися за одним рецептом, ви хочете зберегти в партії {номер} записи за різними рецептами: за різними техкартами {назва} (версія {v1}), {назва} (версія {v2}). Щоб зберегти запис - зробіть різні номери партій
```

Версії додаються до назв лише тоді, коли назви двох техкарт однакові. Джерело:
`messages.properties` і `ManufacturingProcessValidator.mapLabel()`.

### 5.2. Статуси записів

У поточній моделі `ProductionProcess` немає статусу, ознаки archive або soft-delete.
Видалення фізичне й супроводжується rollback складського руху. Зараз у визначенні
рецепта беруть участь усі збережені записи, які одночасно мають:

- той самий `resourceId`;
- той самий `batchNumber`;
- техкарту типу `PRODUCTION`.

`DISASSEMBLY` не враховується. Чернеток і скасованих записів у цій моделі немає.

### 5.3. Legacy-партії

Зафіксована продуктова політика:

- наявні записи не мігруються;
- редагування нерецептурних полів наявного запису не повинно блокуватися через
  історичну неоднорідність партії;
- кожне нове створення проходить нову валідацію;
- новий запис у вже неоднорідній партії має бути відхилений, тому що він не може
  збігатися з усіма наявними рецептами одночасно.

Поточний код порівнює новий запис лише з одним найновішим записом партії. Тому новий
запис, що збігається з найновішим рецептом legacy-партії, зараз може бути збережений.
Це розбіжність між зафіксованою політикою та реалізацією.

### 5.4. Вибір еталонного запису

Поточний код обирає не перший, а **найновіший** запис:

```text
ORDER BY production_date DESC, id DESC
LIMIT 1
```

Партія визначається глобально між складами ключем `(resourceId, batchNumber)`. Під час
редагування поточний `id` виключається із запиту. Це реалізовано в
`ProductionProcessRepository.findIdsInProducedBatch()` і
`ProductionProcessService.getBatchRecipe()`.

### 5.5. Перехід UI на порожню партію

Поточний UI лише знімає блокування `batchLock`. Уже підставлені техкарта, inputs та
альтернативи не очищуються й стають доступними для редагування.

### 5.6. Поточний HTTP-контракт validation error

- HTTP status: `400 Bad Request`;
- поле помилки: `batchNumber`;
- окремого machine-readable error code немає;
- UI читає лише `errors[0].messages[0]`.

```json
{
  "errors": [
    {
      "field": "batchNumber",
      "messages": [
        "Одна партія виробів повинна робитися за одним рецептом, ..."
      ]
    }
  ]
}
```

### 5.7. Конкурентні перші записи

Поточний код не має механізму, що гарантує узгодженість двох паралельних перших
записів. Валідація виконується до транзакційного `ManufacturingProcessFacade.create()`,
запит не бере lock, а в БД є лише неунікальний індекс `(batch_number, resource_id)`.
Обидва запити можуть одночасно побачити порожню партію і зберегти різні рецепти.

### 5.8. Редагування існуючого запису: розбіжність зі специфікацією

Поточний backend має додаткові загальні обмеження:

- техкарту збереженого запису змінювати заборонено завжди;
- непорожній номер партії збереженого запису змінювати заборонено завжди;
- update-flow не приймає новий набір inputs/альтернатив, а лишає збережені inputs.

Сценарії `TC-08`, `TC-09`, `TC-10` і `TC-13` перевіряють саме ці чинні обмеження.
Поточні повідомлення:

```text
Технологічну карту збереженого запису змінити не можна. Створіть новий запис за потрібною картою
```

```text
Номер партії збереженого запису змінити не можна - запис лишається в партії {номер}. Створіть новий запис з потрібним номером партії
```

Рішення для поточного scope: immutability не змінюємо. Рецепт і непорожній номер
партії після створення залишаються незмінними. Тест-план перевіряє поточну поведінку;
зміна рецепта чи перенесення запису між партіями не є acceptance-вимогою.

## 6. Рекомендації для обговорення

### 6.1. Майбутні статуси

Рекомендується прив'язати участь у рецепті не до назви статусу, а до складського
ефекту запису:

- draft — не враховувати до проведення;
- active/posted — враховувати;
- cancelled або soft-deleted — не враховувати лише після повного rollback запасів;
- archived — враховувати, якщо запис і його вироблений залишок продовжують існувати.

### 6.2. Еталон партії

Якщо backend перевіряє всі записи партії, конкретний «перший» або «останній» запис
не впливає на валідацію однорідної партії. Для UI рекомендується залишити поточний
детермінований порядок `date DESC, id DESC`, але називати результат «еталонним
рецептом», а не «першим записом». Для legacy-партії endpoint повинен повернути
конфлікт/ознаку неоднорідності, а не мовчки рецепт останнього запису.

### 6.3. Очищення форми

Рекомендується зберегти поточну поведінку: після переходу на порожню партію залишати
успадкований рецепт, але розблоковувати його. Це не руйнує вже введені дані та дає
зручну стартову копію; backend усе одно залишається остаточною гарантією.

### 6.4. Контракт помилки

**Статус:** deferred, не реалізовувати в поточному scope.

Для сумісності рекомендується залишити `400 Bad Request` і наявні `field/messages`,
але розширити елемент помилки необов'язковими полями:

```json
{
  "field": "batchNumber",
  "code": "BATCH_RECIPE_MISMATCH",
  "messages": ["Локалізований текст для користувача"],
  "details": {
    "batchNumber": "B-100",
    "conflictType": "TECH_MAP_VERSION",
    "reference": { "techMapId": 10, "name": "ТК-А", "version": 1 },
    "candidate": { "techMapId": 11, "name": "ТК-А", "version": 2 },
    "alternativeGroups": []
  }
}
```

UI має приймати рішення за `code`, а `messages` використовувати лише для показу.

### 6.5. Захист від race condition

**Статус:** deferred, не реалізовувати в поточному scope.

Мінімально інвазивний варіант для PostgreSQL:

1. перенести валідацію та save в одну транзакцію;
2. на початку транзакції брати advisory transaction lock за стабільним ключем
   `(resourceId, batchNumber)`;
3. для bulk-запиту брати ключі у відсортованому порядку;
4. після отримання lock повторно читати всі рецепти партії й валідовувати;
5. другий конкурентний запит після очікування отримує звичайний
   `BATCH_RECIPE_MISMATCH`, а не створює неоднорідність.

`SELECT ... FOR UPDATE` лише по записах партії недостатній: у порожній партії немає
рядка, який можна заблокувати. Довгострокова альтернатива — окрема таблиця
`batch_recipe` з унікальним ключем `(resource_id, batch_number)` і recipe fingerprint.
