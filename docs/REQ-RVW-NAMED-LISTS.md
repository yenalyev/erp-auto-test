# Іменовані списки ресурсів відстеження

## Призначення

Користувач із доступом до Resource Viewer зберігає набір ресурсів під назвою та швидко застосовує його на сторінці `/resources-viewer/relocation`. Списки спільні для всіх користувачів, які мають доступ до Resource Viewer. Повний сценарій створення списку перевіряється для системної ролі `resource-tracker` («Відстеження ресурсів»), що має `resource-viewer.read` і `resource.read` для каталогу ресурсів.

## Необхідні ролі та права

- Для користувача функції призначити системну роль `resource-tracker` («Відстеження ресурсів») на потрібну локацію. Вона надає `resource-viewer.read` для сторінки й усіх операцій зі списками та `resource.read` для каталогу в діалозі вибору ресурсів. До складу цієї системної ролі також входять `location.read`, `resource-category.read` та `invoice.read`.
- Якщо користувач має іншу бізнесову роль, зокрема «Декомпозер ресурсів», для повного сценарію йому потрібні ефективні права `resource-viewer.read` (глобальне) і `resource.read` (для потрібної локації). Одного `resource-viewer.read` достатньо для API списків, але недостатньо для вибору ресурсу в UI: запит каталогу повертає 403.
- `ADMIN` використовується тестами для створення ресурсів і локації, перевірки видимості спільного списку та очищення даних. Користувачу функції адміністративна роль не потрібна. `UserRole.RESOURCE_VIEWER` у коді тестів є слотом сесії, до якого тимчасово прив'язується динамічно створений користувач із роллю `resource-tracker`.

## Очікувана поведінка

1. У полі «Список ресурсів» показуються назви всіх збережених списків. Порожній довідник показує «Списків ще немає».
2. Через «Керувати списками» користувач створює список із непорожньою назвою та щонайменше одним ресурсом. Назва без пробілів на краях зберігається; повторна назва та порожній список не зберігаються.
3. Користувач може відкрити список для редагування, змінити назву і склад, а після збереження інші користувачі бачать оновлення. Скасування форми не змінює список.
4. Видалення вимагає підтвердження і прибирає список для всіх користувачів; скасування підтвердження залишає його.
5. Вибір списку підставляє його ресурси у «Ресурси для відстеження» і очищає вибрані категорії. Інші фільтри зберігаються. Користувач може потім змінити набір ресурсів вручну. Пошук, підсумки та Excel працюють з фактично застосованими фільтрами.
6. API `/api/v1/resources-viewer/list` підтримує `POST`, `GET /names`, `GET /{id}`, `PUT /{id}` і `DELETE /{id}`. Всі операції вимагають `resource-viewer.read`. API перевіряє існування ресурсів, непорожні назву й склад, унікальність назви; створення та зміна не мають лишати часткових записів після помилки.

## Автоматизовані перевірки

- `TC-RVW-LIST-API-001`: повний життєвий цикл списку під динамічно створеним користувачем із системною роллю `resource-tracker`, видимість через іншого користувача та збереження після повторного GET.
- `TC-RVW-LIST-API-002`: відхилення порожньої назви, дубля назви, порожнього складу й невідомого resource ID; незмінність уже збереженого списку.
- `TC-UI-RVW-014`: створення, застосування, редагування й видалення списку через UI під користувачем із системною роллю `resource-tracker`.
- `TC-UI-RVW-015`: застосування через UI готового списку під тим самим користувачем.
- `TC-UI-RVW-017`: доступність каталогу ресурсів у формі нового списку під системною роллю `resource-tracker`.

API й UI фікстури динамічно створюють окремого користувача та тестову локацію. Користувач має лише системну роль `resource-tracker` в межах цієї локації, без ролі керівника локації; фікстура перевіряє склад прав і призначених грантів. Тестові списки отримують унікальні назви. Після прогону списки й ресурси прибираються, користувач деактивується, локація архівується. Усі кейси входять до suite `resource-viewer`.

## Стан dev на 13.10.2026

Попередній прогін із тестовою роллю, що мала лише `resource-viewer.read`, показав 403 для каталогу `/api/v1/resources`. Після зміни фікстур цільовий прогін на dev пройшов: обидва API кейси й усі три UI кейси завершились успішно під динамічними користувачами з єдиною системною роллю `resource-tracker`. Фікстура підтвердила її грант на окремій тестовій локації; API каталогу повернув 200. Створені списки й ресурси видалено, гранти відкликано, користувачів деактивовано, локації архівовано.
