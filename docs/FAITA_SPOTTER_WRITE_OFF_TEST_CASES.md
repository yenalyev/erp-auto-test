# Списання Файти з точки спотерів — тест-кейси

Спільно: створити унікальний ресурс `R`, зіставити його із зовнішнім ID Fight; `amount=2`. Перед дією зняти залишки всіх залучених точок; після дії перевірити точний delta та статус. History і журнал для завершених записів залишаються додатковими ручними перевірками. Кожен source event має унікальний маркер.

## TC-FAITA-SPOT-001 — один спотер [P0, автоматизовано]

Дано спотер `S1` з точкою `P1`; `P1=5 R`, CREW спотера `=0`. Створити FLIGHT write-off для `S1`, завершити. Очікувати `COMPLETED`, `P1=3`, CREW незмінний; history списання належить `P1`.

## TC-FAITA-SPOT-002 — ресурс тільки в другого [P0, автоматизовано]

Дано впорядковані склади `S1,S2`, точки `P1=0`, `P2=5`. Завершити списання. Очікувати `P1=0`, `P2=3`, `COMPLETED`, один повний дебет на `P2`.

## TC-FAITA-SPOT-002B — перша точка має частину кількості [P0, автоматизовано]

Дано `P1=1`, `P2=5` при `amount=2`. Очікувати незмінне `P1=1`, `P2=3`, `COMPLETED`. Кількість не ділиться між точками.

## TC-FAITA-SPOT-003 — ресурс в обох [P0, автоматизовано]

Дано впорядковані склади `S1,S2`, `P1=5`, `P2=5`. Завершити списання. Очікувати `P1=3`, `P2=5`, `COMPLETED`. Повторення з переставленим source масивом є окремою перевіркою імпорту.

## TC-FAITA-SPOT-004 — немає достатнього залишку [P1, автоматизовано]

Дано `P1=0`, `P2=0`; окремий ручний варіант: `P1=1`, `P2=1` при `amount=2`. Очікувати нуль дебету, відсутність збирання кількості з двох точок, `FAILED` після прямого complete; правило на етапі імпорту узгодити з no-stock контрактом.

## TC-FAITA-SPOT-005 — масив ID з Fight log [P0, автоматизовано з opt-in]

Створити два контрольовані `crew.team` зі складами спотерів. Додати flight log бойового екіпажу з `spotter_team_id=[S1,S2]`, запустити `syncTeams`. Очікувати `CREATED`, один write-off із `storage_id=CREW(S1)` і `alternative_storage_ids=[CREW(S2)]`; після повторного sync — один запис. Cleanup видаляє лише власні source rows і незавершений write-off.

## TC-FAITA-SPOT-006 — реальний імпорт з `imp.ammo_agg_v2` [P0, ручний/source fixture]

Посіяти source row із `spotter_team_id=[S1,S2]` у керованому Fight schema, імпортувати. Перевірити ідентичний масив у flight log та маршрут до `P1/P2` згідно stock. Повторити sync; не має бути дублів чи другого дебету.

## TC-FAITA-SPOT-007 — позиція вильоту відрізняється [P0, ручний/source fixture]

У FLIGHT write-off явне `fly_point_storage_id` вказує на точку вильоту `P0`, а `storage_id` на CREW спотера з точкою `P1`; обидві мають ресурс. Очікувати дебет тільки `P1`, `P0` незмінна. Повний Fight import із `position_name` потребує окремої source-фікстури.

## TC-FAITA-SPOT-008 — відсутній/порожній масив [P1, регресія]

Для `spotter_team_id=NULL` та `{}` створити два flight events. Очікувати звичайне списання з точки бойового екіпажу або CREW, якщо точки немає. Чужі спотерські точки незмінні.

## TC-FAITA-SPOT-009 — невалідний ID спотера [P1]

Масив містить невідомий ID або спотера без storage. Зафіксувати погоджений результат: явна помилка/пропуск із діагностикою, без тихого списання з бойового екіпажу чи іншого спотера. До уточнення вимоги це exploratory кейс.
