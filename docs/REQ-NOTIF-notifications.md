# REQ-NOTIF — Сповіщення

## Призначення

Функція охоплює адміністративні шаблони та підписки, персональну вкладку
«Мої сповіщення», браузерні сповіщення і доставку через chatbot.

## Зміна каталогу шаблонів

- Шаблони `invoice_generated` і `tech_map_mode_changed` видалені та не повинні
  повертатися ні в `GET /api/v1/notifications/templates`, ні в персональній
  конфігурації `GET /api/v1/notifications/my`.
- Додано `order_created` з описом «Нове замовлення».
- Додано `production_order_created` з описом «Нове виробниче замовлення».

## Персональні підписки

Користувач відкриває «Мої сповіщення» з меню профілю, вмикає потрібний шаблон
та, за потреби, обмежує підписку доступними локаціями. Стан зберігається через
`POST /api/v1/notifications/my`, читається через `GET /api/v1/notifications/my`
і видаляється через `DELETE /api/v1/notifications/my`.

Поточна рольова модель:

- адміністратор замовлень бачить і вмикає «Нове замовлення»;
- окремої ролі адміністратора виробничих замовлень ще немає, тому «Нове
  виробниче замовлення» перевіряється під глобальним `Admin`;
- після появи окремої ролі UI-сценарій необхідно перевести на користувача з
  `production-order.manage`. API-контракт цього дозволу вже покритий окремо.

## Події

- Створення нового замовлення формує браузерне сповіщення `order_created` для
  підписаного адміністратора замовлень у відповідній локації.
- Створення нового виробничого замовлення формує браузерне сповіщення
  `production_order_created` для підписаного користувача у відповідній локації.
- Payload браузерного сповіщення містить щонайменше `template_code` і
  `storage_name`.

## Acceptance criteria

- **AC-02.** Каталог містить актуальні seeded-шаблони, включно з
  `order_created` і `production_order_created`, та не містить
  `invoice_generated` і `tech_map_mode_changed`.
- **AC-09.** Персональна конфігурація повертає актуальні шаблони; підписку можна
  створити, прочитати після повторного запиту та видалити.
- **AC-10.** Після створення замовлення підписаний адміністратор замовлень
  отримує `order_created` для локації замовлення.
- **AC-11.** Після створення виробничого замовлення підписаний користувач
  отримує `production_order_created` для цільової локації.
- **AC-12.** У «Моїх сповіщеннях» адміністратор замовлень може ввімкнути «Нове
  замовлення», а глобальний `Admin` — «Нове виробниче замовлення». Після появи
  окремої виробничої ролі другий сценарій переходить на `production-order.manage`.

## Автоматизоване покриття

- `TC-NOTIF-010` — актуальний каталог шаблонів і відсутність видалених кодів.
- `TC-NOTIF-040` — персональна підписка адміністратора замовлень.
- `TC-NOTIF-041` — API-підписка користувача з `production-order.manage`.
- `TC-NOTIF-042` — видалені коди відсутні у персональній конфігурації.
- `TC-NOTIF-050` — `order_created` після створення замовлення.
- `TC-NOTIF-051` — `production_order_created` після створення виробничого замовлення.
- `TC-NOTIF-UI-020` — UI-підписка адміністратора замовлень.
- `TC-NOTIF-UI-021` — UI-підписка глобального `Admin` на виробничі замовлення.

## Замовлення на переміщення — план перевірки

Ролі: керівник локації, керівник мультилокацій, адміністратор замовлень і
глобальний `Admin`. Для виробничого замовлення перевіряється саме `Admin`.
Адмінський каталог містить «Нове завдання на переміщення»; це окреме
сповіщення від «Замовлення переміщення» для керівників локацій. В адмінському
UI останній рядок не очікується.
Сповіщення прив'язуються до ID щойно створеного замовлення або запиту, щоб
виключити збіг зі сповіщенням попереднього запуску.

Тестова ієрархія для запиту на переміщення: `P → A → A1`, `P → B`, окрема
доступна локація `C` та чужа `X`. Керівник мультилокацій має доступ до `P` і
`C`; керівник однієї локації — до `B`.

- `TC-NOTIF-060` — керівник `B` отримує запит для `B`, але не для `X`.
- `TC-NOTIF-061` — вибір лише `B` не дає сповіщень для `A`, `C` чи `X`.
- `TC-NOTIF-062` — вибір `P` охоплює `P`, `A`, `A1`, `B`, але не `C` і `X`.
- `TC-NOTIF-063` — «Всі локації» охоплюють доступні `P`, `A`, `A1`, `B`, `C`,
  але не `X`.
- `TC-NOTIF-064` — зміна вибору зберігається; після відписки нові запити не
  породжують сповіщення для користувача.
- `TC-NOTIF-UI-022` — керівник однієї локації налаштовує підписку в UI.
- `TC-NOTIF-UI-023` — керівник мультилокацій вибирає батьківську локацію й
  «Всі» в UI; після оновлення сторінки вибір зберігається.

Негативні перевірки доставки опитують API протягом п'яти секунд після
створення запиту. Усі ці сценарії потребують розгорнутої фічі; на поточному
бекенді шаблон замовлення на переміщення відсутній.

## Результат dev-перевірки

API-сценарії `TC-NOTIF-010`, `TC-NOTIF-040`, `TC-NOTIF-041`,
`TC-NOTIF-042`, `TC-NOTIF-050` і `TC-NOTIF-051` пройшли. UI-сценарій
`TC-NOTIF-UI-020` пройшов. Перевірка виробничої підписки під глобальним
`Admin` пройшла; варіант з довільним користувачем, якому вручну видано лише
`production-order.manage`, не показує рядок у поточному UI і лишається
майбутньою перевіркою після появи окремої ролі.
