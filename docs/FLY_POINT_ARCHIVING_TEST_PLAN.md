# План тестування: архівація точки вильоту

## Мета і межі

Перевірити, що комірник підрозділу й адміністратор можуть архівувати точку вильоту лише після врегулювання **активних екіпажів**, **фізичного залишку** та **активного резерву**. Після успішного переміщення залишків або надзвичайної події користувач повертається до перевірки умов архівації. Архівація означає зміну стану точки на неактивний зі збереженням історії, а не фізичне видалення.

Код продукту перевірено в сусідніх репозиторіях `tk-ui` і `tk`. Узгоджений потік відповідає реалізації: кнопка «Архівувати» стоїть на картці точки **у списку** `/fly-points`; вона відкриває сторінку `/fly-points/close/{id}`, а обробка екіпажів — `/fly-points/close/{id}/crews`. Після успішного сабміту форм переміщення й події користувач повертається на `/fly-points/close/{id}`.

**Уточнення користувача:** вантаж у дорозі **не блокує** архівацію. Резерв треба **окремо вручну зняти**, перш ніж переміщувати чи списувати відповідну фізичну кількість; він є частиною фізичного залишку й не додається до нього вдруге. Перелік залишків має показувати **назву, одиницю, кількість і партію**. Екіпаж із власним залишком або активною операцією архівувати не можна. Комірник має тільки «Керівник локації» та доступ до екіпажів, без додаткових грантів; адміністратор проходить той самий функціональний потік.

## Тестові дані

- Підрозділ A: активні точки **P1** (архівуємо), **P2** (ціль переміщення), **P3** (архівна); підрозділ B: активна **P4**. Окремо перевірити випадок, коли в A немає іншої активної точки.
- Для DEV-автотестів використовувати наявний батальйон як незмінний вузол і створювати під ним власні точки, екіпажі й матеріали: поточний `POST /storages` не зберігає `milUnitType=BATALION`, тому новий батальйон не з’явиться в API списку. Тестові точки й екіпажі архівувати в cleanup.
- Для P1 створити варіанти: немає екіпажів/залишків; один і кілька активних екіпажів; лише архівні екіпажі; вільний фізичний залишок; фізичний залишок, **повністю або частково зарезервований**; лише незавершене вихідне переміщення без фізичного залишку; нульові залишки; активні екіпажі разом із фізичним залишком або резервом.
- Для переліку залишків підготувати два ресурси, кілька партій одного ресурсу й різні одиниці виміру. Зафіксувати кількості та UUID партій до кожної дії. Окремий екіпаж має власний залишок, інший — незавершену операцію.
- Сесії: комірник підрозділу A лише з ролями **«Керівник локації» + доступ до екіпажів**, адміністратор, користувач без права архівації, комірник підрозділу B; для сценарію резерву — окремий користувач, який уже має право керувати замовленням/бронню. Для кожного сценарію створювати незалежну P1.

## Пріоритетні сценарії

### P0 — критичний бізнес-потік

1. **Доступ і точка входу.** На картці активної P1 **у списку** комірник A й адміністратор бачать кнопку архівації та відкривають `/fly-points/close/{id}`. Комірник не отримує додаткових прав понад дві узгоджені ролі. Користувач без права кнопку не бачить; пряма дія через API заборонена. Комірник B не може архівувати P1. На архівній P3 повторна дія недоступна. UI перевіряє `business-unit::delete` для ID точки — перевірити, чи цей дозвіл реально випливає з ролей комірника.
2. **Порожня точка.** Натиснути деактивацію P1 без активних екіпажів, фізичних залишків і резерву. На сторінці є фінальне підтвердження «Архівувати точку вильоту …?» — перевірити скасування і підтвердження, `active=false` в API, відсутність у фільтрі «Активні», наявність у «Всі» як архівної, збереження історії та неможливість вибрати її для нових операцій. Окремо: вихідний вантаж уже в дорозі, фізичний залишок нульовий — архівація не блокується тільки через статус переміщення.
3. **Активні екіпажі блокують архівацію.** Для P1 з активними екіпажами перевірити точний текст «На точці є активні екіпажі. Перемістіть екіпажі на інші точки або архівуйте їх», кнопки «Скасувати» і «Перемістити» на сторінці архівації. «Скасувати» не змінює точку й екіпажі. До врегулювання екіпажів P1 лишається активною.
4. **Екіпажі — перемістити.** Після «Перемістити» показані всі й лише активні екіпажі P1. Перемістити один екіпаж на P2: змінюється його батьківська точка, інші екіпажі незмінні, P1 ще активна. Для останнього екіпажу перевірити доступність «Готово» і повернення до перевірки блокерів. У виборі цілі доступні лише інші активні точки **того самого батальйону**; P3 і P4 недоступні. Поточна форма обробляє екіпажі **по одному рядку**; P1 присутня як початкове значення, але кнопка переміщення для неї вимкнена.
5. **Екіпажі — архівувати.** Архівувати порожній екіпаж: він стає неактивним, зникає зі списку активних екіпажів P1, не змінює інші екіпажі; після обробки останнього можна продовжити архівацію P1. Екіпаж із **власним залишком** або **активною операцією** архівувати не можна: показати причину, зберегти стан екіпажу й P1. Перевірити комбінацію дій: один екіпаж переміщено, інший архівовано. Поточний backend перевіряє власний додатний залишок, але окремої перевірки активних операцій у `validateDelete` немає.
6. **Залишки та резерв блокують архівацію.** Для вільної й зарезервованої фізичної кількості перевірити текст «На точці є залишки … Перемістіть залишки на іншу точку або створіть надзвичайну подію», повний перелік із **назвою, одиницею, кількістю та партією** (без нульових або чужих позицій), кнопки «Скасувати», «Перемістити залишки», «Надзвичайна подія». Показувати фізичну кількість один раз, а резерв — окремою ознакою/кількістю **в її межах**, без підсумовування. Бронь у чинній моделі прив'язана до ресурсу, а не до партії; для її рядка не вигадувати партію. Скасування зберігає стан. Прямий API-виклик архівації відхиляється, доки лишається фізичний залишок або активна бронь. Поточний `close-prerequisites` повертає тільки `StorageItem.amount > 0` з назвою й кількістю — одиницю, партію та ознаку резерву не віддає.
7. **Перемістити залишки.** Кнопка відкриває `/relocation/create-output-fly-point` з P1 як фіксованим джерелом і попереднім заповненням **вільного** залишку; ціллю можна обрати лише активну точку підрозділу. Після успішного сабміту перевірити одну створену операцію, її статус і склад/кількості відповідно до життєвого циклу видачі, а також повернення на **`/fly-points/close/{id}`**. Якщо переміщення списало весь фізичний залишок, вантаж у дорозі сам по собі не блокує підтвердження архівації.
8. **Надзвичайна подія точки.** Кнопка відкриває `/inventory/create-incident/{flyPointId}`; форма створює `POST /api/v1/incidents/storages` із датою, описом, ресурсами та необов'язковими партіями. Є **повне** й **часткове** списання: повне бере всі вільні позиції (FIFO для партій), часткове — вибрані ресурси/партії; сервер відхиляє кількість понад фізичний залишок. Після успіху перевірити запис події, списання відповідної кількості й повернення на **`/fly-points/close/{id}`**. Зарезервовану кількість перед списанням треба вручну розбронювати; вантаж у дорозі не є блокером.
9. **Ручне зняття резерву.** Для P1 із фізичною кількістю N, з якої M зарезервовано, перевірити `вільно=N−M`; форма переміщення не дозволяє відправити M, подія не списує M. Уповноважений користувач вручну знімає бронь у пов'язаному замовленні (`DELETE /api/v1/orders/{id}/bookings/{bookingId}?storageId=...`; для броні виробничого замовлення — відповідна дія над hold), після чого вільна кількість стає N. Комірник повторно відкриває архівацію, переміщує або списує N й архівує точку. Не надавати комірнику `order.manage` чи `production-order.manage` тільки заради цього потоку. Якщо від комірника очікується самостійне зняття резерву, це окреме продуктове рішення, не припущення тесту.
10. **Одночасно екіпажі й залишки.** P1 має обидві перешкоди. Поточний UI перевіряє `crews.length > 0` **перед** `stocks.length > 0`, тому спершу показує екіпажі, після їх врегулювання — залишки; цей порядок підтвердити тестом як фактичну реалізацію. Після обробки обох — рівно одна успішна архівація. Порядок не закріплювати як нове продуктове правило.

### P1 — помилки, межі, узгодженість

11. **Неуспішні форми.** Валідація, 4xx/5xx або мережева помилка при переміщенні екіпажу, його архівації, переміщенні залишків, створенні події, знятті резерву й архівації точки: показана помилка, користувач залишається в контексті дії, дані не змінені частково. Закриття форми/повернення назад також не змінює дані.
12. **Межі даних.** Один/багато екіпажів; лише архівні екіпажі; один/багато ресурсів; нульовий баланс; часткове переміщення залишку; повний/частковий резерв; відсутня інша активна точка в підрозділі; довгі назви ресурсів і екіпажів. Списки на сторінках мають бути повними, без дублювання та коректними після оновлення.
13. **Стан змінився в іншій сесії.** Після відкриття сторінки інший користувач додає екіпаж або залишок, створює/знімає резерв, змінює цільову точку на архівну чи вже архівує P1. При сабміті сервер повторно перевіряє умови; UI оновлює стан або показує конфлікт. Подвійний клік не створює дубльованих переміщень, подій чи архівацій.
14. **Права в усіх діях.** Комірник тільки з двома узгодженими ролями й адміністратор проходять усі доступні дії; додаткових грантів комірнику в тесті не видавати. Кнопка й API мають однаково відмовляти без потрібного права; дані іншого підрозділу не відкриваються через підміну ID у URL/запиті. Зняття броні виконує лише користувач, уповноважений для відповідного замовлення.
15. **Регресія після архівації.** Архівна точка не з'являється серед активних цілей, у новій видачі, призначенні екіпажу та інших селекторах; попередні операції, залишки й історія доступні відповідно до наявних правил. Якщо підтримується розархівація, перевірити повернення в активний список без втрати історії.

## Рівні перевірки й автоматизація

- **UI, Playwright:** кнопка й ролі, тексти та склад сторінок, вибір цілі, скасування, маршрути, успішний/неуспішний сабміт. Розширити `FlyPointsPage` і додати Page Object для сторінок `/fly-points/close/{id}` та `/crews`; перевикористати форми переміщення й події.
- **API, RestAssured:** серверне блокування архівації за активних екіпажів, фізичного залишку та активного резерву; **не** блокувати лише через вантаж у дорозі. Перевірити права, `active`, зв'язки екіпажу, баланси, конкуренцію й повторні запити. Поточний backend `StorageValidator.validateDelete` уже блокує фізичний додатний залишок, але окремої перевірки активних екіпажів/броні немає. Старий коментар у `StorageDeactivationTest` про відсутність блокування залишків застарів.
- **Наскрізний smoke:** по одному успішному шляху для порожньої точки, екіпажів, переміщення залишків і події; звіряти UI з API після дії. Регресійні перевірки списку точок і видачі між точками повторити після зміни.

## Права й поточна навігація за кодом

- Кнопка архівації точки: `business-unit::delete` для ID точки; API `DELETE /api/v1/storages/{id}` перевіряє те саме право.
- Переміщення екіпажу: `PUT /api/v1/storages/{crewId}` потребує `business-unit::update` для ID екіпажу. Архівація екіпажу: `business-unit::delete` для ID екіпажу. На сторінці екіпажів кнопки зараз не приховані за окремими перевірками цих прав: відмова приходить із сервера.
- Переміщення залишків: створення видачі вимагає `relocation::create` для точки-відправника. Подія точки: `incident::create` **та** `business-unit-list::read` на точку; UI показує кнопку за `incident::create`. `SystemRoles.location-head` включає `incident.create` й `relocation.create`, але **не** глобальне `locations.manage`, яке мапиться на `business-unit::update/delete`. Тому поточний UI/API архівації точки та екіпажу для комірника з узгодженими двома ролями можуть бути недоступними. Це дефект прав/авторизації фічі; у тестах не видавати обхідних грантів.
- Ручне зняття броні замовлення: `order.manage` на джерело; ця дія не входить до ролі «Керівник локації». Її має виконати користувач із чинним правом на замовлення. Бронь виробничого замовлення знімається окремим API з правом керувати відповідним ВЗ.
- «Скасувати» на `/fly-points/close/{id}` повертає на `/fly-points`; у сторінці екіпажів використано `navigate(-1)`; у формі переміщення — `returnTo` на екран архівації; у формі події — `navigate(-1)`. Після **успішного** сабміту обох форм користувач повертається на `/fly-points/close/{id}`.

## Виявлені розриви для реалізації

1. **Права комірника:** поточна роль «Керівник локації» не дає `business-unit::update/delete`; узгоджена фіча має працювати без додаткових грантів. Потрібна зміна авторизації продукту, а не тестової ролі.
2. **Серверний guard:** `StorageValidator.validateDelete` перевіряє додатний фізичний залишок, але не активні екіпажі/броні та активні операції екіпажу. Це дозволяє обійти UI-послідовність прямим API-запитом.
3. **Дані попередження:** `close-prerequisites` не віддає одиницю, партію й розмір резерву. Для броні поточний `BookingResponse` містить ресурс і кількість, але не партію; показувати її як окрему частину фізичного залишку без вигаданого номера партії.
4. **Зняття броні:** на сторінці архівації немає прямого переходу до відповідного замовлення/броні. Бронь треба вручну зняти через чинний потік замовлення, а потім оновити перевірку точки.

**Критерій завершення:** точка архівується тільки без активних екіпажів, фізичного залишку й активного резерву; вантаж у дорозі сам по собі не блокує. Комірник з двома узгодженими ролями та адміністратор проходять дозволені шляхи, прямі API-запити не обходять правила; після успішного переміщення залишків або події користувач повертається до перевірки умов архівації.
