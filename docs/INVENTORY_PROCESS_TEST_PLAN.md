# Зміна процесу інвентаризації — тест-план

## Мета

Перевірити збереження причини запиту, рішення адміністратора та результату проведення інвентаризації, а також одноразовість проведення і доступність історії для адміністратора.

Актуальний API-процес:

1. `POST /api/v1/storages/inventory` — створити запит із `storageId` і обов'язковим `comment`.
2. `PUT /api/v1/storages/inventory` — адміністратор погоджує запит і переводить його у `OPEN`.
3. `DELETE /api/v1/storages/inventory` — адміністратор відхиляє запит із поясненням.
4. `PUT /api/v1/storages/{storageId}/inventory` — зберегти фактичні залишки; процес автоматично переходить у `CLOSED`.
5. `GET /api/v1/storages/inventory/processes` — історія процесів зі станами `REQUESTED`, `OPEN`, `CLOSED`, `REJECTED`.

## Знайдене попереднє покриття

- `InventorySessionApiTest` перевіряв стару модель: адміністратор напряму відкриває/закриває сесію, owner не може її відкрити.
- `InventoryConductApiTest` перевіряв зміну залишків, але очікував, що після `Зберегти` сесія лишається відкритою.
- `InventoryUiTest` і `UnitManagementPage` використовують старі кнопки `Відкрити інвентаризацію` / `Закрити інвентаризацію`.
- `CrewFlyPointInventoryUiTest` також містив старий toggle; deep-link сценарій fly-point адаптовано до `OPEN` process + доступної кнопки проведення.
- Тематичний набір `inventory.xml` містить ці API та UI класи, але змішує процес інвентаризації з експортом, ієрархією, алертами та іншими inventory-функціями.

## Оновлене автопокриття

- `TC-INV-PROC-001` — owner створює запит із причиною; причина і автор доступні в історії.
- `TC-INV-PROC-002` — admin погоджує запит; зберігаються дата відкриття, хто розглянув і коментар рішення.
- `TC-INV-PROC-003` — admin відхиляє запит із поясненням; owner отримує стан `REJECTED` і пояснення.
- `TC-INV-PROC-004` — owner не може сам погодити запит.
- `TC-INV-PROC-005` — backend не повинен приймати порожню або whitespace-only причину.
- `TC-INV-PROC-006` — після першого збереження процес `CLOSED`, повторне збереження заборонене.
- `TC-INV-PROC-007` — історія завершеного процесу має містити для кожного зміненого ресурсу `було`, `що змінилося`, `стало`.
- Наявні позитивні тести зміни/додавання/видалення залишків збережені; helper-и відкривають новий процес через request + approve.
- Окремий suite: `src/test/resources/suites/inventory-process.xml`.

## UI-перевірки за вимогою

1. Owner на конкретній локації бачить кнопку `Запит на інвентаризацію`; submit без причини недоступний.
2. Після submit відображається стан очікування рішення.
3. Admin у сайдбарі бачить `Інвентаризація` і три вкладки: нерозглянуті запити, відкриті, проведені.
4. У нерозглянутому запиті відображаються дата, локація, автор, причина та дії `Дозволити` / `Відхилити`.
5. Після відхилення owner бачить червону кнопку з текстом `Запит на інвентаризацію відхилено`; перший клік показує пояснення, після закриття кнопка повертається до звичайного стану.
6. Після погодження owner бачить зелену кнопку `Провести інвентаризацію`.
7. Після `Зберегти` повторний submit недоступний, а запис з'являється у проведених.
8. Результат містить ресурс, значення до інвентаризації, delta та значення після неї.
9. Пряма інвентаризація адміністратором також вимагає причину і зберігає результат.

## Команда запуску

```bash
mvn test -Denv=dev -Dsuite=inventory-process -Dsuite.artifact.sweep=false -Dtcm.enabled=false -Dgoogle.sheets.enabled=false
```

## Виявлені розбіжності dev

Станом на 06.10.2026:

- backend приймає `comment: "   "` при створенні запиту і повертає `200`, хоча причина обов'язкова;
- `diff` завершеного процесу містить лише `resourceId`, `resourceName`, `diffAmount`; значень `було` і `стало` немає;
- frontend показує `Запросити інвентаризацію`, а після відхилення — окремий жовтий текст і tooltip; це не червона кнопка `Запит на інвентаризацію відхилено` з одноразовим popup;
- вкладка історії називається `Закриті`, об'єднує `CLOSED` і `REJECTED`, а результат показується inline як delta, без окремої кнопки/popup і колонок `було` / `стало`;
- після завершення процесу на fly-point deep-link admin не отримує дії для початку наступної інвентаризації з обов'язковою причиною; у наявному admin modal frontend позначає коментар необов'язковим;
- POST-відповідь для базової локації може містити `storage.name: null`; JSON-схему тестів скориговано відповідно до фактичного nullable-контракту.
