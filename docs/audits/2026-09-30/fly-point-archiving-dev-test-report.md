# Архівація точки вильоту — DEV-прогін 30.09.2026

## Обсяг і спосіб запуску

Середовище: `https://dev.cukerochka.sbs`. Запуск UI/API-автотестів:

```powershell
mvn -Denv=dev -Dtest=FlyPointArchivingUiTest -Dtcm.enabled=false -Dgoogle.sheets.enabled=false test
```

Автотести створюють унікальні точки, екіпажі й ресурс під наявним DEV-батальйоном. Cleanup знімає тестові залишки й архівує створені точки та екіпажі; ресурс лишається в довіднику DEV. Новий батальйон через `POST /storages` створити не можна для цих сценаріїв: API ігнорує `milUnitType`, тож сторінка точок його не індексує. Це обмеження фікстури, а не результат кейсу архівації.

Основний прогін 10 методів: **6 успішних, 4 неуспішних**. Після виправлення двох фікстур повторний прогін `005` і `009` підтвердив два функціональні провали; додатковий `013` теж провалився через серверний guard. Підсумок 11 автоматизованих методів: **6 пройшли, 4 виявили дефекти, 1 заблокований правами створення тестового користувача**. Логи: `target/fly-point-archiving-final-dev.log`, `target/fly-point-archiving-blockers-dev.log`, `target/fly-point-archiving-race-dev.log`; скриншоти та кроки — `target/allure-results/`.

## Результати за кейсами

- **TC-FPA-001 — пройшов.** Адмін бачить кнопку на картці, архівує порожню точку; `active=false`, у «Активні» її немає, у «Всі» вона є.
- **TC-FPA-002 — заблокований середовищем.** `POST /api/v1/users` від адмінської сесії DEV повернув `403 Access Denied` при створенні комірника з рівно двома узгодженими ролями. Тест не видає додаткових прав. Право комірника на архівацію фактичним прогоном не підтверджене. Перевірка коду показує, що `business-unit::delete` мапиться на глобальне `locations.manage`, якого в «Керівник локації» немає.
- **TC-FPA-003 — дефект.** UI показує екіпаж як перший блокер і не дає фінального підтвердження. Прямий `DELETE /api/v1/storages/{pointId}` повернув `200` та архівував точку з активним екіпажем; очікували 4xx і `active=true`.
- **TC-FPA-004 — пройшов.** Адмін перемістив екіпаж на іншу активну точку того самого батальйону; зв’язок `parent` змінився, початкова точка успішно архівувалася.
- **TC-FPA-005 — дефект.** Справжня партія з унікальним номером і 7 одиниць створені на точці. Прямий DELETE точки за фізичного залишку відхилений 4xx. Попередження показало лише назву ресурсу і `7`, без одиниці `шт` і номера партії. Це суперечить погодженому переліку полів; резерв також не представлений у `close-prerequisites`.
- **TC-FPA-006 — частково пройшов.** Кнопки відкрили форми переміщення й надзвичайної події з `returnTo=/fly-points/close/{id}`. Збереження обох форм і фактичне повернення ще не автоматизовані.
- **TC-FPA-007 — пройшов.** Після відправлення всього фізичного запасу вантаж залишився в дорозі, `stocks` у `close-prerequisites` порожній, архівація пройшла. Це відповідає уточненню, що вантаж у дорозі не блокує сам по собі.
- **TC-FPA-009 — дефект для перевіреної частини.** Баланс прикріпленого екіпажу в чинній моделі обліковується на його точці. За наявності такого балансу прямий DELETE екіпажу повернув `200` замість 4xx. Активну операцію екіпажу та UI-повідомлення окремо не проганяли.
- **TC-FPA-010 — частково пройшов.** Коли є і екіпаж, і залишок, UI спочатку показав екіпаж; після його переміщення показав залишок і не дав архівувати точку. Завершення врегулювання залишку й фінальна архівація не входили до цього методу.
- **TC-FPA-011 — частково пройшов.** Скасування на сторінці архівації повернуло до `/fly-points`, точка лишилася активною. Скасування інших форм та помилки сабміту ще не автоматизовані.
- **TC-FPA-013 — дефект для перевіреної частини.** Після відкриття фінального підтвердження окремий API-запит створив активний екіпаж. Фінальний DELETE від UI усе одно повернув `200` замість 4xx; сервер не повторив перевірку блокерів. Конкурентний залишок і подвійний клік ще не автоматизовані.

`TC-FPA-008`, `012` і непокриті кроки `014` не проганялися. `TC-FPA-014` частково перевірений у `001` через фільтри списку. Ручне зняття резерву, серверне блокування за активною бронню, повні сабміти переміщення/події та чужий батальйон залишаються відкритими.

## Висновки для реалізації

1. Додати серверну перевірку активних екіпажів при архівації точки. `StorageValidator.validateDelete` зараз блокує фізичний залишок, але не дочірні активні екіпажі.
2. Заборонити архівацію екіпажу з пов’язаним балансом або активною операцією в UI **і** на сервері. Для прикріпленого екіпажу баланс проксується на точку; перевірка лише власного `StorageItem` екіпажу недостатня.
3. Розширити `GET /fly-points/{id}/close-prerequisites` і попередження: назва, одиниця, кількість, партія; резерв показувати окремо всередині фізичної кількості без подвоєння. Вантаж у дорозі не додавати до блокера.
4. Надати комірнику з «Керівник локації» та «Екіпажі: перегляд» можливість архівувати свою точку й переміщувати/архівувати екіпажі без додаткових грантів. Після відновлення створення тестових користувачів на DEV повторити `TC-FPA-002`.
