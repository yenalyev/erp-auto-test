# Dev прогін — синхронізація екіпажів Файти та позиція з ЖБД

Дата: 2026-09-30. Середовище: `dev.cukerochka.sbs`. Suite: `faita-crew-sync`. Прогін виконувався з `tcm.enabled=false`, `google.sheets.enabled=false` і Corretto 21; жодних source/ERP даних новий suite не створював.

## Результат

- Повний suite: **2 тести, 2 failure, 0 skipped**. Maven зібрав код і виконав API/UI тести.
- `TC-FAITA-SYNC-POS-API-001`: **FAIL**. `GET /api/v1/storages/inventory/write-off` повернув FLIGHT запис `id=375265` без ключа `positionName`. Це підтверджує відсутність нового поля в поточному API-контракті. Тест перевіряв перші 1000 найновіших списань.
- `TC-FAITA-SYNC-POS-UI-001`: **FAIL на відкритті журналу**. Після авторизації перехід на `/inventory-write-off` на dev перенаправляє браузер до `/production`. Колонку перевірити неможливо, доки журнал не відкривається для тестового ADMIN. Це не є доказом лише відсутності нової колонки. У коді `tk-ui` колонка «Позиція з ЖБД» також наразі відсутня.

Після першого suite UI тест повторено двічі для діагностики базової колонки; обидва рази замість журналу відображалося «Виробництво». Після цього тест уточнено перевіркою фактичного URL і весь read-only suite запущено повторно; наведені вище результати — фінальний прогін. Surefire: `target/surefire-reports`.

## Обмеження прогону

Dev профіль має `use.database=false`; окремий read-only прогін з `use.database=true` підтвердив успішний DB pre-flight, але не виконував мутацій. Немає керованих source рядків `imp.vw_cs_teams`, `imp.vw_cs_watch_schedule`, `imp.ammo_agg_v2` у звичайному suite. Тому цей прогін не перевіряв створення/оновлення team/storage, чотири гілки списання, stock delta, ідемпотентність та фактичне походження позиції від конкретної Fight події. Ці сценарії залишаються у [кейсах](../../FAITA_CREW_SYNC_TEST_CASES.md) як release gate.

Контрольований E2E тест із dev `/log` і `/syncTeams` підготовлено окремо. Початкову спробу запуску відхилила автоматична перевірка дозволів через можливий вплив загального `syncTeams` на сторонні дані. Користувач надав явний дозвіл 2026-10-01; результат дозволеного запуску наведено нижче.

`mvn test-compile` для підготовленого E2E тесту та всього проєкту завершився успішно. Жодного висновку про поведінку E2E тесту з компіляції не робимо.

## Дозволений E2E прогін — 2026-10-01

- Запуск: `faita-crew-sync-e2e`, `use.database=true`, `faita.sync.e2e.enabled=true`; **1 тест, 1 failure**.
- `POST /api/v1/integrations/faita/log` прийняв контрольований запис (`202`). `POST /api/v1/integrations/faita/syncTeams` повернув **500** з тілом `Something went wrong`. Тест зупинився до перевірки `position_name`, API, статусу та ідемпотентності. Причина 500 без серверного stack trace невідома.
- Адресний DB audit після запуску знайшов один тестовий flight log зі статусом `NEW` і нуль пов'язаних write-off. Початковий cleanup не видалив log через надто вузьку умову за timestamp; її замінено на унікальний маркер, team ID та ammunition ID/name.
- Одноразовий cleanup видалив **рівно один** власний `NEW` log після перевірки відсутності write-off. Фінальний read-only `TC-FAITA-SYNC-CLEANUP-001` пройшов: **0 log, 0 write-off** для маркера `erp-auto-test-faita-pos-633a0697-18e`.
- Загальний `syncTeams` міг обробити інші dev записи до повернення 500; цей тест не може довести відсутність таких змін. Повторний мутаційний запуск без діагнозу 500 не виконувався.

## Наступний крок для приймання

Реалізувати й розгорнути окремий snapshot позиції в backend/API/UI, забезпечити доступний журнал на dev, додати контрольовані source fixtures або backend integration tests для повного шляху. Повторити `mvn test -Denv=dev -Dsuite=faita-crew-sync -Dtcm.enabled=false -Dgoogle.sheets.enabled=false` і виконати P0 з перевіркою залишків.
