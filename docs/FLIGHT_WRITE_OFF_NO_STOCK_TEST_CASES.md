# Тест-кейси: списання ЖБД, статуси й відсутній залишок

Позначення: `S` — фактичний склад списання, `Q` — кількість у ЖБД, `R` — ізольований mapped ресурс. Для прив'язаного екіпажа `S=FLY_POINT`, для вільного `S=CREW`. Кожен кейс використовує унікальний `sourceId` і знімає залишки до/після. Уточнений контракт: за нульового залишку запис списання **не створюється**.

## TC-FLIGHT-NOSTOCK-001 — нульовий залишок

**P0; автоматизовано.** Передумови: mapped `R`, `stock(S,R)=0`, унікальна source подія ЖБД з `amount=Q=1`; dev `syncTeams` увімкнений. Сіяти source log, викликати sync, прочитати його стан, DB/API журнал і stock. Очікування: source подія оброблена, у журналі немає рядка для її `sourceId`/resource ID, залишок 0. Якщо source log лишається `NEW`, передумова sync не виконана. **Поточний backend-код створює рядок; тест має виявити розбіжність, коли sync доступний.**

## TC-FLIGHT-STATUS-002 — явне відхилення

**P1; автоматизовано.** Передумови: `PENDING` FLIGHT рядок, `stock(S,R)=0`. Виконати `PUT /write-off/reject`, прочитати рядок і залишки. Очікування: HTTP 200, статус `REJECTED_USER`, stock без змін. Лічильник `skipped` у dashboard перевіряти окремо: його поточний SQL використовує інше значення `REJECTED`.

## TC-FLIGHT-003 — точний залишок

**P0; заплановано E2E.** Передумови: екіпаж на точці, `stock(FLY_POINT,R)=Q`, `stock(CREW,R)=0`. Додати одну ЖБД подію, виконати sync та auto-complete. Очікування: один рядок для `sourceId`, terminal success, `stock(FLY_POINT,R)=0`, CREW незмінний, одна операція в history на FLY_POINT.

## TC-FLIGHT-004 — ресурс лише на екіпажі

**P0; заплановано E2E.** Передумови: екіпаж на точці, `stock(FLY_POINT,R)=0`, `stock(CREW,R)>=Q`. Імпортувати ЖБД подію. Очікування: запис списання не створюється, CREW не використовується як непомітний fallback, обидва склади незмінні. Якщо alternative storage заданий подією, перевіряти погоджений пріоритет окремим варіантом.

## TC-FLIGHT-005 — недостатній залишок

**P0; заплановано E2E.** Передумови: `stock(S,R)=Q-1`, `Q>1`. Імпортувати подію та обробити. Очікування: stock лишається `Q-1`, немає операції в history. Чи має створюватися рядок при частковому залишку — потребує уточнення.

## TC-FLIGHT-006 — надходження після очікування

**P1; заплановано E2E.** Після пропущеної через нульовий залишок події поповнити `S` до `Q` і повторити sync. Потрібно уточнити, чи подія має обробитися після надходження; у будь-якому разі дублікати неприпустимі.

## TC-FLIGHT-007 — відсутнє зіставлення

**P1; заплановано E2E.** Імпортувати ЖБД ресурс без ERP mapping при достатньому stock схожого ресурсу. Очікування: немає випадкового дебету; row/status відповідають правилу unmapped; після додавання mapping повторна обробка списує лише правильний ERP ресурс.

## TC-FLIGHT-008 — змішаний набір одного event

**P1; заплановано E2E.** Подія містить основний ресурс, ініціатор і implicit ресурс. Для двох є stock, для третього — 0. Після sync перевірити всі рядки з тим самим `sourceId`, їхні `externalResourceId`, `amount`, статус і незалежні дельти; повторний sync не додає дублів. Погодити, чи потрібна атомарність усього набору або кожного рядка.

## TC-FLIGHT-009 — журнал і статистика

**P1; заплановано API/UI.** Підготувати рядки кожного погодженого статусу. Перевірити фільтр status, badge у `/inventory-write-off`, `stats-by-status`, short stats і dashboard для того самого scope/date. Очікування: однакові назви та кількості; `REJECTED_USER` не плутається з автоматичним no-stock станом.
