# REQ-PLAN-ANL-SUPPLIER — Аналітика для плану: фільтр «Постачальник»

Статус: **контракт зафіксовано; QA-покриття автоматизовано**

Сторінка: `/analytics/plan` → «Аналітика» → «Для плану»

Батьківська вимога TCM: `REQ-PLAN-ANL`

Модуль TCM: `PLAN`

## 1. Мета і межі

Фільтр «Постачальник» звужує аналітичні рядки до ресурсів, у яких поточне значення властивості з точною назвою `Постачальник` збігається з одним із вибраних значень.

Ця вимога документує і покриває тестами уже наявну функціональність. Вона не змінює frontend, backend, endpoint definitions, JSON-схеми чи бізнес-контракти.

Поза обсягом:

- історичне значення властивості на дату операції;
- фактичний постачальник партії або локація типу `SUPPLIER`;
- зміна формул `produced`, `relocated`, `used`, `stockTotal`, `stockInRoot`;
- `/analytics/plan/stock/{resourceId}`;
- блок аналітики глобального плану.

## 2. Фактичний контракт

### Джерело опцій

UI читає унікальні значення з `category_property_options["Постачальник"]` (у JavaScript-моделі — `categoryPropertyOptions["Постачальник"]`). Порожнє значення не є окремою опцією. Селектор підтримує пошук і кілька значень.

### Rows API

Вибір передається текстовим query-параметром `supplier`. Для multi-select параметр повторюється:

```text
GET /api/v1/analytics/plan/rows?resourceIds=101&fromDate=2026-08-01&toDate=2026-08-31&supplier=МОУ&supplier=Інші
```

- усередині групи `supplier` значення комбінуються через `OR`;
- група постачальників комбінується з `resourceIds`, `categoryIds` і періодом через `AND`;
- порівняння виконується з актуальним точним значенням властивості ресурсу;
- без вибраного постачальника `supplier` у query відсутній;
- response contract `content`, `page`, `totals` не змінюється.

Сам supplier-фільтр не формує цільову вибірку: без `resourceIds` або `categoryIds` UI не викликає rows API.

## 3. Acceptance criteria

### AC-01 — опції та multi-select

- Фільтр «Постачальник» доступний на `/analytics/plan`.
- Опції походять із `category_property_options["Постачальник"]`, унікальні та не містять порожнього значення.
- Пошук звужує список опцій.
- Один варіант не може бути вибраний двічі.

### AC-02 — семантика фільтрації

- Один `supplier` залишає лише ресурси з точним актуальним значенням.
- Повторювані `supplier` працюють як `OR`.
- Ресурс без властивості «Постачальник» не входить у відфільтровану вибірку.
- Після зміни властивості ресурсу використовується нове значення; старе більше не збігається.

### AC-03 — перетин з іншими критеріями

- Supplier-група лише додатково звужує вибірку через `AND` з `resourceIds`, `categoryIds` і періодом.
- Зміна періоду не скидає supplier у межах поточного стану сторінки.
- Вибір supplier без ресурсу або категорії не викликає rows API; після вибору цілі наступний запит містить раніше вибрані значення.

### AC-04 — підсумки й пагінація

- `content` містить лише рядки, що пройшли supplier-фільтр.
- `page.totalElements` і `page.totalPages` відповідають усій відфільтрованій вибірці.
- `totals` враховують усі відфільтровані рядки, а не лише поточну сторінку, і зберігають групування за одиницею.

### AC-05 — очищення і persistence

- Очищення прибирає всі `supplier` із наступного rows-запиту.
- Після очищення діють решта активних критеріїв.
- Reload і повторне відкриття `/analytics/plan` не відновлюють supplier-вибір з URL, local storage або іншого persistence.

### AC-06 — стабільність контракту

- Multi-select кодується повторюваним параметром `supplier=A&supplier=B`.
- URL-кодування зберігає кирилицю та пробіли значень.
- Supplier-фільтр не змінює форму rows-response і не потребує окремої JSON-схеми.

## 4. Автоматизовані тестові дані

`PlanAnalyticApiTest` створює в одній категорії та з однаковою одиницею три ізольовані ресурси:

- A: `Постачальник = МОУ`;
- B: `Постачальник = Інші`;
- C: властивість відсутня.

Для кожного ресурсу створюється ненульовий залишок у доступній локації. Назви ресурсів мають унікальний суфікс запуску. UI-тести використовують контрольовані rows-відповіді для стабільної перевірки відображення, але аналізують реальний URL запиту, сформований frontend.

## 5. Автоматизовані тест-кейси

### TC-PLAN-ANL-005 — один постачальник

Запит із `supplier=МОУ` повертає A, виключає B і C та проходить чинну JSON-схему.

### TC-PLAN-ANL-006 — supplier OR, зовнішній AND

Повторювані `supplier=МОУ&supplier=Інші` повертають A і B. Додавання `resourceIds`, `categoryIds` і періоду звужує результат як `AND`.

### TC-PLAN-ANL-007 — лише актуальна властивість

Після PUT ресурсу A зі значення `МОУ` на `Інші` нове значення збігається, а старе — ні. Історичне значення не використовується.

### TC-PLAN-ANL-008 — ресурс без властивості, totals і pagination

C виключений. За малого `size` `totalElements`, `totalPages` і `totals` описують всю відфільтровану вибірку, а не одну сторінку.

### TC-PLAN-ANL-UI-004 — опції, пошук, query і результат

Опції унікальні, пошук працює, один і два вибрані постачальники формують відповідно один і два повторювані `supplier` та показують контрольовані рядки.

### TC-PLAN-ANL-UI-005 — період, очищення і відсутність persistence

Зміна періоду зберігає supplier у поточному стані. Очищення прибирає параметр. Reload і повторне відкриття сторінки не відновлюють вибір.

### TC-PLAN-ANL-UI-006 — supplier не є ціллю вибірки

Вибір supplier без ресурсу або категорії не викликає rows API. Після вибору ресурсу запит містить раніше вибраних постачальників.
