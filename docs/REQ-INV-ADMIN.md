# REQ-INV-ADMIN — Інвентаризація для адміна

## Вимога

Для користувачів із правами **Адміністратор** та **Адміністратор: перегляд** у робочому просторі **Всі локації** сайдбар показує розділ **Інвентаризація**. На вкладці запитів доступні всі запити на проведення інвентаризації з усіх локацій, включно з дочірніми й незалежними гілками дерева.

Для **Адміністратора** таблиця запитів залишається **глобальною незалежно від вибраної локації в сайдбарі**. Після вибору конкретної локації адміністратор і далі бачить усі запити з усіх локацій, включно з незалежними гілками. Це погоджена вимога від 27.10.2026. Для ролі **Адміністратор: перегляд** зберігається поточна поведінка: конкретна локація обмежує список цією локацією та її дочірніми, «Всі локації» показує глобальний список.

Це перегляд журналу `/inventory-processes`. Створення запиту, погодження, відхилення й проведення інвентаризації мають окремі права та сценарії в батьківській вимозі `REQ-WMS-003`. Ця вимога не надає ролі перегляду права зміни даних.

Адміністратор у фікстурі має системні ролі «Адміністратор системи» та «Повний доступ» зі scope ALL. Другий користувач має тільки системну роль «Адміністратор: перегляд» зі scope ALL, без додаткових дозволів на оновлення. Використовуються нові користувачі; існуючі права користувачів не змінюються.

## Критерії приймання

- **AC-01:** Обидві ролі бачать у сайдбарі «Інвентаризація» після вибору «Всі локації» та переходять до доступної сторінки запитів.
- **AC-02:** У просторі «Всі локації» обидві ролі отримують і бачать усі REQUESTED-процеси з усіх локацій; для Адміністратора цей глобальний список зберігається також при виборі конкретної локації. Пагінація не губить і не дублює рядки, OPEN/REJECTED не потрапляють до запитів; локація та причина запиту відповідають API.
- **AC-03:** Під час перемикання «Всі локації → конкретна локація → Всі локації» Адміністратор на всіх етапах бачить глобальний список, зокрема після перезавантаження. Адміністратор: перегляд на конкретній локації бачить її запити та запити дочірніх локацій, а після повернення до «Всі локації» і перезавантаження — глобальний список без застарілого фільтра. Перегляд не змінює процеси й залишки.

## Контракт і дані

Фронтенд: `tk-ui/src/components/layout/sidebarItems.ts`, `components/app-sidebar.tsx`, `pages/inventory/InventoryProcessesPage.tsx`, `api/inventoryProcess.ts`.

GET `/api/v1/storages/inventory/processes?states=REQUESTED&page=0&size=...` у глобальному просторі не передає `parentStorageId`. Для Адміністратора запити журналу залишаються без `parentStorageId` також після вибору конкретної локації. Для ролі «Адміністратор: перегляд» при виборі конкретної локації параметр дорівнює її ID. Явний API-запит із `parentStorageId` фільтрує за локацією та дочірніми; це не означає, що UI адміністратора має застосовувати цей фільтр. Відповідь містить `content` і `page.totalPages/totalElements`.

Фікстура створює п'ять порожніх локацій: A, дочірню B, незалежну C та два контрольні об'єкти. A/B/C мають REQUESTED; контролі — OPEN та REJECTED. Усі створені ID відстежуються. Перевірка API використовує сторінки по 2 рядки та порівнює точний набір з повним списком ADMIN; UI проходить усі сторінки реальної таблиці. Глобальний baseline включає також існуючі запити dev, але тести їх не змінюють. Паралельна зміна чужих запитів під час порівняння може потребувати повтору; порівняння не послаблюється до перевірки лише власних трьох рядків.

Назви локацій у рядках UI порівнюються з GET журналу: POST створення запиту на dev може містити лише ID локації без назви. Для Адміністратора на кожному етапі перемикання очікується точний глобальний набір ID; повторний запит при незмінній глобальній вибірці не є обов'язковим. Для ролі перегляду при виборі конкретної локації очікується GET з її `parentStorageId`, завершення відповіді та оновлення рядків ізольованої гілки в React; після повернення до «Всі локації» — запит без цього параметра та глобальний набір ID.

Після перевірок контролюються початкові стани всіх п'яти процесів і порожні залишки. Cleanup завершує власні REQUESTED/OPEN, архівує лише власні локації спочатку дочірні, потім батьківські, деактивує власних користувачів. Повторне читання перевіряє active=false та enabled=false. JDBC/SSH не потрібні.

## Автоматизовані тест-кейси

Передумови для всіх кейсів: ERP dev доступний; Chrome встановлений; фікстура створила зазначені п'ять процесів та двох користувачів. Перегляд виконується з фактичною сесією відповідної ролі.

### TC-INV-ADMIN-API-001 — Адміністратор отримує всі сторінки запитів [AC-02]

Автотест: `InventoryAdminUiTest#adminReadsAllRequestedPages`

1. Отримати повний REQUESTED baseline через адміністративну сесію без parentStorageId.
2. У сесії нового адміністратора пройти всі сторінки по 2 рядки з states=REQUESTED, sort=id,asc.
3. Порівняти точні ID та totalElements; перевірити три власні запити, стани контролів і залишки.

Очікування: HTTP 200; глобальні ID точно збігаються, без дублів або втрат; A/B/C присутні, OPEN/REJECTED виключені; власні дані незмінні.

### TC-INV-ADMIN-API-002 — Адміністратор перегляд отримує всі сторінки запитів [AC-02]

Автотест: `InventoryAdminUiTest#viewerReadsAllRequestedPages`

1. Отримати повний REQUESTED baseline через адміністративну сесію.
2. У сесії користувача лише з «Адміністратор: перегляд» пройти всі сторінки по 2 рядки без parentStorageId.
3. Порівняти точні ID та totalElements; перевірити три власні запити й незмінність даних.

Очікування: HTTP 200; роль перегляду отримує той самий глобальний REQUESTED-список без сторонніх станів, дублів і побічних змін.

### TC-INV-ADMIN-UI-001 — Адміністратор бачить розділ у всіх локаціях [AC-01]

Автотест: `InventoryAdminUiTest#adminSeesSidebarAtAllLocations`

1. Відкрити застосунок у сесії нового адміністратора з конкретною локацією.
2. Через реальний селектор сайдбара обрати «Всі локації».
3. Перевірити вибір глобального простору та пункт «Інвентаризація», натиснути його та дочекатися вкладки запитів.

Очікування: пункт видимий; відкрито /inventory-processes зі вкладкою запитів; власні процеси та залишки незмінні.

### TC-INV-ADMIN-UI-002 — Адміністратор перегляд бачить розділ у всіх локаціях [AC-01]

Автотест: `InventoryAdminUiTest#viewerSeesSidebarAtAllLocations`

1. Увійти користувачем лише з «Адміністратор: перегляд».
2. Через селектор сайдбара обрати «Всі локації» та перевірити пункт «Інвентаризація».
3. Натиснути пункт і дочекатися сторінки запитів.

Очікування: розділ видимий та доступний за правом перегляду; відсутність права оновлення не приховує журнал; власні дані незмінні.

### TC-INV-ADMIN-UI-003 — Адміністратор бачить усі рядки запитів [AC-02]

Автотест: `InventoryAdminUiTest#adminSeesAllRequestRows`

1. Вибрати «Всі локації» в сесії нового адміністратора й відкрити журнал.
2. Пройти реальні сторінки вкладки запитів кнопкою «Наступна» та зібрати ID й тексти рядків.
3. Порівняти всі ID з API baseline; для власних запитів перевірити локацію і причину; перевірити незмінність даних.

Очікування: таблиця містить точний глобальний REQUESTED-список; власні A/B/C видимі з правильними назвами та причинами; OPEN/REJECTED виключені.

### TC-INV-ADMIN-UI-004 — Адміністратор перегляд бачить усі рядки запитів [AC-02]

Автотест: `InventoryAdminUiTest#viewerSeesAllRequestRows`

1. Вибрати «Всі локації» користувачем «Адміністратор: перегляд» і відкрити журнал.
2. Пройти всі сторінки таблиці та зібрати ID і тексти рядків.
3. Звірити повний набір з API адміністратора; перевірити власні назви, причини й незмінність даних.

Очікування: роль перегляду бачить ті самі запити всіх гілок без пропусків, дублів або чужих станів; власні дані незмінні.

### TC-INV-ADMIN-UI-005 — Адміністратор зберігає глобальний список після вибору локації [AC-03]

Автотест: `InventoryAdminUiTest#adminRestoresAllLocationsAfterSwitch`

1. Відкрити журнал у просторі «Всі локації» від нового адміністратора.
2. Вибрати A та перевірити фактичний вибір у сайдбарі; порівняти всі рядки таблиці з глобальним API baseline без parentStorageId, включно з незалежною C.
3. Перезавантажити сторінку зі збереженим вибором A й повторити глобальне порівняння; повернути «Всі локації», перезавантажити й знову перевірити той самий повний список.

Очікування: вибір A у сайдбарі не звужує таблицю адміністратора; A/B/C та інші глобальні REQUESTED-запити залишаються видимими на всіх етапах і після reload, без пропусків, дублів або побічних змін.

Зміна специфікації від 27.10.2026: глобальна таблиця після вибору A прийнята як вимога. Попереднє очікування GET з `parentStorageId=A` для адміністратора скасовано. Java-реалізація цього автотесту ще перевіряє попередній контракт і потребує окремого узгодження з новими кроками; оновлення документації не є повторним виконанням тесту.

### TC-INV-ADMIN-UI-006 — Адміністратор перегляд відновлює глобальний список [AC-03]

Автотест: `InventoryAdminUiTest#viewerRestoresAllLocationsAfterSwitch`

1. Відкрити журнал у просторі «Всі локації» від «Адміністратор: перегляд».
2. Через селектор вибрати A й порівняти таблицю з API-фільтром A та дочірніх локацій.
3. Повернути «Всі локації», перезавантажити сторінку та звірити всі рядки з глобальним API baseline.

Очікування: роль перегляду має доступ під час обох переходів; глобальний список відновлено без застарілого parentStorageId; дані незмінні.

## Запуск і результати

`powershell -ExecutionPolicy Bypass -File scripts/run_inventory_admin_dev.ps1`

Або `mvn test -Denv=dev -Dsuite=inventory-admin -Duse.database=false -Dssh.enabled=false -Dframework.browser.channel=chrome`.

8 окремих automation IDs: 2 API + 6 UI; клас входить до inventory, ui, regression та окремого inventory-admin. Скріншоти ключових кроків і завершення додаються в Allure. Актуальний результат dev зберігається в `docs/audits/2026-10-27/inventory-admin-dev-report.md`; документація вимоги сама по собі не означає PASS.

### Перевірка dev 27.10.2026

Прогін `inventory-admin-dev-20261027-final`: **7 PASS / 1 FAIL / 0 SKIP**; configuration/cleanup failures — **0**. Обидві ролі бачать розділ у просторі «Всі локації», відкривають журнал і бачать точний глобальний REQUESTED-список. API-пагінація обох ролей проходить. Попередня проблема відсутнього розділу від 24.10 на поточному dev не відтворюється.

Framework-прогін `inventory-admin-framework-20261027-verified`: **112 PASS / 0 FAIL / 0 SKIP**, `BUILD SUCCESS`; зокрема `RegressionSuiteCompletenessTest` підтверджує склад regression suite. Sandbox-прогін framework було зупинено після зависання локальних інфраструктурних перевірок; фінальне виконання поза sandbox завершене успішно.

`TC-INV-ADMIN-UI-005` у цьому історичному прогоні впав через попереднє очікування локального списку й відповіді з `parentStorageId=A`. На скріншоті за вибраної A таблиця містить глобальні запити, включно з незалежною C. Після погодження вимоги 27.10.2026 така поведінка є очікуваною і не класифікується як дефект. Збережений результат прогону залишається **7 PASS / 1 FAIL**: нові кроки та reload зі збереженою A ще не виконувалися. `TC-INV-ADMIN-UI-006` для ролі перегляду пройшов, включно з поверненням до глобального списку й reload.

Виправлено дві проблеми автотестів: назви локацій беруться з GET журналу замість неповної POST-відповіді; очікування перемикання перевіряє точний `parentStorageId`, завершення відповіді та рендер рядків. Перша sandbox-спроба зупинилася на DNS до створення даних; окремий початковий dev-прогін збережений для аудиту й не змішується з фінальними результатами.

П'ять власних локацій архівовано й двох користувачів деактивовано; значення перевірені повторним GET. Фінальні результати імпортовано в [TCM prod, run 175](http://tcm.lab/test-runs/175) і [TCM stage, run 236](http://localhost:18100/test-runs/236): 8/8 automation IDs зіставлені, unmatched/outOfScope порожні. Це виконання ERP dev, опубліковане в обох TCM.

### Перевірка dev 24.10.2026

Фінальний прогін `inventory-admin-dev-verified-20261024`: **2 PASS / 6 FAIL / 0 SKIP**; configuration/cleanup failures — **0**. Локальний `framework` — **100 PASS / 0 FAIL / 0 SKIP**, зокрема перевірка включення класів до regression.

API обох ролей повертає повний REQUESTED-список без втрат на межі сторінок. У UI обидві ролі не бачать «Інвентаризація» у глобальному просторі. Прямий перехід на `/inventory-processes` не показує сторінку запитів: для адміністратора видно іншу сторінку застосунку, для ролі перегляду доступ також відхилено. Два UI-кейси видимості падають на відсутньому пункті; чотири кейси списку/перемикання падають на початковій навігації, тому подальшу UI-пагінацію й повернення фільтра на dev ще не підтверджено. Очікування не послаблено до поточної помилкової поведінки.

Технічна підказка: у `sidebarItems.ts` пункт і відповідний route guard спираються на `inventory-status::update`, а не тільки на право читання журналу; `useLocationScopedPermission` додатково перевіряє scope вибраних локацій. Це напрямок перевірки причини, а не підтвердження єдиного джерела дефекту. Backend/frontend не змінювалися.

Власні локації фінального прогону архівовано в порядку «дочірні → батьківські», власних користувачів деактивовано; значення перевірено через GET. Окреме відновлення підтвердило архівацію всіх 10 локацій попередніх спроб. Початкові результати та помилка порядку cleanup збережені в аудиті й не підраховуються повторно.

Фактичні dev-результати імпортовано в [TCM prod, run 167](http://tcm.lab/test-runs/167) та [TCM stage, run 228](http://localhost:18100/test-runs/228): усі 8 automation IDs зіставлені, unmatched/outOfScope порожні; статуси підтверджено повторним читанням. Це результати ERP dev, збережені в обох TCM.
