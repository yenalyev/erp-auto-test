# Тест-план: бухгалтерська назва та вартість партії ресурсу

Документація нової функціональності для продукту, QA та автоматизації.
Функціональний контур: ресурсні переміщення, форма зовнішнього отримання
`/relocation/create-input` та API створення отримання.
TCM: **REQ-EDIT_REL-008** (модуль `EDIT_REL`, батько `REQ-EDIT_REL`).

Статус: **правило нормалізованої унікальності збережено; порушення в API/UI
зафіксовано автотестами як відкриті баги**.

---

## 1. Мета зміни

Під час отримання ресурсу користувач може вказати для його партії два додаткові
опціональні атрибути:

- **бухгалтерська назва**;
- **вартість (сума)**.

Один ресурс можна внести в одне отримання кількома рядками, якщо бухгалтерські
назви різні після обрізання крайніх пробілів і зміни регістру. Комбінація має
бути унікальною в межах ключа:

`переміщення + ресурс + бухгалтерська назва`.

Приклад очікуваного валідного отримання:

- ресурс «Кабель», бухгалтерська назва «Кабель силовий», кількість 10, сума 1 200,00;
- той самий ресурс «Кабель», бухгалтерська назва «Комплект кабельний», кількість 5,
  сума 900,00.

Це два окремі рядки/партії одного ресурсу в одному переміщенні. Буквально
однакова непорожня назва, назви, що збігаються після нормалізації, і кілька
безіменних рядків того самого ресурсу є дублікатами.

---

## 2. Межі функціональності

### У scope

- UI форми отримання ресурсу від зовнішнього постачальника;
- створення отримання через `POST /api/v1/relocations/receive`;
- збереження нових атрибутів на рівні партії;
- відповідь API після створення отримання;
- розрахунок і відображення верхнього поля «Сплачена сума» у формі отримання;
- складські залишки після одного й кількох рядків одного ресурсу;
- атомарність і унікальність даних.

### Поза scope, доки немає окремої вимоги

- отримання обладнання;
- повернення від екіпажа (`/relocation/create-input-crew`);
- приймання внутрішньої видачі з вкладки «В дорозі»;
- виробництво та партії виробничих записів;
- глобальний довідник цін ресурсів `/resources-price`;
- перерахунок вартості за курсом або робота з кількома валютами.
- редагування вартості вже створеного отримання; надалі воно має з'явитися в
  кабінеті бухгалтера;
- відображення бухгалтерської суми в залишках та нових атрибутів у журналі,
  експорті й накладній; надалі вони мають використовуватися в кабінеті бухгалтера.

Ці сценарії входять до регресії лише для перевірки, що нові поля не стали для них
неочікувано обов'язковими та не змінили чинну поведінку.

## 3. Функціональні правила для приймання

Підтверджені постановкою правила:

1. Поля «Бухгалтерська назва» і «Сума» доступні для кожного рядка/партії ресурсу
   у формі отримання та є опціональними незалежно одне від одного.
2. В одному отриманні дозволено повторно додати той самий ресурс, якщо в рядках
   різні бухгалтерські назви після нормалізації.
3. У межах одного переміщення комбінація `resourceId + normalizedAccountingName`
   унікальна; назва нормалізується через `trim` і зміну регістру на нижній.
4. Нові значення належать партії, а не картці ресурсу та не переміщенню загалом.
5. `batchNumber` залишається окремим атрибутом партії та не входить до ключа
   унікальності. Інший номер партії не дозволяє повторити ту саму
   нормалізовану бухгалтерську назву для того самого ресурсу.
6. «Сума» — уже підрахована повна вартість позиції номенклатури, а не ціна за
   одиницю. Під час обчислення підсумку її не множать на кількість.
7. Сума має бути `0` або більше й не більше двох знаків після коми. UI обмежує
   введення двома десятковими знаками (наприклад, після введення `1.234` у полі
   лишається `1.23`); прямий API-запит із більшою точністю відхиляється з `400`.
   Підтвердження форми після приведення введення до двох знаків залишається доступним.
8. Для бухгалтерської назви немає бізнес-обмеження довжини або набору символів.
   Назви `Назва`, `назва` і ` Назва ` утворюють один ключ. Порожня або відсутня
   назва після нормалізації утворює одне порожнє значення для того самого ресурсу.
9. Коли заповнена хоча б одна сума рядка, вгорі форми з'являється поле
   «Сплачена сума» із сумою всіх заповнених значень. Окремого блоку «Загальна
   вартість» немає. Порожні суми ігноруються; якщо всі суми порожні, поле не
   показується. Явно введений `0.00` показує `0,00`. Верхнє поле використовує
   кому як видимий десятковий роздільник і завжди показує два знаки після коми.
   Числовий `input` у DOM повертає значення з крапкою (`inputValue()` → `0.00`).
10. Бухгалтерська назва відображається в переліку партій ресурсу в залишках.
    Бухгалтерська сума там не показується. У журналі, експорті та накладній нові
    атрибути поки не відображаються; редагування планується в кабінеті бухгалтера.

Правила, які має однаково забезпечувати UI і backend:

- UI показує помилку для дубля нормалізованої назви того самого ресурсу та не
  підтверджує форму;
- прямий API-запит із таким дублікатом має бути відхилений з `400`;
- два рядки одного ресурсу без бухгалтерської назви також є дублікатом;
- помилка одного рядка не повинна частково зараховувати інші рядки отримання;
- загальний залишок ресурсу збільшується на суму кількостей усіх його валідних
  бухгалтерських рядків; бухгалтерська сума не змінює фізичну кількість;
- два різні ресурси можуть мати однакову бухгалтерську назву;
- той самий ресурс і та сама бухгалтерська назва можуть повторюватися в різних
  переміщеннях.

---

## 4. Поведінка після створення

Поточна зміна покриває введення бухгалтерських атрибутів під час створення
отримання. Після збереження бухгалтерська назва видима в переліку партій ресурсу
у залишках. Якщо під час редагування отримання задано іншу бухгалтерську назву
партії, після збереження перелік партій має показувати нову назву. У журналі
бухгалтерські поля не показуються; редагування вартості планується в майбутньому
кабінеті бухгалтера.

Водночас чинне редагування інших даних отримання через
`PUT /api/v1/relocations/{id}/receive?storageId=` не повинно очищати або змінювати
раніше збережені бухгалтерські атрибути, навіть якщо їх немає в update payload.

## 5. Тестові дані та передумови

Потрібні:

- користувач із правом створювати отримання для конкретного складу;
- зовнішній постачальник;
- два активні ресурси `R1` і `R2` з однаковою одиницею вимірювання;
- ресурс `R3` з дробовою одиницею вимірювання, якщо система це підтримує;
- унікальні номер накладної та номер партії для кожного сценарію;
- можливість прочитати переміщення через API та перевірити складський залишок;
- для конкурентного тесту — два паралельні запити з однаковою версією/ключем.

Базовий набір значень:

- бухгалтерські назви: `Кабель силовий`, `Комплект кабельний`, `кабель силовий`,
  ` Кабель силовий `, `Кабель/силовий №1`;
- кількості: `10`, `5`, `0.5`;
- суми: `1200.00`, `900.00`, `0`, `0.10`, `-1`, `0.001` та дуже велике додатне
  значення.

## 6. Основні тестові сценарії

### P0 — критичний бізнес-потік

#### TC-REL-ACC-001 — Один ресурс, одна бухгалтерська назва

Створити отримання `R1`, заповнити кількість, бухгалтерську назву та суму.

Очікування:

- отримання успішно створене;
- відповідь API містить точні значення нових атрибутів у потрібній партії;
- залишок `R1` збільшився на введену кількість;
- верхнє поле «Сплачена сума» показує `1200,00`;
- після збереження API повертає значення без втрати точності.

#### TC-REL-ACC-002 — Один ресурс, дві різні бухгалтерські назви

Додати в одне отримання два рядки `R1`: `Кабель силовий` і
`Комплект кабельний`, з різними кількостями та сумами.

Очікування:

- обидва рядки можна ввести й підтвердити;
- створено дві окремі партії з правильними парами назва/кількість/сума;
- `R1` не дублюється як два незалежні підсумкові ресурси, якщо контракт агрегує
  items за ресурсом;
- фізичний залишок `R1` збільшився на суму кількостей обох рядків;
- значення одного рядка не підмінили значення іншого;
- поле «Сплачена сума» дорівнює сумі вартостей двох рядків.

#### TC-REL-ACC-003 — Дубль ресурсу та бухгалтерської назви

Додати два рядки `R1` з буквально однаковою непорожньою бухгалтерською назвою,
зокрема з різними `batchNumber`.

Очікування:

- UI показує помилку, не дозволяє підтвердити форму та чітко позначає конфліктний
  рядок;
- прямий API-запит отримує узгоджену validation-відповідь;
- переміщення та жодна з його партій не створені;
- залишок не змінився.

#### TC-REL-ACC-004 — Одна назва для різних ресурсів

Створити рядки `R1` і `R2` з однаковою бухгалтерською назвою.

Очікування: отримання успішне, оскільки `resourceId` є частиною унікального ключа;
обидва залишки та партії збережені правильно.

#### TC-REL-ACC-005 — Одна комбінація в різних переміщеннях

Створити два отримання з однаковими `R1 + accountingName`.

Очікування: обидва успішні, оскільки `relocationId` є частиною ключа; залишок
збільшився на суму кількостей двох переміщень.

#### TC-REL-ACC-006 — Опціональні поля

Окремо створити отримання з такими варіантами рядка: обидва поля порожні, лише
бухгалтерська назва, лише сума, обидва поля заповнені.

Очікування: усі чотири варіанти валідні; відсутні значення передаються як
відсутнє поле або `null` згідно з API-контрактом; фізичний залишок у всіх випадках
збільшується на кількість ресурсу.

#### TC-REL-ACC-007 — Дубль порожньої бухгалтерської назви

Додати в одне отримання два рядки `R1` без бухгалтерської назви, у тому числі
варіант `null` і рядок лише з пробілів.

Очікування: кожний окремий безіменний рядок допустимий, але два такі рядки
того самого ресурсу в одному отриманні є дублікатом. API повертає `400` без
зміни залишку. UI має блокувати такий дубль; окреме UI-підтвердження потребує
передумови без автоматично вибраної назви в селекторі.

#### TC-REL-ACC-008 — Видалення отримання з кількома бухгалтерськими рядками

Видалити дозволене зовнішнє отримання.

Очікування: усі його партії видалені/деактивовані згідно з чинною моделлю,
загальна кількість повністю списана із залишку, чужі партії не змінені.

#### TC-REL-ACC-009 — Атомарність multi-resource запиту

Надіслати валідні рядки `R1` і невалідний/дубльований рядок `R2` одним запитом.

Очікування: весь запит відхилений; немає relocation, партій або часткової зміни
залишків.

#### TC-REL-ACC-010 — Сума є повною вартістю, не ціною одиниці

Додати `R1` у кількості `10` із сумою `1200.00`, а `R2` у кількості `2` із сумою
`300.00`.

Очікування: поле «Сплачена сума» показує `1500,00`; введені суми вже є повними
вартостями позицій, тому система не множить їх на кількість ресурсу.

### P1 — валідація і контракт

#### TC-REL-ACC-011 — Null, відсутнє поле і пробіли

Перевірити відсутнє поле, `null`, порожній рядок і рядок лише з пробілів для назви;
відсутнє поле та `null` для суми.

Очікування: усі варіанти дозволені окремо; для перевірки дубля назва
порівнюється після `trim` і зміни регістру, а пробільна назва еквівалентна
порожній; поле
«Сплачена сума» не показується, якщо в усіх рядках сума відсутня.

#### TC-REL-ACC-012 — Межі суми

Перевірити `0`, ціле число, один і два знаки після коми, від'ємне значення, три
знаки після коми та дуже велике додатне значення.

Очікування: `0` і додатні значення з точністю до двох знаків валідні. UI
обмежує введення двома знаками: `1.234` відображається в рядку як `1.23`, а
підтвердження залишається доступним. Спосіб округлення для інших значень
окремо не визначено. Прямі API-запити з від'ємною сумою або більш ніж двома
знаками відхиляються з `400`; після відмови дані та залишки незмінні.

#### TC-REL-ACC-013 — Межі бухгалтерської назви

Перевірити 1 символ, довгі рядки, кирилицю, латиницю, цифри, апостроф, дефіс,
переноси, лапки та HTML/JS-подібний текст.

Очікування: UI не встановлює бізнес-ліміт довжини або набору символів, значення не
обрізається і не спотворюється; під час відображення текст екранується і не
виконується як markup/script.

#### TC-REL-ACC-014 — Нормалізація унікальності

Перевірити пари `Назва` / `назва` та `Назва` / ` Назва `.

Очікування: обидві пари є дублікатами; UI показує помилку, API повертає `400`
і не змінює залишок.

Окремо перевірити однакові `resourceId + accountingName` з різними `batchNumber`:
це також дублікат, бо номер партії не входить до ключа унікальності.

#### TC-REL-ACC-015 — Узгодженість item amount і batches

Прямим API надіслати `item.amount`, що не дорівнює сумі `batches[].amount`.

Очікування: чинний інваріант кількості збережено; запит відхилений атомарно або
сервер однозначно обчислює total за документованим правилом.

#### TC-REL-ACC-016 — Контракт create/read і збереження після звичайного edit

Перевірити JSON schema та типи нових полів у request/response, серіалізацію
десяткової суми без втрати точності, стабільність назв полів і повернення значень
після POST та подальшого GET. Після цього змінити через чинний PUT лише дозволене
небухгалтерське поле отримання.

Очікування: якщо бухгалтерську назву не змінювали, вона і сума залишаються без
змін; відсутність цих полів в update payload не перезаписує їх у `null`. Збереження
назви перевіряти за `batchUuid` через `GET /api/v1/storage-items/batches`, а не
лише за відповіддю `PUT`: у ній бухгалтерські поля можуть бути `null`.

#### TC-REL-ACC-016A — Зміна бухгалтерської назви наявної партії

Створити отримання з бухгалтерською назвою A. При редагуванні передати для тієї
самої партії (`batchUuid`) назву B й зберегти. Очікування: `GET` партій повертає
`accResourceId` і видиму назву B; назва A більше не прив'язана до цієї партії.

#### TC-REL-ACC-016B — Зміна дати зовнішнього отримання

Створити отримання минулою датою й відредагувати дату на інший дозволений день.
Очікування: нова дата збережена як `date`, дата в колонці «Отримано» (`receivedAt`)
і дата надходження партії відповідають новому дню. Це також покриття вимоги дати
отримання в `RECEIVED_DATE_TEST_PLAN.md`.

#### TC-REL-ACC-017 — Права доступу

Повторити create/read для дозволеної ролі, користувача іншої локації та
неавторизованого запиту. Зміна бухгалтерської назви через update має бути
доступною лише користувачу з правом редагувати це отримання.

Очікування: чинний RBAC переміщень не послаблено; відмова не розкриває
бухгалтерські назви, суми або складські партії чужої локації.

### P1 — UI та наскрізна поведінка

#### TC-REL-ACC-UI-001 — Поля нового рядка

Відкрити форму отримання, додати ресурс.

Очікування: для рядка доступні два правильно підписані опціональні поля;
введення суми обмежується двома знаками після коми (`1.234` → `1.23` у полі),
після такого приведення підтвердження доступне; keyboard navigation і focus
order логічні; validation message прив'язане до конкретного рядка.

#### TC-REL-ACC-UI-002 — Додати другий рядок того самого ресурсу

Після вибору `R1` додати `R1` повторно з іншою бухгалтерською назвою.

Очікування: селектор не приховує ресурс лише тому, що він уже є у формі; обидва
рядки редагуються незалежно; видалення одного не очищує другий.

#### TC-REL-ACC-UI-003 — Збереження введених значень після помилки

Заповнити кілька рядків, в одному зробити validation-помилку й натиснути
«Підтвердити».

Очікування: помилка видима біля потрібного поля, введені назви, кількості й суми
інших рядків не втрачені, дубльоване натискання не створює кілька переміщень.

#### TC-REL-ACC-UI-004 — Поле «Сплачена сума»

Перевірити форму з усіма порожніми сумами, з однією сумою `0.00`, з однією
додатною сумою та зі змішаними заповненими/порожніми сумами.

Очікування: за всіх порожніх сум верхнє поле відсутнє; уже `0.00` вважається
заповненою сумою і показує «Сплачена сума» `0,00`. Значення `1200.10` і
`300.20` при кількостях `10` і `2` показують `1500,30`; якщо друга сума
порожня, поле показує `1200,10`. Підсумок не множиться на кількість і має два
знаки після коми з десятковою комою.

### P2 — сумісність і міграція

#### TC-REL-ACC-018 — Legacy-партія без нових атрибутів

Відкрити історичне отримання, створене до міграції.

Очікування: GET, журнал і залишки не падають; опціональні нові атрибути мають
`null`/відсутнє значення, backfill не потрібен, чинні кількості не змінюються.

#### TC-REL-ACC-019 — Експорт/накладна/інвентаризація

Перевірити, що бухгалтерська назва відображається в партіях ресурсу в залишках,
а сума там не показується. У журналі, експорті та накладній нові атрибути поки
не відображаються. Наявність кількох бухгалтерських партій не повинна дублювати або
спотворювати поточні підсумки кількості. Дані мають залишатися доступними API для
майбутнього кабінету бухгалтера.

#### TC-REL-ACC-020 — Локалізація та формат

Перевірити українські labels, десятковий роздільник у UI, copy/paste значення з
комою і крапкою та однакове відображення після reload. API продовжує використовувати
JSON number, незалежний від локалі браузера.

## 8. Контракт і реалізована автоматизація в `erp-auto-test`

Фактичний контракт партії:

- `accResourceId` — ідентифікатор бухгалтерської назви з reconciliation source
  `ACCOUNTING`; видимий користувачу текст зберігається в довіднику як
  `externalName`;
- `paidAmount` — повна вартість бухгалтерського рядка, nullable `BigDecimal`;
- `batchNumber` — незалежний номер партії, який не входить до ключа
  бухгалтерської унікальності.

Автоматизовано:

1. DTO request/response та JSON Schema знають `accResourceId` і `paidAmount`.
2. `RelocationDataFactory` уміє будувати бухгалтерську партію і multi-row
   отримання.
3. `RelocationBatchAccountingTest` покриває всі API-сценарії
   `TC-REL-ACC-001…019`: persistence, multi-row, буквальні та нормалізовані
   дублікати назви, дублі безіменних рядків,
   опціональність, межі суми й назви, atomicity, delete rollback, edit,
   RBAC, legacy compatibility, журнал, інвентаризацію та експорти. Негативні
   сценарії перевіряють незмінність залишку та одразу видаляють запис, якщо dev
   помилково прийняв невалідний запит.
4. `RelocationCreateInputPage` має операції для вибору ресурсу, додавання рядка,
   суми, бухгалтерської назви, duplicate error і поля «Сплачена сума».
5. `RelocationBatchAccountingUiTest` покриває `TC-REL-ACC-UI-001…004` та
   `TC-REL-ACC-020`: наявність і локалізацію полів, приведення введеного
   `1.234` до `1.23`, два рядки одного ресурсу, блокування дубліката та
   значення поля «Сплачена сума» для порожніх сум, `0.00` і додатних сум.
6. Нові класи підключені до `relocations.xml`, `regression.xml` та `ui.xml`.

У TCM автоматизовано **24 із 24** кейсів: 19 API та 5 UI; manual-кейсів у feature
не залишилося. Окремий конкурентний stress/race тест unique constraint не входить
до цих 24 функціональних кейсів і може бути доданий пізніше як non-blocking
розширення.

### Цільова перевірка на dev — 29.09.2026 (до остаточного рішення про назви)

UI-покриття розширено окремим сценарієм дубля після `trim` і зміни регістру,
перевіркою очищення єдиної суми та сценарієм із двома різними бухгалтерськими
назвами: `1200.10 + 300.20 = 1500.30` при кількостях `10` і `2`. Другу суму
очищують, щоб перевірити ігнорування порожнього рядка.

- API: цільові тести для `-0.01` і `0.001` пройшли — обидва значення дають
  `HTTP 400` без зміни залишку. Це актуальніший результат за прогін 23.09.
- API: дубль після `trim` і зміни регістру досі приймається (`HTTP 200`
  замість `400`); тест фіксує зміну залишку й видаляє неочікувано створене
  отримання під час cleanup.
- UI: буквальний дубль і локалізовані поля пройшли. Нормалізований дубль
  вибирається в обох рядках, але UI не показує помилку.
- UI: попередній селектор не знаходив окремого блоку «Загальна вартість»;
  атрибут `min` у полі суми відсутній. Пізніше підтверджено верхнє поле
  «Сплачена сума» з потрібним значенням.

Повний прогін двох класів `RelocationBatchAccountingTest` і
`RelocationBatchAccountingUiTest` на dev: **26 виконань, 16 пройшли, 10 впали**.
API: 14/19 пройшли; UI: 2/7 пройшли. Наступні цільові прогони перезаписують
`target/surefire-reports/TEST-TestSuite.xml`, тому цей підсумок зафіксовано тут.

- API падіння: нормалізований і безіменний дублікати прийняті; створення

  порожні бухгалтерські поля у відповіді `PUT` як втрату збережених атрибутів;

### Уточнена продуктова поведінка — 29.09.2026

- Верхнє поле має назву «Сплачена сума», окремого блоку «Загальна вартість»
  немає. Якщо всі суми порожні, поле приховане. Для явно введеного `0.00`
  воно показує `0,00`.
- Суми `1200.10` і `300.20` при кількостях `10` і `2` показують `1500,30`;
  з порожньою другою сумою результат `1200,10`. Сума рядка вже є фактичною
  вартістю позиції, тому кількість її не змінює.
- Після введення `1.234` поле рядка показує `1.23`, підтвердження доступне.
  Цей результат не визначає загальне правило округлення чи відсікання.
  Прямі API-запити з `0.001` та `-0.01` повернули `400`.
- **Чинне правило:** буквально однакова непорожня назва, назви, що збігаються
  після `trim` і зміни регістру, та два безіменні рядки того самого ресурсу
  в одному переміщенні є дублікатами. API має відхиляти всі три випадки з
  `400` без зміни залишку; UI має позначати дубль і блокувати підтвердження.
- **Відкриті баги:** API на dev приймає (`200`) усі три види дублів і створює
  дві партії. UI блокує буквальний дубль, але не позначає назви, що
  збігаються після нормалізації, та залишає підтвердження доступним.
- За попереднім спостереженням UI блокував два безіменні рядки, проте пробний
  автотест не підтвердив саме цю умову: селектор автоматично вибрав
  бухгалтерську назву для першого рядка. Перевірка справді безіменних рядків
  у UI потребує окремої передумови.
- Прямий API-запит із двома буквально однаковими непорожніми назвами на dev
  повернув `200` і створив дві партії, хоча UI блокує такий дубль.

Наведений нижче прогін відбувся до повторного підтвердження правила. Після
оновлення селектора поля суми та попередніх очікувань повний прогін
`RelocationBatchAccountingUiTest` на dev: **8 виконань, 7 пройшли, 1 впало**.
Падав лише тест нормалізованого дубля, що відповідає чинному очікуванню.
Сценарії «Сплачена сума»,
точності введення, буквального дубля та локалізації пройшли. Автотест читає
значення числового `input` з DOM через `inputValue()` з крапкою, наприклад
`1500.30`; видиме користувачу значення має десяткову кому (`1500,30`).

### Історичний прогін із тимчасово зміненим очікуванням дублів

змінено на прийняття. За тих очікувань API-тести пройшли: обидва запити

доступним для нормалізованого дубля. Ці результати підтверджують дефекти
відносно чинного правила; тести знову очікують відмову.

4 впали**. UI: **8/8 пройшли**; API: **16/20 пройшли**. Падіння API:

  завершився `Read timed out`; решту тверджень цього тесту не перевірено.

Ці числа не є підсумком для відновленого правила нормалізованої унікальності.
Після відновлення правила цільовий прогін чотирьох тестів дублів на dev дав
**4 падіння з 4 виконань**: API прийняв буквальний, нормалізований і безіменний
дублі (`200` замість `400`), а UI не показав помилку нормалізованого дубля.
Неочікувано створені API-тестами отримання видалено під час cleanup.

Повний повторний прогін двох класів на dev 29.09.2026 після додавання сценаріїв
редагування: **30 виконань, 22 пройшли, 8 впали, 0 errors, 0 skipped**.
API: **22 виконання, 7 падінь**; UI: **8 виконань, 1 падіння**.

- API прийняв три заборонені дублікати одного ресурсу в одному отриманні:
  буквальну назву, збіг після `trim`/нижнього регістру та два рядки без назви;
  у всіх трьох випадках повернув `200` замість `400` і змінив залишок.
- UI не позначив збіг назв після `trim`/нижнього регістру й не заблокував
  підтвердження. Буквальний дубль UI заблокував.
- Reconciliation із Unicode-назвою з 432 символів Unicode (433 UTF-16 code units)
  повернув `500 Something went wrong`.
- Зміна бухгалтерської назви існуючої партії через `PUT` повернула `200`, але
  партія зберегла попередні `accResourceId` і видиму назву.
- Зміна дати отримання через `PUT` оновила `date`, але `receivedAt` у відповіді
  й журналі та дата складської партії залишилися попередніми.
- `GET /api/v1/relocations/export?receiverIds=...` завершився
  `SocketTimeoutException: Read timed out`. Через це фінальні перевірки обох
  експортів у `TC-REL-ACC-019` не виконалися; правильність їхнього вмісту не
  підтверджена цим прогоном.

Тест `TC-REL-ACC-016` із редагуванням лише примітки пройшов: бухгалтерська
назва збереженої партії не зникла. Негативна сума та три десяткові знаки були
відхилені згідно з поточними очікуваннями тестів. Тестові отримання, створені
під час прогону, видалені у cleanup.

## 9. Критерії входу і виходу

### Вхід у тестування

- опублікований request/response contract із nullable-полями;
- UI labels, формат суми, поле «Сплачена сума» і тексти validation доступні;
- тестове середовище містить міграцію БД і сумісний frontend/backend.

### Вихід

- усі P0 пройдені;
- усі P1 поточного scope пройдені;
- немає часткових змін relocation/stock після негативних сценаріїв;
- у БД неможливо створити дубль нормалізованої бухгалтерської назви для того
  самого ресурсу в одному переміщенні, включно з двома порожніми назвами;
- `relocations`, `inventory` та релевантна UI-регресія не мають нових падінь;
- документація API та UI відповідає фактичній реалізації.

## 10. Ризики

- Якщо UI дозволить повторний ресурс, а backend і далі агрегуватиме лише за
  `resourceId`, одна бухгалтерська назва може перезаписати іншу.
- Java `Map<resourceId, ...>` у fixtures або SUT може непомітно втратити другий
  рядок; тести мають використовувати список і перевіряти обидва значення.
- `double` для суми спричинить втрату точності; у контракті й автотестах потрібен
  десятковий тип (`BigDecimal`/DB decimal).
- Відсутність однакової нормалізації (`trim` і нижній регістр) в UI/backend/БД
  дає різну поведінку для буквальних, регістрових і пробільних дублів.
- Реалізація опціональних полів як `NOT NULL` може зламати читання історичних
  партій; поля мають лишатися nullable без обов'язкового backfill.
- Якщо нові атрибути не копіюються разом із партією під час внутрішньої видачі,
  бухгалтерський зв'язок може втратитися після першого переміщення.
