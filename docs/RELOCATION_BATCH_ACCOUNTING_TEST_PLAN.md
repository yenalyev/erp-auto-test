# Тест-план: бухгалтерська назва та вартість партії ресурсу

Документація нової функціональності для продукту, QA та автоматизації.
Функціональний контур: ресурсні переміщення, форма зовнішнього отримання
`/relocation/create-input` та API створення отримання.
TCM: **REQ-EDIT_REL-008** (модуль `EDIT_REL`, батько `REQ-EDIT_REL`).

Статус: **продуктові правила уточнено; API/UI автотести додано, знайдені
невідповідності реалізації мають залишатися видимими як падіння цільових тестів**.

---

## 1. Мета зміни

Під час отримання ресурсу користувач може вказати для його партії два додаткові
опціональні атрибути:

- **бухгалтерська назва**;
- **вартість (сума)**.

Один ресурс можна внести в одне отримання кількома рядками, якщо бухгалтерські
назви відрізняються. Партія ресурсу має бути унікальною в межах ключа:

`переміщення + ресурс + бухгалтерська назва`.

Приклад очікуваного валідного отримання:

- ресурс «Кабель», бухгалтерська назва «Кабель силовий», кількість 10, сума 1 200,00;
- той самий ресурс «Кабель», бухгалтерська назва «Комплект кабельний», кількість 5,
  сума 900,00.

Це два окремі рядки/партії одного ресурсу в одному переміщенні. Два рядки з тим
самим ресурсом і тією самою бухгалтерською назвою не повинні створювати дві партії.

---

## 2. Межі функціональності

### У scope

- UI форми отримання ресурсу від зовнішнього постачальника;
- створення отримання через `POST /api/v1/relocations/receive`;
- збереження нових атрибутів на рівні партії;
- відповідь API після створення отримання;
- розрахунок і відображення загальної вартості у формі отримання;
- складські залишки після одного й кількох рядків одного ресурсу;
- атомарність і унікальність даних.

### Поза scope, доки немає окремої вимоги

- отримання обладнання;
- повернення від екіпажа (`/relocation/create-input-crew`);
- приймання внутрішньої видачі з вкладки «В дорозі»;
- виробництво та партії виробничих записів;
- глобальний довідник цін ресурсів `/resources-price`;
- перерахунок вартості за курсом або робота з кількома валютами.
- редагування бухгалтерської назви та вартості вже створеного отримання; надалі
  воно має з'явитися в кабінеті бухгалтера;
- відображення нових атрибутів у журналі, залишках, експорті та накладній; надалі
  вони мають використовуватися в кабінеті бухгалтера.

Ці сценарії входять до регресії лише для перевірки, що нові поля не стали для них
неочікувано обов'язковими та не змінили чинну поведінку.

## 3. Функціональні правила для приймання

Підтверджені постановкою правила:

1. Поля «Бухгалтерська назва» і «Сума» доступні для кожного рядка/партії ресурсу
   у формі отримання та є опціональними незалежно одне від одного.
2. В одному отриманні дозволено повторно додати той самий ресурс, якщо в рядках
   різні бухгалтерські назви.
3. У межах одного переміщення комбінація `resourceId + accountingName` унікальна.
4. Нові значення належать партії, а не картці ресурсу та не переміщенню загалом.
5. `batchNumber` залишається окремим атрибутом партії та не входить до нового
   унікального ключа. Інший номер партії не дозволяє повторити ту саму комбінацію
   `resourceId + accountingName` в одному переміщенні.
6. «Сума» — повна вартість конкретного бухгалтерського рядка, не ціна за одиницю.
7. Сума має бути `0` або більше, допускає не більше двох знаків після коми та в UI
   відображається з двома знаками після коми.
8. Для бухгалтерської назви немає бізнес-обмеження довжини або набору символів.
   Для формування унікального ключа до значення застосовується `trim`, а регістр
   не враховується. Інші символи назви не змінюються.
9. Якщо заповнена хоча б одна сума, форма показує загальну вартість переміщення —
   суму всіх заповнених значень. Порожні суми не додають значення до підсумку.
   Якщо всі суми порожні, блок загальної вартості не показується.
10. Нові атрибути поки не відображаються в журналі, залишках, експорті чи накладній;
    наступним споживачем даних планується кабінет бухгалтера.

Правила, які має однаково забезпечувати UI і backend:

- UI показує помилку для дубліката нормалізованого ключа та не підтверджує форму;
- прямий API-запит із дублікатом має бути відхилений, а не створити суперечливі
  партії;
- помилка одного рядка не повинна частково зараховувати інші рядки отримання;
- загальний залишок ресурсу збільшується на суму кількостей усіх його валідних
  бухгалтерських рядків; бухгалтерська сума не змінює фізичну кількість;
- два різні ресурси можуть мати однакову бухгалтерську назву;
- той самий ресурс і та сама бухгалтерська назва можуть повторюватися в різних
  переміщеннях.
- порожня або відсутня бухгалтерська назва після нормалізації розглядається як
  одне порожнє значення: для одного ресурсу в одному переміщенні не можна створити
  кілька безіменних бухгалтерських рядків.

---

## 4. Поведінка після створення

Поточна зміна покриває введення бухгалтерських атрибутів лише під час створення
отримання. Після збереження користувач поки не бачить і не редагує ці значення в
журналі, залишках, експорті, накладній або чинній формі редагування. Перегляд і
редагування плануються в майбутньому кабінеті бухгалтера.

Водночас чинне редагування інших даних отримання через
`PUT /api/v1/relocations/{id}/receive?storageId=` не повинно очищати або змінювати
раніше збережені бухгалтерські атрибути, навіть якщо їх немає в update payload.

---

## 5. Тестові дані та передумови

Потрібні:

- користувач із правом створювати отримання для конкретного складу;
- зовнішній постачальник;
- два активні ресурси `R1` і `R2` з однаковою одиницею вимірювання;
- ресурс `R3` з дробовою одиницею вимірювання, якщо система це підтримує;
- унікальні номер накладної та номер партії для кожного сценарію;
- можливість прочитати переміщення через API та перевірити складський залишок;
- для конкурентного тесту — два паралельні запити з однаковою версією/ключем.

Базовий набір значень:

- бухгалтерські назви: `Кабель силовий`, `Комплект кабельний`, `кабель силовий`,
  ` Кабель силовий `, `Кабель/силовий №1`;
- кількості: `10`, `5`, `0.5`;
- суми: `1200.00`, `900.00`, `0`, `0.10`, `-1`, `0.001` та дуже велике додатне
  значення.

## 6. Основні тестові сценарії

### P0 — критичний бізнес-потік

#### TC-REL-ACC-001 — Один ресурс, одна бухгалтерська назва

Створити отримання `R1`, заповнити кількість, бухгалтерську назву та суму.

Очікування:

- отримання успішно створене;
- відповідь API містить точні значення нових атрибутів у потрібній партії;
- залишок `R1` збільшився на введену кількість;
- форма показує загальну вартість `1200.00`;
- після збереження API повертає значення без втрати точності.

#### TC-REL-ACC-002 — Один ресурс, дві різні бухгалтерські назви

Додати в одне отримання два рядки `R1`: `Кабель силовий` і
`Комплект кабельний`, з різними кількостями та сумами.

Очікування:

- обидва рядки можна ввести й підтвердити;
- створено дві окремі партії з правильними парами назва/кількість/сума;
- `R1` не дублюється як два незалежні підсумкові ресурси, якщо контракт агрегує
  items за ресурсом;
- фізичний залишок `R1` збільшився на суму кількостей обох рядків;
- значення одного рядка не підмінили значення іншого;
- загальна вартість дорівнює сумі вартостей двох рядків.

#### TC-REL-ACC-003 — Дублікат ресурсу та бухгалтерської назви

Додати два рядки `R1` з бухгалтерськими назвами, однаковими буквально або після
нормалізації, наприклад `Кабель силовий` і ` кабель силовий `.

Очікування:

- UI показує помилку, не дозволяє підтвердити форму та чітко позначає конфліктний
  рядок;
- прямий API-запит отримує узгоджену validation-відповідь;
- переміщення та жодна з його партій не створені;
- залишок не змінився.

#### TC-REL-ACC-004 — Одна назва для різних ресурсів

Створити рядки `R1` і `R2` з однаковою бухгалтерською назвою.

Очікування: отримання успішне, оскільки `resourceId` є частиною унікального ключа;
обидва залишки та партії збережені правильно.

#### TC-REL-ACC-005 — Одна комбінація в різних переміщеннях

Створити два отримання з однаковими `R1 + accountingName`.

Очікування: обидва успішні, оскільки `relocationId` є частиною ключа; залишок
збільшився на суму кількостей двох переміщень.

#### TC-REL-ACC-006 — Опціональні поля

Окремо створити отримання з такими варіантами рядка: обидва поля порожні, лише
бухгалтерська назва, лише сума, обидва поля заповнені.

Очікування: усі чотири варіанти валідні; відсутні значення передаються як
відсутнє поле або `null` згідно з API-контрактом; фізичний залишок у всіх випадках
збільшується на кількість ресурсу.

#### TC-REL-ACC-007 — Порожня назва в унікальному ключі

Додати в одне отримання два рядки `R1` без бухгалтерської назви, у тому числі
варіант `null` і рядок лише з пробілів.

Очікування: після `trim` обидва значення утворюють один порожній ключ; UI показує
помилку дубліката, API не створює дві безіменні партії одного ресурсу.

#### TC-REL-ACC-008 — Видалення отримання з кількома бухгалтерськими рядками

Видалити дозволене зовнішнє отримання.

Очікування: усі його партії видалені/деактивовані згідно з чинною моделлю,
загальна кількість повністю списана із залишку, чужі партії не змінені.

#### TC-REL-ACC-009 — Атомарність multi-resource запиту

Надіслати валідні рядки `R1` і невалідний/дубльований рядок `R2` одним запитом.

Очікування: весь запит відхилений; немає relocation, партій або часткової зміни
залишків.

#### TC-REL-ACC-010 — Сума є повною вартістю, не ціною одиниці

Додати `R1` у кількості `10` із сумою `1200.00`, а `R2` у кількості `2` із сумою
`300.00`.

Очікування: загальна вартість дорівнює `1500.00`; система не множить введені
значення на кількість ресурсу й не показує `12600.00`.

### P1 — валідація і контракт

#### TC-REL-ACC-011 — Null, відсутнє поле і пробіли

Перевірити відсутнє поле, `null`, порожній рядок і рядок лише з пробілів для назви;
відсутнє поле та `null` для суми.

Очікування: усі варіанти дозволені; для унікальності назва порівнюється після
`trim`, а значення лише з пробілів еквівалентне порожній назві; загальна вартість
не показується, якщо в усіх рядках сума відсутня.

#### TC-REL-ACC-012 — Межі суми

Перевірити `0`, ціле число, один і два знаки після коми, від'ємне значення, три
знаки після коми та дуже велике додатне значення.

Очікування: `0` і додатні значення з scale до 2 валідні та показуються з двома
знаками; від'ємне значення і scale понад 2 відхиляються; UI і API застосовують
однакові правила; після відмови дані та залишки незмінні.

#### TC-REL-ACC-013 — Межі бухгалтерської назви

Перевірити 1 символ, довгі рядки, кирилицю, латиницю, цифри, апостроф, дефіс,
переноси, лапки та HTML/JS-подібний текст.

Очікування: UI не встановлює бізнес-ліміт довжини або набору символів, значення не
обрізається і не спотворюється; під час відображення текст екранується і не
виконується як markup/script.

#### TC-REL-ACC-014 — Нормалізація унікальності

Перевірити пари `Назва` / `назва` та `Назва` / ` Назва `.

Очікування: обидві пари є дублікатами; UI показує помилку, API відхиляє запит,
DB constraint/нормалізований ключ не дозволяє обійти правило паралельним запитом.

Окремо перевірити однакові `resourceId + accountingName` з різними `batchNumber`:
це також дублікат, оскільки номер партії не входить до ключа унікальності.

#### TC-REL-ACC-015 — Узгодженість item amount і batches

Прямим API надіслати `item.amount`, що не дорівнює сумі `batches[].amount`.

Очікування: чинний інваріант кількості збережено; запит відхилений атомарно або
сервер однозначно обчислює total за документованим правилом.

#### TC-REL-ACC-016 — Контракт create/read і збереження після звичайного edit

Перевірити JSON schema та типи нових полів у request/response, серіалізацію
десяткової суми без втрати точності, стабільність назв полів і повернення значень
після POST та подальшого GET. Після цього змінити через чинний PUT лише дозволене
небухгалтерське поле отримання.

Очікування: бухгалтерські назва і сума не редагуються, але залишаються без змін;
відсутність цих полів в update payload не перезаписує їх у `null`.

#### TC-REL-ACC-017 — Права доступу

Повторити create/read для дозволеної ролі, користувача іншої локації та
неавторизованого запиту. Чинний update інших полів не повинен дозволяти підмінити
бухгалтерські атрибути обхідним payload.

Очікування: чинний RBAC переміщень не послаблено; відмова не розкриває
бухгалтерські назви, суми або складські партії чужої локації.

### P1 — UI та наскрізна поведінка

#### TC-REL-ACC-UI-001 — Поля нового рядка

Відкрити форму отримання, додати ресурс.

Очікування: для рядка доступні два правильно підписані опціональні поля; сума
приймає невід'ємне число з максимум двома знаками після коми та відображається з
двома знаками; keyboard navigation і focus order логічні; validation message
прив'язане до конкретного рядка.

#### TC-REL-ACC-UI-002 — Додати другий рядок того самого ресурсу

Після вибору `R1` додати `R1` повторно з іншою бухгалтерською назвою.

Очікування: селектор не приховує ресурс лише тому, що він уже є у формі; обидва
рядки редагуються незалежно; видалення одного не очищує другий.

#### TC-REL-ACC-UI-003 — Збереження введених значень після помилки

Заповнити кілька рядків, в одному зробити validation-помилку й натиснути
«Підтвердити».

Очікування: помилка видима біля потрібного поля, введені назви, кількості й суми
інших рядків не втрачені, дубльоване натискання не створює кілька переміщень.

#### TC-REL-ACC-UI-004 — Загальна вартість форми

Перевірити форму з усіма порожніми сумами, з однією сумою `0.00`, з однією
додатною сумою та зі змішаними заповненими/порожніми сумами.

Очікування: за всіх порожніх сум підсумок відсутній; уже `0.00` вважається
заповненою сумою і показує загальну вартість `0.00`; в інших випадках підсумок
дорівнює сумі заповнених значень, а порожні рядки не змінюють результат.

### P2 — сумісність і міграція

#### TC-REL-ACC-018 — Legacy-партія без нових атрибутів

Відкрити історичне отримання, створене до міграції.

Очікування: GET, журнал і залишки не падають; опціональні нові атрибути мають
`null`/відсутнє значення, backfill не потрібен, чинні кількості не змінюються.

#### TC-REL-ACC-019 — Експорт/накладна/інвентаризація

Перевірити, що нові атрибути поки не відображаються в журналі, залишках, експорті
та накладній. Наявність кількох бухгалтерських партій не повинна дублювати або
спотворювати поточні підсумки кількості. Дані мають залишатися доступними API для
майбутнього кабінету бухгалтера.

#### TC-REL-ACC-020 — Локалізація та формат

Перевірити українські labels, десятковий роздільник у UI, copy/paste значення з
комою і крапкою та однакове відображення після reload. API продовжує використовувати
JSON number, незалежний від локалі браузера.

## 8. Контракт і реалізована автоматизація в `erp-auto-test`

Фактичний контракт партії:

- `accResourceId` — ідентифікатор бухгалтерської назви з reconciliation source
  `ACCOUNTING`; видимий користувачу текст зберігається в довіднику як
  `externalName`;
- `paidAmount` — повна вартість бухгалтерського рядка, nullable `BigDecimal`;
- `batchNumber` — незалежний номер партії, який не входить до ключа
  бухгалтерської унікальності.

Автоматизовано:

1. DTO request/response та JSON Schema знають `accResourceId` і `paidAmount`.
2. `RelocationDataFactory` уміє будувати бухгалтерську партію і multi-row
   отримання.
3. `RelocationBatchAccountingTest` покриває всі API-сценарії
   `TC-REL-ACC-001…019`: persistence, multi-row, normalized uniqueness,
   опціональність, межі суми й назви, atomicity, delete rollback, edit,
   RBAC, legacy compatibility, журнал, інвентаризацію та експорти. Негативні
   сценарії перевіряють незмінність залишку та одразу видаляють запис, якщо dev
   помилково прийняв невалідний запит.
4. `RelocationCreateInputPage` має операції для вибору ресурсу, додавання рядка,
   суми, бухгалтерської назви, duplicate error і загальної вартості.
5. `RelocationBatchAccountingUiTest` покриває `TC-REL-ACC-UI-001…004` та
   `TC-REL-ACC-020`: наявність і локалізацію полів, крок `0.01`, формат суми,
   два рядки одного ресурсу, блокування дубліката та підсумок для
   `0.00`/додатної суми.
6. Нові класи підключені до `relocations.xml`, `regression.xml` та `ui.xml`.

У TCM автоматизовано **24 із 24** кейсів: 19 API та 5 UI; manual-кейсів у feature
не залишилося. Окремий конкурентний stress/race тест unique constraint не входить
до цих 24 функціональних кейсів і може бути доданий пізніше як non-blocking
розширення.

## 9. Критерії входу і виходу

### Вхід у тестування

- опублікований request/response contract із nullable-полями;
- UI labels, формат суми, загальна вартість і тексти validation доступні;
- тестове середовище містить міграцію БД і сумісний frontend/backend.

### Вихід

- усі P0 пройдені;
- усі P1 поточного scope пройдені;
- немає часткових змін relocation/stock після негативних сценаріїв;
- у БД неможливо створити дублікат узгодженого normalized unique key;
- `relocations`, `inventory` та релевантна UI-регресія не мають нових падінь;
- документація API та UI відповідає фактичній реалізації.

## 10. Ризики

- Якщо UI дозволить повторний ресурс, а backend і далі агрегуватиме лише за
  `resourceId`, одна бухгалтерська назва може перезаписати іншу.
- Java `Map<resourceId, ...>` у fixtures або SUT може непомітно втратити другий
  рядок; тести мають використовувати список і перевіряти обидва значення.
- `double` для суми спричинить втрату точності; у контракті й автотестах потрібен
  десятковий тип (`BigDecimal`/DB decimal).
- Unique constraint без такої самої нормалізації в UI/backend дасть різну поведінку
  для регістру та пробілів.
- Реалізація опціональних полів як `NOT NULL` може зламати читання історичних
  партій; поля мають лишатися nullable без обов'язкового backfill.
- Якщо нові атрибути не копіюються разом із партією під час внутрішньої видачі,
  бухгалтерський зв'язок може втратитися після першого переміщення.
