# Редагування техкарт, доданих у глобальний план

## Бізнес-правило

Техкарту, яка збережена в `decomposition` snapshot актуального глобального плану, можна редагувати. Актуальним вважається план поточного календарного місяця або майбутнього періоду.

Архівація такої техкарти й надалі заборонена: `DELETE /api/v1/technological-maps/{id}?storageId={storageId}` повертає `400` з посиланням на глобальний план.

## Видалення та архівація

`DELETE` техкарти є soft-delete: карта деактивується й зникає зі списку активних, але її запис та історичні посилання зберігаються.

- якщо точний `id` техкарти є в `decomposition` snapshot поточного або майбутнього глобального плану, архівація заборонена для OWNER і ADMIN; карта лишається активною;
- наявність іншої активної карти для того самого продукту не обходить guard актуального snapshot;
- глобальний план без `generate` не має snapshot і не блокує архівацію;
- якщо карта є лише в snapshot минулого плану, архівація дозволена, а історичний snapshot продовжує зберігати її `id`;
- після дозволеної архівації можна створити нову карту на той самий output-продукт і використати її під час `decompose` та `generate` нового актуального плану.

## Варіанти редагування

### Зміна лише назви

- `PUT /api/v1/technological-maps/{id}` повертає `200`;
- `id`, `groupId` і `version` не змінюються;
- snapshot глобального плану лишається валідним.

### Структурна зміна

Структурною зміною є зміна складу або кількості input/output ресурсів чи альтернативних груп, включно з default-альтернативою.

- `PUT /api/v1/technological-maps/{id}` повертає `200`;
- створюється нова активна версія з новим `id` і `version + 1` у тому самому `groupId`;
- попередня версія стає неактивною, але не видаляється;
- `decomposition` snapshot не мігрує автоматично й продовжує містити `id` попередньої версії;
- у кожному актуальному глобальному плані ресурс треба призначити повторно на вкладці «Хто буде виробляти?» та ще раз згенерувати плани на локації.

## Інформування UI

Форма редагування викликає `GET /api/v1/technological-maps/{id}/global-plans`.

Endpoint:

- доступний користувачеві з `tech-map-list::read`;
- повертає `id`, `description`, `from`, `to` поточних і майбутніх планів, snapshot яких посилається на техкарту;
- не повертає минулі плани;
- повертає порожній список для карти без актуальних посилань.

Якщо список непорожній, UI показує warning із посиланнями на плани. Під час structural edit після першого натискання «Зберегти» UI відкриває confirmation «Створити нову версію техкарти?». `PUT` виконується лише після підтвердження. Для зміни лише назви цей modal не потрібен.

Текст warning:

> Ця техкарта використовується в глобальних планах: **{назва плану}**.
> Зміна складу ресурсів, кількостей або альтернативних груп створить нову версію картки. Розподіл у цих планах доведеться перепризначити: відкрийте план, на вкладці «Хто буде виробляти?» призначте ресурс знову й повторно згенеруйте плани на локації.

Назва кожного плану є клікабельним посиланням `/global-plans/{id}`.

Після структурної зміни та натискання «Зберегти» показується confirmation popup:

- title: «Створити нову версію техкарти?»;
- description: «Розподіл у глобальних планах {UI-назва плану} стане недійсним для цієї картки. Після збереження відкрийте кожен план, призначте ресурс знову й повторно згенеруйте плани на локації.»; UI-назва дорівнює періоду (`Вересень 2026`), якщо description збігається з ним, інакше має формат `{description} ({період})`;
- actions: «Скасувати» і «Зберегти»;
- «Скасувати» закриває popup без `PUT` і без створення нової версії.

## Минулі плани та відсутній snapshot

Минулі глобальні плани не блокують архівацію або structural edit. Їх snapshot може відтворювати неактивну історичну версію. План, створений без `generate`, не має decomposition snapshot і також не створює обмеження архівації.

Якщо одна карта одночасно є в минулому й актуальному snapshot, для архівації діє обмеження актуального плану, а structural edit створює нову версію за правилами вище.

## Автоматизоване покриття

- `TC-GP-046/047/048` — архівація карти з актуального snapshot заборонена.
- `TC-GP-049` — без snapshot архівація дозволена.
- `TC-GP-056` — карта лише в історичному snapshot архівується, snapshot зберігає її id.
- `TC-GP-060` — після архівації replacement-карта працює у новому актуальному плані.
- `TC-GP-053/058` — name-only update не змінює id/version для майбутнього й поточного місяця.
- `TC-GP-054/059` — structural update дозволений; створюється version+1, стара версія неактивна, snapshot зберігає старий id.
- `TC-GP-057/061/062` — structural edit історичних snapshot і взаємодія з новими актуальними планами.
- `TC-GP-063` — endpoint актуальних GP повертає повні references і `[]` для невикористаної карти.
- `TC-GP-UI-063` — warning, link, confirmation modal, successful PUT і незмінний snapshot у UI-flow.
- `TC-GP-UI-064` — точний title/description/actions confirmation popup; cancel не створює нову версію.

Виявлена суміжна контрактна неузгодженість DEV: безпосередня відповідь structural `PUT` містить resource `id`, але `name` і `unit` можуть бути `null`. Persisted нова версія читається повністю через наступний `GET`; бізнес-флоу й UI працюють. Це не змінює описане правило versioning, але response DTO потребує окремого виправлення або узгодження JSON Schema.
