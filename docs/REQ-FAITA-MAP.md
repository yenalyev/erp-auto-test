# Словник мапінгу Файта — Цукерка для витрат

Версія вимог і тест-плану: 17.10.2026. Середовище перевірки: dev.
Ідентифікатор: `REQ-FAITA-MAP`. SUT: `tk` / `tk-ui`; зміни в цьому завданні стосуються лише автотестів.

## Призначення та межі

Довідник дозволяє переглядати зіставлення назв Файти з ресурсами Цукерочки для витрат. У сайдбарі є пункт **Словники Файти**, на екрані — вкладки **Амуніція** та **Ініціатори**. Назву «Амуніція» замість початкового «БЧ» та окремі поля пошуку користувач погодив 17.10.2026. Це окремий довідник: існуючий екран `/faita-resources` використовує resource reconciliation та implicit resources і не є підтвердженням реалізації цієї вимоги.

БЧ читаються з `faita.resource_alias_with_ammo`; ініціатори — з `faita.resource_alias_with_initiators`. Обидві таблиці отримують `updated_by`; усім записам, що існували до міграції, встановлюється рядок `system` зі збереженням бізнес-полів мапінгу. Назва Файти — саме `name`, а не колишні `ammunition_name` чи `initiator_name`. Ресурс відображається за `resource_id`; колонка множника належить лише БЧ.

Погоджений обсяг доповнено 17.10.2026: створення та видалення зіставлень для обох вкладок. Додатково перевіряються кнопка з олівцем і початок редагування. Додатково автоматизовано чинний PUT-контракт із `tk-ui/FaitaAliasDialog`: зміна ресурсу, для БЧ також множника й `matchByName`, автор поточного користувача та незмінність сусіднього запису. Ці додаткові перевірки описують реалізацію, а не розширюють погоджену вимогу.

## Фактично знайдена реалізація

Екран `/faita-mapping`, `FaitaMappingController`, міграція `V156__faita_mapping.sql`. API: `GET /api/v1/faita-mapping/ammunition` та `/initiators`; параметри `faitaName`, `resourceName`, `sort`, `page`, `size`. Окремі endpoint `/unmapped` повертають відсутні мапінги із витрат Файти. PUT на `/{id}` приймає `{resourceId,multiplier,matchByName}` для БЧ і `{resourceId}` для ініціаторів. Доступ регулюється `faita-mapping::read/create/update/delete`, видимість меню — `view`.

Погоджені відмінності: вкладка **Амуніція** замість **БЧ**, два незалежні поля **Назва Файти** та **Ресурс**, які разом діють як AND. Відповідні АС і тести оновлено за прямим рішенням користувача; початковий звіт із 7 FAIL залишається історичним доказом попередньої версії вимог.

17.10.2026 користувач також погодив заміну чекбокса перемикачем **Неспівставлені/Співставлені** для обох вкладок. «Неспівставлені» — черга позицій із витрат Файти, а не фільтр aliases за `resource_id=NULL`; «Співставлені» — список aliases. Колонки ресурсу, множника, редагування та сортування за двома ключами стосуються списку aliases. У черзі є назва, остання витрата, дія «Співставити», для амуніції також виробник; пошук за назвою доступний в обох режимах, за ресурсом — лише у «Співставлені».

17.10.2026 за рішенням користувача перевірки штучно неконсистентних aliases вилучено як несуттєві. Після додавання створення й видалення чинний набір містить 31 кейс; вилучені TC-FMAP-API-009…012 не відновлюються. Результати попередніх прогонів та SELECT-аудиту збережено в історичних звітах; вони не входять до поточного release gate.

## Декомпозиція фіч

- `REQ-FAITA-MAP`: навігація та загальна бізнес-вимога.
- `REQ-FAITA-MAP-AUDIT`: зміна схеми й міграція історичних записів обох таблиць.
- `REQ-FAITA-MAP-AMMO`: вкладка Амуніція, значення, пошук, неспівставлені, сортування й редагування.
- `REQ-FAITA-MAP-INIT`: відповідна поведінка вкладки Ініціатори без множника.

Це стабільні бізнес-ID для TCM; батько трьох дочірніх фіч — `REQ-FAITA-MAP`.

## Критерії приймання

### REQ-FAITA-MAP

- **AC-01.** Авторизований користувач із доступом до довідника бачить у сайдбарі «Словники Файти»; перехід відкриває екран із вкладками «Амуніція» та «Ініціатори». Назву погоджено 17.10.2026.

### REQ-FAITA-MAP-AUDIT

- **AC-01.** У `faita.resource_alias_with_ammo` є текстове поле `updated_by`. Кожний запис, що існував до міграції, отримує `system`; ID, `name`, прив'язки, множник та `match_by_name` зберігаються.
- **AC-02.** Те саме для `faita.resource_alias_with_initiators`; міграція зберігає ID, `name` та прив'язки.

### REQ-FAITA-MAP-AMMO

- **AC-01.** Вкладка «Амуніція» показує записи саме `resource_alias_with_ammo`: «Назва Файти» = `name`, «Ресурс» = назва за `resource_id`, «Множник» = `multiplier`, включно з відмінними від 1 і дробовими збереженими значеннями. Запис без прив'язки залишається видимим.
- **AC-02.** Два незалежні поля «Назва Файти» та «Ресурс» шукають за відповідним атрибутом; разом діють як AND. Немає збігів — немає рядків даних. Очищення одного поля зберігає другий фільтр; очищення обох відновлює список. Погоджено 17.10.2026.
- **AC-03.** Замість чекбокса погоджено взаємовиключні режими «Неспівставлені» / «Співставлені». «Неспівставлені» показує чергу витрат Файти з назвою, виробником, останньою витратою та дією «Співставити»; пошук назви звужує чергу, відсутній збіг дає порожній результат, очищення відновлює чергу. Поле «Ресурс» доступне лише у «Співставлені»; повернення до цього режиму відновлює колонки й список aliases згідно з фільтрами. Погоджено 17.10.2026.
- **AC-04.** За замовчуванням обрано «Назва Файти». Обидва напрями сортують за `name`, потім `resource_name` в одному напрямі; порядок другого ключа перевіряється на однакових `name`.
- **AC-05.** Обидва напрями сортування за «Ресурс» застосовують `resource_name`, потім `name` в одному напрямі; порядок другого ключа перевіряється на однакових ресурсах.
- **AC-06.** У рядку є кнопка редагування з іконкою олівця; натискання починає редагування цього запису. Форма без збереження не змінює дані.

- **AC-07.** Створення: дія «Співставити» відкриває форму вибраного FAITA ID; без ресурсу «Зберегти» недоступне. «Скасувати» не створює alias. Збереження з власним ресурсом створює рівно один alias із правильними FAITA ID/resource_id та created_by/updated_by поточного користувача; для амуніції зберігається введений множник (у тесті 1.75) і matchByName=false. Ціль зникає з черги й видима у «Співставлені» після reload; сусідні aliases збережені.
- **AC-08.** Видалення: підтвердження показує назву й ресурс вибраного alias. Скасування зберігає запис незмінним; підтвердження видаляє лише його. GET, SQL та reload підтверджують відсутність; сусідній alias не змінюється. Перерахунок витрат і refresh views не входять до цього кейсу.

### REQ-FAITA-MAP-INIT

- **AC-01.** Вкладка «Ініціатори» показує записи саме `resource_alias_with_initiators`: «Назва Файти» = `name`, «Ресурс» = назва за `resource_id`; запис без прив'язки залишається видимим; множник не виводиться.
- **AC-02.** Погоджені окремі поля «Назва Файти» та «Ресурс», AND, порожній результат і незалежне очищення працюють як на вкладці «Амуніція».
- **AC-03.** Погоджений перемикач «Неспівставлені» / «Співставлені», пошук назви, порожній результат, очищення та повернення до aliases працюють як для амуніції. Черга містить назву, останню витрату й дію «Співставити» без виробника/множника; пошук ресурсу доступний лише у «Співставлені». Погоджено 17.10.2026.
- **AC-04.** Типове сортування — «Назва Файти»; ASC/DESC застосовує `name`, потім `resource_name` в одному напрямі.
- **AC-05.** Сортування «Ресурс» ASC/DESC застосовує `resource_name`, потім `name` в одному напрямі.
- **AC-06.** Є кнопка з олівцем для початку редагування відповідного запису; закриття без збереження не змінює дані.

- **AC-07.** Створення: дія «Співставити» відкриває форму вибраного FAITA ID; без ресурсу «Зберегти» недоступне. «Скасувати» не створює alias. Збереження з власним ресурсом створює рівно один alias із правильними FAITA ID/resource_id та created_by/updated_by поточного користувача; для амуніції зберігається введений множник (у тесті 1.75) і matchByName=false. Ціль зникає з черги й видима у «Співставлені» після reload; сусідні aliases збережені.
- **AC-08.** Видалення: підтвердження показує назву й ресурс вибраного alias. Скасування зберігає запис незмінним; підтвердження видаляє лише його. GET, SQL та reload підтверджують відсутність; сусідній alias не змінюється. Перерахунок витрат і refresh views не входять до цього кейсу.

## Стратегія тестування

Початковий release gate — читання реальної схеми dev і навігація ADMIN через реальний сайдбар. Відсутні поле або пункт меню — FAIL із фактичним доказом; такі перевірки не маскуються під PASS чи «інтеграція вимкнена». Сценарії, до яких неможливо дійти через відсутню реалізацію, у звіті позначаються як заблоковані тим самим release gap, а не як незалежні дефекти пошуку/сортування.

Чотири DB-тести перевіряють deployed схему, відсутність порожніх авторів та backfill. Alias ALTER statements зі знімка реальної V156 виконуються на двох TEMP legacy-таблицях PostgreSQL: змінюється лише кваліфікатор схеми на `pg_temp`. Перевіряються `system`, кількість рядків і збереження бізнес-полів mapped/unmapped записів; транзакція відкочується. Sequence repairs та індекси materialized view з повної V156 цим кейсом не виконуються. Це підтверджує поведінку SQL на legacy-даних; без знімка до історичного деплою воно не доводить незмінність кожного колишнього рядка dev.

Дев’ятнадцять UI-тестів проходять через Playwright із чинною OAuth-сесією ADMIN. Сценарії даних створюють два власні ERP-ресурси та п'ять aliases тільки для відповідної вкладки. Створення aliases через JDBC потрібне для повторів і legacy NULL-прив'язок, які не створюються валідним POST-контрактом. Fixture використовує власний marker, зберігає створені ID, після методу видаляє лише свої aliases та деактивує власні ресурси. Події імпорту, записи витрат і складські залишки не створюються. TC-FMAP-UI-008/009 перевіряють погоджені режими, їх взаємовиключність, пошук реальної позиції з GET /unmapped, порожній результат, очищення й повернення до власних aliases.

Вісім API-тестів незалежно перевіряють обидві таблиці: значення та типовий порядок, окремі фільтри й AND/скидання, чотири варіанти сортування з повторами ключів, збереження через PUT з аудитом і незмінністю сусіднього alias. Поля `ammunition_name` та `initiator_name` у V156 видалено; зіставляються бізнес-поля `name`, `resource_id`, множник та ознака для БЧ.

Дані для кожної вкладки:

1. Однакова назва А: ресурс B, потім ресурс A; порядок вставки протилежний другому ключу ASC.
2. Назва Б: ресурс B; назва В: ресурс A. Це забезпечує однакові ресурси з різними назвами.
3. Назва Я: legacy alias із `resource_id = NULL`, лише перевірка відображення порожнього ресурсу у списку aliases. Це не позиція черги «Неспівставлені»; справжній FAITA ID до цього alias не прив’язується.
4. Для БЧ множники: `2`, `1.5`, `1`, `3`, `0.25`; перевіряється числове значення, а не формат десяткового роздільника.

Обидві вкладки перевіряються окремими методами з власними `@TestCaseId`. Усі 31 кейс мають код і входять у `faita-expense-mapping.xml` та `regression.xml`. Скріншоти додаються в Allure перед навігацією й на ключових кроках.

Ці додаткові сценарії залишаються поза чинним погодженим розширенням. Поточний набір не заявляє автоматизованого покриття решти цих сценаріїв, повного UI-редагування зі збереженням чи фактичного списання витрат; вони не позначаються як перевірені лише через наявність коду.

### Ізоляція створення й видалення

UI-016/017 перевіряють створення для амуніції/ініціаторів; UI-018/019 — видалення. Для кожного кейсу береться існуючий неспівставлений FAITA ID і власний UUID ERP-ресурс. Guard перевіряє відсутність alias за ID; для амуніції також виключає takeover чужого name-only alias з тією самою назвою. Події, довідники Файти, materialized views і stock не змінюються. Створення виконується через UI; для незалежного сценарію видалення setup використовує штатний POST. Cleanup завжди видаляє лише aliases за парою FAITA ID + власний resource_id, перевіряє відсутність і деактивує лише свої ERP-ресурси. Сусідній власний alias звіряється з повним SQL snapshot.

Повернення позиції до черги після видалення залежить також від актуальності materialized view витрат. Тести не запускають імпорт/refresh і не заявляють перевірки повного перерахунку витрат.

## Припущення та відкриті питання

Ці пункти не є новими погодженими продуктовими вимогами:

- Початковий напрям для «Назва Файти» у тестах прийнято ASC; вимога прямо задає лише колонку за замовчуванням.
- Початкове трактування «Неспівставлені = resource_id IS NULL» було припущенням тест-плану. Перевірки штучного NULL/неіснуючого ERP-ресурсу вилучено за рішенням користувача; вони поза чинним обсягом.
- Порядок NULL при сортуванні за ресурсом не визначено. Перевірки двох ключів виконуються на зіставлених рядках.
- Чинний редактор — dialog із закриттям Escape; це звірено з `FaitaAliasDialog`.
- У вимозі не визначено матрицю прав ролей, валідацію множника, можливість скинути прив'язку, поведінку конфліктного редагування, пошук без урахування регістру/пробілів, пагінацію та перенесення фільтрів між вкладками. Наявний код не є погодженням цих правил.
- Міграцію SQL перевірено на TEMP legacy-даних; для доказу незмінності всіх історичних dev-записів потрібен знімок до деплою.

Після узгодження цих контрактів потрібні додаткові сценарії відхилених змін, RBAC та регресії фактичного списання витрат. Поточний набір не заявляє такого покриття. Позитивний PUT, автор і незмінність сусіднього запису вже входять у API-набір.
